# English

## Overview

TimeVault (version 1.1.0) serves a JSON API below `/api/v1` and server-rendered pages. Both are implemented by the same service layer, so they behave identically. This document describes what exists now; it differs from the illustrative API in plan.md §6 in the ways listed in [Differences from plan.md](#differences-from-planmd).

## Conventions

- **Authentication.** Reading is open to everyone; everything that changes something, and everything that shows the inside of the service, needs an account (see [Who may call what](#who-may-call-what)). Sign in with `POST /login` (form fields `username`, `password`, optional `next`). `username` is the employee ID, the name or the e-mail address of a company account from the Redis user directory, or the name of the local administrator. The response sets the `tv_session` cookie (HttpOnly, SameSite=Lax, Secure when the Site setting `cookie_secure` is `true`). A protected endpoint answers `401` with a JSON error when there is no valid session, and `403` when the account may not do it. The sign-in itself answers `401` for a wrong or unknown account (the same text for every reason), `429` with `Retry-After` when too many attempts were made, and `503` when the user directory cannot be reached. **Single sign-on** (when the Site setting `sso_host` is set) is the other way in: the login page calls `POST /auth/sso/start` and then `POST /auth/sso/poll` (see [Page routes](#page-routes)).
- **Base path.** With the Site setting `base_path` set to `/tv` (see [runbook.md](./runbook.md#behind-a-reverse-proxy-under-a-path)) every path in this document is under `/tv` as the browser sees it (`/tv/api/v1/sources`, `/tv/login`). The service also accepts a request without the prefix, for a proxy that takes it off. The `Location` headers of the API and the `next` of `POST /auth/sso/poll` carry the prefix, and the cookies are limited to it. Without the setting every path is as written here.
- **Folder access.** What a caller may do with a monitored folder is its **level** on that folder: `browse`, `backup` or `full` (see [Who may call what](#who-may-call-what) and [ADR 0013](./adr/0013-per-folder-access-levels.md)). A folder the caller may not browse is not there for them: `GET /api/v1/sources` leaves it out and every other request that names it (`source_id`, a job, a recovery point) answers `404` with the same body as for an id that does not exist. A folder the caller can see but not use in the way asked answers `403` `forbidden` (and the attempt is audited with the folder).
- **CSRF.** Every `POST`, `PATCH` and other state-changing request of a signed-in account needs the session's token in the `X-CSRF-Token` header (HTML forms use the `csrf_token` field). Read it from `GET /api/v1/session`. A request whose `Origin` or `Sec-Fetch-Site` shows another site is rejected with `403`.
- **JSON.** Request bodies are JSON with `Content-Type: application/json`; unknown fields are rejected with `400`. Times are RFC 3339. Sizes are bytes.
- **Errors.** `{"error": {"code": "...", "message": "..."}}` with these statuses: `400` invalid input (bad path, bad destination, unknown field, a schedule outside 1 to 43200), `401` not signed in, `403` CSRF (`csrf`) or not allowed (`forbidden`), `404` not found, `409` conflict (duplicate monitored folder, a backup of the folder is running (`source_busy`), the folder is switched off (`source_disabled`), stale preview, old versions of the folder are being deleted, so a restore, a verification or a change of the version limit is refused (`prune_running`), lowering the version limit would delete versions and `confirm_prune` was not sent (`prune_not_confirmed`), the new lists of a folder would take away the caller's own `full` and `confirm_lockout` was not sent (`lockout_not_confirmed`), the lists that were sent were made from grants that somebody else has changed since (`access_changed`)), `422` confirmation missing or items blocked, `503` search index unavailable, folder unreadable or health failure, `500` internal error (the message carries only a reference id; details are in the server log, under the same `id`, and the web log has the reference as `ref`).
- **Paths.** Source-relative, using `/` or `\`; leading and trailing separators are ignored; `""` is the source root. `..`, drive letters, reserved device names and invalid characters are rejected with `400`.
- **Paging, sorting and filtering.** `files` and `search` use `offset`/`limit` and return `next_offset` while more results exist. `files` and `history/tree` also take `sort` (`name`, `type`, `size` or `mtime`; default `name`), `order` (`asc` or `desc`), `type` (a filter: `dir`, `file` for everything that is not a folder, `link`, `noext`, or `ext:<extension>` in lower case) and `dirs_first=true` (folders before everything else; the pages always do this, the API only when asked). A value that is not understood means the default: by name, no filter. `history/tree` keeps its opaque `cursor` and `next_cursor` as long as none of `sort`, `order`, `type`, `dirs_first` and `offset` is given; with one of them it takes `offset`/`limit` like `files`. These list answers have `total` (the items that match the filter), `unfiltered` (the items of the folder) and `types[]` (`type` and `count` of every kind of item in the folder, whatever the filter), and every entry has a `type`: `dir`, `link` (a junction or symbolic link), `noext` (a file without an extension) or `ext:<extension>`. `audit` uses `before` (an event id) and `limit`.
- **Several servers.** When this server is in a group (see [runbook.md](./runbook.md#several-servers-on-one-database)), the endpoints that read the history take the `server` parameter, the name of another server of the group, and read that server's folders from its schema in the database: `GET /api/v1/sources`, `/recovery-points`, `/history/tree`, `/history/versions`, `/jobs/{id}` and `/audit`. Without it, or with the name of this server, they are about this server and answer as they always did; with another server's name the answer carries `"server": "<name>"`. A folder is addressed by its server and its number there: the same number can be a folder of each server. A caller's level on a folder of another server comes from the grants stored in that server's schema (an `admin` account has full reach there; the local administrator may only browse). A server that is not in the register is `404` (also on a server that is not in a group), one that has not reported yet or reports another read contract is `503` `server_not_readable`, and one whose schema cannot be read is `503` `server_unreachable`. For a folder of another server `GET /api/v1/history/versions` says `content_checked: false`, and `object_present` then only means that the catalog records the content. The live view, the search and everything that changes something (`GET /api/v1/files`, `/search`, `POST /api/v1/backups`, `/restores/preview`, `/restores`, `POST /api/v1/sources`, `PATCH /api/v1/sources/{id}`) are for this server only: a request that names another server in `server` is answered `501` `other_server`.

## Who may call what

| Caller | May |
|---|---|
| Anyone | `GET /healthz`, `GET /help` (the user guide), `GET /api/v1/session`, and, for the monitored folders that give guests Browse, `GET /api/v1/sources`, `/files`, `/search`, `/recovery-points`, `/history/tree`, `/history/versions`, and `GET /api/v1/jobs/{id}` of a backup or verify job. Also `POST /auth/sso/start` and `POST /auth/sso/poll`, which exist to sign in (only when single sign-on is configured, and only from the site itself). |
| Any signed-in account | Everything above, for every folder it has a level on (what guests get, what everybody who is signed in gets and what the account itself is given: the highest of them), with more detail (see below); `GET /api/v1/jobs/{id}` of a restore job; `GET /api/v1/audit` (the events of the folders it may browse and the events that belong to no folder); `GET /api/v1/health`; `GET /api/v1/settings`. And, by the level on the folder: `POST /api/v1/restores/preview` and `POST /api/v1/restores` (Browse), `POST /api/v1/backups` (Back up), `PATCH /api/v1/sources/{id}` without `root_path` (Full). |
| `admin` account (or the local administrator) | Everything above on every folder, whether it is listed or not, and `POST /api/v1/sources`, `root_path` in `PATCH /api/v1/sources/{id}`, and `POST /api/v1/update/check`. |
| The local administrator | Everything an `admin` account may do, and the Site settings: `GET /api/v1/site-settings`, `PATCH /api/v1/site-settings`, `POST /api/v1/site-settings/restart`, and the whole answer of `GET /api/v1/settings`. Everybody else who is signed in is told that these endpoints do not exist (`404` `not_found`, and the attempt is audited as an access denied). |

| Level | What it allows |
|---|---|
| `browse` | Reading the folder: files, history, versions, search, recovery points, the state of its jobs, the audit events about it; restoring from it (preview and start; the caller must be signed in). |
| `backup` | Also `POST /api/v1/backups` (also with `rehash`) and the equivalent page actions: back up now, verify a recovery point, stop a job of the folder. |
| `full` | Also `PATCH /api/v1/sources/{id}`: the name, display path, excludes, enabled, schedule, version limit and `access` of the folder; not `root_path`. |

A level is the highest that any of these gives the caller: Full for administrators; what the **guest** grant gives (anybody; only `browse`); what the **everyone** grant gives (any signed-in account); what the account's own employee ID is given. A signed-in account therefore never has less than a guest. Whoever started a restore job may also stop it (page action) when they only have `browse`.

What a visitor without an account does not get: in `GET /api/v1/jobs/{id}` the `requested_by`, the `error` text and the `events` (the log). A restore job is `401` for a visitor.

What only administrators get is the folders of the server's disk: `root_path` in `GET /api/v1/sources`, `repository`, `restore_root` and `env_file` in `GET /api/v1/settings`, and `destination_real` in a restore preview. The address of the release and the last error of the automatic update (`update.manifest` and `update.error` in `GET /api/v1/settings`) are for administrators too, because they may quote a share or a folder of the server. Everybody gets the display folders instead (`display_path`, `destination`, `restore_display_root`). In the answers to anybody else, the real folders in texts (job errors and logs, restore messages and problems, audit details, health details, the reasons a file was not captured) are replaced as described in [ADR 0007](./adr/0007-display-folders-and-hiding-server-paths.md): by the display folder, by `[<name of the monitored folder>]`, `[backup folder]` or `[restore folder]`.

What only the local administrator gets is the rest of `GET /api/v1/settings` (`listen`, `database`, `user_directory`, `sso_host`, `base_path`, `search_index`, `local_admin`, `sign_in_disabled`, `session_ttl`, `cookie_secure` and `web_log`) and the events about the Site settings in `GET /api/v1/audit`.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| GET | `/healthz` | Liveness probe, no authentication, returns `ok`. |
| GET | `/api/v1/session` | `{"authenticated": false}` for a visitor; for an account `authenticated`, `user` (employee ID), `name`, `role` (`user` or `admin`), `csrf_token`, `auth_disabled`. |
| GET | `/api/v1/servers` | The servers of the group, open to everybody (what is counted is what the caller may browse): `group` (false on a server that is not in a group, with an empty `servers`), `this_server` (the name of this server) and `servers[]`, this server first, each with `name`, `this_server`, `state` (`online`, `offline`, `waiting` or `incompatible`), `version`, `folders` (how many of its folders the caller may browse; null when they could not be counted), `latest_recovery_point_at` and `last_seen`; administrators also get `schema`, `contract`, `repository_id`, `repository_root` and `restore_root`. |
| GET | `/api/v1/health` | Accounts only. `ok`, `components[]` (`database`, `repository`, `search`, `directory`, `restore`, `vss`, `jobs`) each with `state` (`ok`, `degraded`, `disabled`, `failed`) and `detail`; HTTP `503` when a component is `failed`. The user directory is `degraded` when Redis does not answer, which is not a failure. The `search` component is `degraded` while the NTFS index of a volume is being built or cannot read it (no administrator rights, no change journal, not NTFS), `disabled` when the Site setting `search_index` is `off`, and `ok` otherwise; its `detail` says why, or how many entries are held (see [runbook.md](./runbook.md#search-index)). For accounts that are not administrators the `detail` of the repository is only how full it is, and real folders are replaced in the other details. |
| GET | `/api/v1/settings` | Accounts only. The running configuration without secrets. Every account gets `version`, `server_host`, `restore_display_root` and `update`, the automatic update (below). The local administrator also gets `listen`, `database` and `user_directory` (`host:port/name`), `sso_host` (the single sign-on service, empty when it is off), `base_path` (the path prefix, empty when there is none), `search_index` (`auto` or `off`), `local_admin` (boolean), `sign_in_disabled`, `session_ttl`, `cookie_secure` and `web_log` (the web log: `{"enabled", "key", "host"}`; `enabled` is `false` when it is off, and `key` and `host` are the settings in force). `update` is `{"enabled": false}` when the Site setting `update_url` is not set, otherwise `enabled`, `state` (`idle`, `checking`, `downloading`, `waiting`, `applying` or `error`), `latest_version` (what the manifest said at the last look; empty before the first), `check_interval`, `waiting_jobs` (how many jobs a `waiting` update waits for), `checked_at` (when the manifest was last read, when it has been). Administrators also get `repository`, `restore_root` and `env_file`, and in `update` `manifest` (the address of the release) and `error` (the last problem, when there is one): both may quote a share or a folder of the server. |
| POST | `/api/v1/update/check` | Administrators only. Asks the updater to look at the release now, without waiting for the interval, and answers at once with `202` `{"requested": true}`; what it finds shows in `update` of `GET /api/v1/settings` a moment later. `409` `updates_off` when `update_url` is not set. Needs the CSRF token like every other `POST`. |
| GET | `/api/v1/site-settings` | The local administrator only (`404` `not_found` for everybody else). `settings[]`, one for each Site setting in the order of the page: `key`, `group` (`address`, `signin`, `performance`, `scheduler`, `search`, `updates` or `logging`), `kind` (`text`, `number`, `bool` or `choice`), `value` (the value in effect), `default`, `stored` (true when a value is stored for it) and, for a `choice`, `choices[]`; and `restart_required` (true while what is stored differs from what the running service started with) and `can_restart`. |
| PATCH | `/api/v1/site-settings` | The local administrator only. `{"settings": {"job_workers": "3", "log_level": null}}`: each value is a string, as it would be typed; `null`, an empty string or the default sets the setting back to its default, and a setting that is not named stays as it is. The values are checked together with the settings of `.env` that they depend on: `400` `unknown_setting` for a key that is not a Site setting, `400` `invalid_setting` (the message says what is wrong, never a value) for a value that is not valid, `400` `invalid_request` for an empty `settings`. `200` with `changed[]` and `reset[]` (the keys) and `restart_required`. Nothing changes in the running service until it restarts. The change is audited as `site.update`, with the key names only. |
| POST | `/api/v1/site-settings/restart` | The local administrator only. Asks the service to stop and start again with the Site settings that are stored, and answers `202` `{"restarting": true}` at once. `409` `jobs_running` while a job runs, and `409` `restart_unavailable` when the service cannot restart itself. Audited as `site.restart`. |
| GET | `/api/v1/sources` | The monitored folders the caller may browse, with their newest committed recovery point: `id`, `name`, `display_path` (when there is one), `root_path` (administrators only), `excludes`, `enabled`, `schedule_minutes` (`null` = manual only), `last_run_at`, `last_run_ms` (how long the last backup run took, when known), `max_versions` (the most versions kept of one file; `null` = every version is kept), `created_at`, `latest_point`, `level` (what the caller may do with the folder: `browse`, `backup` or `full`) and, for callers that have `full`, `access` (who may do what: `{"browse": [...], "backup": [...], "full": [...]}`, whose entries are `"guest"`, `"everyone"` and upper-case employee IDs; an ID that is spelled like a group is written `user:<ID>`) and `access_rev` (a digest of those lists, to send back with `access` in `PATCH`). |
| POST | `/api/v1/sources` | Administrators only. Add a monitored folder: `{"name", "display_path", "root_path", "excludes": [], "schedule_minutes": null, "max_versions": null, "access": {...}}` (default excludes when omitted; `schedule_minutes` is 1 to 43200 or omitted; `max_versions` is 1 to 10000, and `0`, `null` or omitted keeps every version; `400` for any other value). `access` says who may do what with the folder, in the form of the `access` of `GET /api/v1/sources`; omitted or empty, nobody but administrators sees the folder. It is refused with `400` when guests are given more than `browse`, when `guest` or `everyone` is combined with employee IDs or with each other in one list, when an employee ID is not valid or not an active account of the user directory, or when more than 500 accounts are named; a person that is in several lists gets the highest level. `201`. The folder must be a local, existing directory that does not overlap the repository, the restore folder or another monitored folder. `display_path` is the network path people open the folder with (`\\server\share\folder`, either slash, no hidden share ending in `$`). It is required, and its host must be the Site setting `server_host` (case does not matter, it is stored as the setting spells it), when that setting is set; otherwise it is optional. `400` when it is not a network path or is on another host. |
| PATCH | `/api/v1/sources/{id}` | Callers that have `full` on the folder (administrators have it on every folder). Change the fields that are present and leave the others: `name`, `display_path` (an empty string removes it, which `server_host` forbids), `root_path` (administrators only: from anybody else `403`, whatever the value), `excludes`, `enabled`, `schedule_minutes` (a number, or `null` to remove the schedule), `max_versions` (1 to 10000, or `0` or `null` to keep every version), `access` (replaces all of the lists, with the rules of `POST`; an employee ID that is already in the lists stays even when it is not an active account now; a person can be written as the employee ID or as `user:<employee ID>`, which an ID that is spelled `guest` or `everyone` needs), `confirm_prune` and `confirm_lockout` (`true` says that taking away the caller's own `full` is meant: without it, a caller who is not an administrator and whose new lists no longer give them `full` gets `409` `lockout_not_confirmed` and nothing is changed). `access_rev` (the `access_rev` of the folder that the lists of `access` were made from) is checked with `access`: when the lists of the folder have been changed by somebody else since, the request is refused with `409` `access_changed` and nothing is changed; without `access_rev` the lists are replaced as they are, and `access_rev` without `access` is not looked at. `200` with the source. `403` when the caller can see the folder but has less than `full`, `404` when they cannot see it, `400` for an invalid value, `409` when a backup of the folder is running (`source_busy`) or the name or folder is taken. The folder of a source that has any recovery point cannot be changed (`400`). A change of folder forgets the last run. While `server_host` is set, a source that has no display folder cannot be changed (`400`) until the request gives it one. A `max_versions` that is set, or set lower than before, on a source that has history queues a version cleanup job for the whole folder (see [ADR 0010](./adr/0010-version-limit-and-garbage-collection.md)). When that would delete versions, the request is refused with `409` `prune_not_confirmed` (the message says how many versions of how many files) unless it carries `"confirm_prune": true`. While a cleanup of the folder runs, a request that changes `max_versions` is refused with `409` `prune_running`; the other fields can still be changed. |
| GET | `/api/v1/files` | Current folder: `source_id`, `path`, `sort`, `order`, `type`, `dirs_first`, `offset`, `limit` (≤ 1000, default 200). Returns `entries[]` (`name`, `path`, `is_dir`, `type`, `size`, `modified_at`, `status` = `protected` / `changed` / `new` / `not_captured`), `total`, `unfiltered`, `types[]`, `next_offset`, `deleted[]` (items present in the newest recovery point but gone from disk, following the type filter), `latest_point`. The `size` of a folder is the size of everything inside it according to the NTFS index (see [runbook.md](./runbook.md#search-index)), or `0` when the index cannot say; sorting by `size` uses it. |
| GET | `/api/v1/search` | `q`, `source_id`, `offset`, `limit` (≤ 200). Returns `results[]` (with a `type`), `total`, `next_offset`. `503` with code `search_unavailable` when the index is off, not ready (it is being built) or cannot read the volume of the folder, or when the folder is not on a local NTFS drive letter. A name matches when it contains every term of `q`, ignoring case; the results come folders first, then by name, and every one is below the folder. |
| GET | `/api/v1/recovery-points` | Committed points of `source_id`, newest first (`limit`, `before_seq`). Each has `seq`, `kind` (`full` / `incremental`), `consistency` (`live_scan`), counters, `verification`, `restorable`, `partial` (true when older versions of some files were deleted to stay within the folder's version limit, so the point no longer shows every file as it was), `manifest_sha256`. |
| GET | `/api/v1/history/tree` | A folder as it was at `point_id`: `source_id`, `point_id`, `path`, and either `cursor`/`limit` or the list parameters of `files`. Each entry has a `type` and a `status` relative to the newest point: `same`, `modified`, `deleted`. |
| GET | `/api/v1/history/versions` | Every version of `path`: `type`, `captured_at`, `until`, `current`, `size`, `sha256`, `state`, `first_point_id`, `object_present`. |
| POST | `/api/v1/backups` | Accounts that have `backup` on the source (`403` with less, `404` when they cannot see it). `{"source_id", "rehash": false}`. `202` with `{job, already_active}`; if a backup of that source is already queued or running (it may be an automatic one) the existing job is returned with `200` and `already_active: true`. `409` (`source_disabled`) when the folder is switched off. |
| GET | `/api/v1/jobs/{id}` | `{job, events[]}`; `after_event` returns only newer log lines. `job.active` is true while queued or running; `job.progress` is a JSON object whose fields depend on the kind. A visitor gets no `requested_by`, no `error` and no events; a restore job needs an account. A job of a folder the caller may not browse answers `404`. An automatic backup that finds nothing changed leaves no job, so its id answers `404`. |
| POST | `/api/v1/restores/preview` | Accounts that may browse the source. `{"source_id", "point_id", "paths": [], "dest_name", "policy": "skip"|"rename"|"overwrite", "allow_partial": false}` (at most 500 paths; a `point_id` that is not a recovery point of that folder is `404`, as one that does not exist). Writes nothing. Returns `destination` (the display path of the destination folder, or `[restore folder]\<dest_name>` when the restore folder has no display root; administrators also get `destination_real`), `totals` (`create`, `overwrite`, `rename`, `skip_same`, `skip_exists`, `blocked`, `missing_objects`, `not_captured`, …), `sample[]`, `problems[]`, `digest` and `confirmation_token`. |
| POST | `/api/v1/restores` | Accounts that may browse the source. The preview body plus `confirmation_token`, `idempotency_key` and `confirm_overwrite`. `202` with `{job}`. `422` when the token is missing or invalid, when files would be replaced without `confirm_overwrite`, or when items are blocked without `allow_partial`; `409` when the preview is stale, or (`prune_running`) while old versions of the folder are being deleted. Repeating a request with the same `idempotency_key` returns the original job when it is the caller's own restore of the same folder; a key that was used by another account or for another folder is a `409`. |
| GET | `/api/v1/audit` | Accounts only. Audit events newest first: `action`, `actor`, `before`, `limit`. Administrators get all events; everybody else the events of the folders they may browse and the events that belong to no folder (no `source_id`: sign-ins and the like). Each event has `duration_ms` when the audited operation has a duration (backups, verifications, restores and the deletion of old versions; not sign-ins or requests). The `backup.finish` detail has `bytes`, `new_bytes` and `new_objects`, the action `retention.prune` is the deletion of old versions, and the `source.create` and `source.update` details list the access lists as `access` (the whole list when the folder was added, old and new when it changed), which only those who have `full` on the folder read: for everybody else its value is `"[hidden]"`. The events about the Site settings (`site.update` and `site.restart`, target type `site`, with the names of the settings that changed and never their values) are only in the answer for the local administrator. |

## Page routes

| Route | Page |
|---|---|
| `GET /login`, `POST /login`, `POST /logout` | Sign-in and sign-out. Anyone may open the sign-in page; signing out needs a session. |
| `POST /auth/sso/start`, `POST /auth/sso/poll` | Single sign-on, only when the Site setting `sso_host` is set (otherwise `404`) and only from the site itself (`403` otherwise). `start` takes the form field `next` (a local path) and answers `{"token", "url", "expires_in"}`: `url` is the page of the company sign-on service to open in a window. `poll` takes the form field `token` and answers `200` with `{"status": ...}`: `pending` (ask again; at most once a second), `ok` (with `next`, the page to go to, with the base path when there is one; the session cookie is set), `expired`, `mismatch` (the address that the sign-on service saw is not the browser's), `no_user` (Windows gave no user), `denied` (no active account), `unavailable` (Redis does not answer). A token works once. `429` `busy` when too many sign-ins are waiting (5 per address, 2000 in all). See [ADR 0009](./adr/0009-single-sign-on-and-trusted-proxies.md). |
| `GET /lang?set=en\|zh&next=…` | Sets the language cookie and redirects to a local path. |
| `GET /help` | The user guide: what TimeVault is for and how each page is used, in English and Chinese (the language of the EN / 中文 switch). A page of the application that is open to everybody (its content is the same for everyone), with the header and the round buttons of every page; a request with `X-TV-Partial: 1` gets the content only. The **Documentation** button of every page opens it in a new tab. The template is `web/templates/help.html`. |
| `GET /explorer?source=&path=&q=&sort=&order=&type=&page=&per_page=` | Current files, deleted items, and search results, as pages of 100 by default (`per_page` 50, 100, 200 or 500, 50, 100 or 200 for search results). A page past the end answers `303` to the last page. Open to everyone, for the folders that give guests Browse (an account also sees the folders it was given). |
| `GET /history?source=&point=&path=&sort=&order=&type=&page=&per_page=` | Time Machine: timeline of recovery points and the folder at the selected point, in pages like the Explorer. Open to everyone for the folders they may browse; the restore form needs an account. |
| `GET /versions?source=&path=` | Versions of one file or folder. Open to everyone for the folders they may browse. |
| `GET /servers` | The Servers page: the servers of a group, how they look and how many of their folders the visitor may browse (`404` on a server that is not in a group). Open to everybody. |
| `GET /backups`, `POST /backups/run`, `POST /backups/verify` | Monitored folders, recovery points, jobs, schedules; start a backup (also with `rehash`), start an integrity check (accounts that have Back up on the folder). Viewing is open to everyone, for the folders they may browse; visitors do not see restore jobs, who asked for a job or why one failed. Nobody but administrators sees the folders of the server's disk, only display folders. |
| `GET /jobs/{id}`, `POST /jobs/{id}/cancel` | A job, its log and (for restores) the per-item results. Viewing a backup job is open to everyone who may browse its folder, without the requester, the error and the log (a job of another folder is `404`); a restore job needs an account; cancelling needs Back up on the folder, or having started the restore. |
| `POST /restore/preview`, `POST /restore/start` | Restore preview and confirmation (accounts that may browse the folder). |
| `GET /audit`, `GET /status`, `GET /settings` | Audit log (the events of the folders the account may browse, and the events that belong to no folder), component status, and the settings page (accounts). Administrators see the real folders on them, everybody else the display folders. The settings page lists the folders the account may browse with its level on each; `GET /settings?edit=<id>` opens the form of a folder it has Full on (with the editor of who may do what, which lists every account of the user directory and so is not part of the plain page) and administrators get the form that adds a folder with `GET /settings?add=1`. |
| `POST /settings/sources`, `POST /settings/sources/{id}` | Add a monitored folder (administrators) and edit one (administrators, and accounts that have Full on it); the form has the fields `name`, `display_path`, `root_path` (administrators only: from anybody else the form is refused), `excludes`, `enabled`, `schedule`, `schedule_minutes`, `max_versions`, (when lowering a limit would delete versions) `confirm_prune`, (when the lists would take away the editor's own Full) `confirm_lockout`, and the editor of who may do what: `access_set` (always `1`, because a list in which nobody is ticked posts no field), `access_rev` (the digest of the lists the form was made from; the form is refused with `409` when it changes the lists and they have been changed since, and a form that did not change them leaves them alone) and the lists `access_browse`, `access_backup` and `access_full`, whose values are `guest`, `everyone` and `user:<employee ID>`. A form without `access_set` leaves the access of the folder as it is (a new folder then has none). |
| `POST /settings/update/check` | Administrators only (the **Check now** button of the **Program updates** card): asks the updater to look at the release now and redirects to `/settings#updates` with a message (a message that updates are not turned on when `update_url` is not set). The same as `POST /api/v1/update/check`. |
| `GET /settings/site`, `POST /settings/site`, `POST /settings/site/restart` | The Site settings page, its form and its **Restart now** button: the local administrator only (any other signed-in account gets the `404` page, a visitor who is not signed in the sign-in page). The form has one field `s_<key>` for each Site setting that it carries (an empty value means the default; a setting without a field is left as it is); a form with a problem is answered with `400` and shown again as it was typed. A change and a restart are audited like those of the API. |

`/history`, `/versions`, `/backups`, `/jobs/{id}` and `/audit` take `server=<name>` for the folders of another server of the group (and `/history` also `source=<server>:<number>`, which is what its folder selector sends); `/explorer` and every `POST` route answer `501` to a request that names another server.

A request that carries the header `X-TV-Partial: 1` receives only the page content, which the UI script swaps in without a full reload; links remain ordinary deep-linkable URLs. The answer to such a request carries `X-TV-Title`, `X-TV-Nav` and `X-TV-Notice` (the sentence that is shown under the header while the service waits to restart for a new version, URL-encoded, and empty when there is none; only signed-in accounts get it), so that the script keeps the title, the navigation and the notice right without a reload. The script adds `X-TV-Auto: 1` to the request when it reloads a page by itself because a job that the page shows is running or has finished (the job page and the Backups page); the answer is the same, and only the web log treats such a request differently (it is not a page that somebody opened; see [runbook.md](./runbook.md#web-log)).

## Example (PowerShell)

```powershell
$base = 'http://127.0.0.1:8660'
$session = $null
try { Invoke-WebRequest "$base/login" -Method Post -UseBasicParsing -MaximumRedirection 0 -SessionVariable session `
        -Body @{ username = 'admin'; password = $password; next = '/' } } catch { }   # a 303 is expected
$csrf = (Invoke-RestMethod "$base/api/v1/session" -WebSession $session).csrf_token
Invoke-RestMethod "$base/api/v1/backups" -Method Post -WebSession $session `
    -Headers @{ 'X-CSRF-Token' = $csrf } -ContentType 'application/json' -Body '{"source_id": 1}'
```

`scripts/dev-demo.ps1` is a complete working example (it signs in as the local administrator). A company account signs in the same way with its employee ID, name or e-mail address as `username`.

## Differences from plan.md

- Folders and files are addressed by **source-relative `path`**, not by `parent_id` / `node_id`, so every URL stays deep-linkable and no internal id leaks.
- `GET /api/v1/session`, `GET /api/v1/settings`, `POST /api/v1/sources` and `PATCH /api/v1/sources/{id}` were added so the API can be scripted. `GET /api/v1/site-settings`, `PATCH /api/v1/site-settings` and `POST /api/v1/site-settings/restart` came with the Site settings page (1.0.1); plan.md does not describe them.
- Reading is open to everyone for the folders that give guests Browse, and changes need an account, with two roles (`user`, `admin`) and a level (`browse`, `backup`, `full`) on each monitored folder; plan.md describes a richer role model that is not implemented.
- `GET /api/v1/files` reads the live folder and `history/tree` the folder of a recovery point; both can be sorted, filtered by type and paged with `offset`/`limit` (`history/tree` also still pages with a `cursor`).
- Restore requests name a destination **folder below the configured restore root** instead of a free path.
- Job progress is polled (`/api/v1/jobs/{id}`); server-sent events are not implemented.

# 中文

## 概述

TimeVault（1.1.0 版）在 `/api/v1` 下提供 JSON API，同时提供服务端渲染的页面。两者由同一个服务层实现，行为一致。本文档描述当前已有的内容；与 plan.md §6 中示意性 API 的差异见[与 plan.md 的差异](#与-planmd-的差异)。

## 约定

- **认证。** 读取对所有人开放；任何会改变内容的操作，以及任何展示服务内部情况的内容，都需要账号（见[谁可以调用什么](#谁可以调用什么)）。通过 `POST /login` 登录（表单字段 `username`、`password`，可选 `next`）。`username` 是 Redis 用户目录中公司账号的工号、姓名或邮箱，或者是本地管理员的名字。响应会设置 `tv_session` Cookie（HttpOnly、SameSite=Lax；当站点设置 `cookie_secure` 为 `true` 时带 Secure）。受保护的接口在没有有效会话时返回带 JSON 错误的 `401`，在账号无权执行时返回 `403`。登录本身对错误或未知的账号返回 `401`（无论原因，文本都相同），尝试次数过多时返回 `429` 和 `Retry-After`，无法连接用户目录时返回 `503`。**单点登录**（设置了站点设置 `sso_host` 时）是另一种登录方式：登录页调用 `POST /auth/sso/start`，然后调用 `POST /auth/sso/poll`（见[页面路由](#页面路由)）。
- **基础路径。** 把站点设置 `base_path` 设为 `/tv`（见 [runbook.md](./runbook.md#放在带路径前缀的反向代理之后)）后，本文档中的每个路径，在浏览器看来都在 `/tv` 之下（`/tv/api/v1/sources`、`/tv/login`）。服务也接受不带前缀的请求，供去掉前缀的代理使用。API 的 `Location` 头和 `POST /auth/sso/poll` 的 `next` 都带有前缀，Cookie 也限制在该前缀之内。不设置时，每个路径都和这里写的一样。
- **文件夹访问。** 调用者能对某个监控文件夹做什么，取决于他在该文件夹上的**级别**：`browse`、`backup` 或 `full`（见[谁可以调用什么](#谁可以调用什么)和 [ADR 0013](./adr/0013-per-folder-access-levels.md)）。调用者不能浏览的文件夹对他们来说不存在：`GET /api/v1/sources` 不会列出它，其他任何提到它的请求（`source_id`、任务、恢复点）都返回 `404`，响应体与不存在的 id 完全相同。调用者能看到、但不能按所请求的方式使用的文件夹返回 `403` `forbidden`（该尝试会连同文件夹一起记入审计）。
- **CSRF。** 已登录账号的所有 `POST`、`PATCH` 以及其他会改变状态的请求，都需要在 `X-CSRF-Token` 请求头中携带会话的令牌（HTML 表单使用 `csrf_token` 字段）。可从 `GET /api/v1/session` 获取。如果 `Origin` 或 `Sec-Fetch-Site` 显示请求来自其他站点，则返回 `403`。
- **JSON。** 请求体为 `Content-Type: application/json` 的 JSON；未知字段会返回 `400`。时间为 RFC 3339 格式，大小单位为字节。
- **错误。** `{"error": {"code": "...", "message": "..."}}`，状态码含义：`400` 输入无效（路径错误、目标错误、未知字段、1 到 43200 之外的计划），`401` 未登录，`403` CSRF（`csrf`）或无权执行（`forbidden`），`404` 未找到，`409` 冲突（监控文件夹重复、该文件夹的备份正在运行（`source_busy`）、文件夹已停用（`source_disabled`）、预览已过期、正在删除该文件夹的旧版本因而拒绝恢复、校验或更改版本数上限（`prune_running`）、调低版本数上限会删除版本而请求没有带上 `confirm_prune`（`prune_not_confirmed`）、文件夹的新列表会取消调用者自己的 `full` 而请求没有带上 `confirm_lockout`（`lockout_not_confirmed`）、发来的列表是依据此后已被别人修改的授权做出的（`access_changed`）），`422` 缺少确认或存在被阻止的项目，`503` 搜索索引不可用、文件夹无法读取或健康检查失败，`500` 内部错误（消息只包含参考编号，细节在服务端日志中同一个 `id` 之下，Web 日志中则以 `ref` 记录这个参考编号）。
- **路径。** 相对于备份源，使用 `/` 或 `\`；忽略开头和结尾的分隔符；`""` 表示备份源根目录。`..`、盘符、保留设备名和非法字符会返回 `400`。
- **分页、排序和筛选。** `files` 和 `search` 使用 `offset`/`limit`，还有更多结果时返回 `next_offset`。`files` 和 `history/tree` 还接受 `sort`（`name`、`type`、`size` 或 `mtime`；默认 `name`）、`order`（`asc` 或 `desc`）、`type`（筛选：`dir`；`file` 表示所有不是文件夹的项目；`link`；`noext`；或小写的 `ext:<扩展名>`）和 `dirs_first=true`（文件夹排在其他所有项目之前；页面总是这样做，API 只有在要求时才这样）。无法识别的值表示默认：按名称排序，不筛选。只要没有给出 `sort`、`order`、`type`、`dirs_first` 和 `offset` 中的任何一个，`history/tree` 就保持它不透明的 `cursor` 和 `next_cursor`；给出其中任何一个时，它像 `files` 一样使用 `offset`/`limit`。这些列表的响应包含 `total`（符合筛选条件的项目数）、`unfiltered`（文件夹中的项目数）和 `types[]`（文件夹中每种项目的 `type` 和 `count`，与筛选无关），并且每个条目都有 `type`：`dir`、`link`（联接点或符号链接）、`noext`（没有扩展名的文件）或 `ext:<扩展名>`。`audit` 使用 `before`（事件 id）和 `limit`。
- **多台服务器。** 当这台服务器在一个组里时（见 [runbook.md](./runbook.md#几台服务器共用一个数据库)），读取历史的接口接受 `server` 参数，即组内另一台服务器的名称，并在数据库里从那台服务器的 schema 读取它的文件夹：`GET /api/v1/sources`、`/recovery-points`、`/history/tree`、`/history/versions`、`/jobs/{id}` 和 `/audit`。不带它，或者带的是本服务器的名称，就是关于本服务器的，应答和以前一样；带另一台服务器的名称时，应答里有 `"server": "<名称>"`。文件夹用它所在的服务器和它在那里的编号来指定：同一个编号可以是每台服务器上各自的文件夹。调用者在另一台服务器文件夹上的级别，来自保存在那台服务器 schema 里的授权（`admin` 账号在那里有完全的权限；本地管理员只能浏览）。不在登记表里的服务器是 `404`（不在组里的服务器也是），尚未报告或报告了另一个读取契约的服务器是 `503` `server_not_readable`，读不了其 schema 的服务器是 `503` `server_unreachable`。对于另一台服务器的文件夹，`GET /api/v1/history/versions` 会说 `content_checked: false`，这时 `object_present` 只表示目录库记录了这份内容。实时视图、搜索以及一切会改变东西的接口（`GET /api/v1/files`、`/search`、`POST /api/v1/backups`、`/restores/preview`、`/restores`、`POST /api/v1/sources`、`PATCH /api/v1/sources/{id}`）只用于本服务器：在 `server` 里指明另一台服务器的请求，会得到 `501` `other_server`。

## 谁可以调用什么

| 调用者 | 可以 |
|---|---|
| 任何人 | `GET /healthz`、`GET /help`（用户手册）、`GET /api/v1/session`，以及对允许访客"浏览"的监控文件夹：`GET /api/v1/sources`、`/files`、`/search`、`/recovery-points`、`/history/tree`、`/history/versions`，以及备份或校验任务的 `GET /api/v1/jobs/{id}`。还有 `POST /auth/sso/start` 和 `POST /auth/sso/poll`，它们的用途就是登录（仅在配置了单点登录时，并且只接受来自站点本身的请求）。 |
| 任何已登录的账号 | 上述全部，范围是它在其上拥有级别的每个文件夹（访客所得的权限、所有已登录的人所得的权限，以及账号本人被授予的权限：取其中最高的），内容更详细（见下文）；恢复任务的 `GET /api/v1/jobs/{id}`；`GET /api/v1/audit`（它可以浏览的文件夹的事件，以及不属于任何文件夹的事件）；`GET /api/v1/health`；`GET /api/v1/settings`。并且按它在文件夹上的级别：`POST /api/v1/restores/preview` 和 `POST /api/v1/restores`（浏览）、`POST /api/v1/backups`（备份）、不带 `root_path` 的 `PATCH /api/v1/sources/{id}`（完全）。 |
| `admin` 账号（或本地管理员） | 在每个文件夹上拥有上述全部权限（无论是否被列出），以及 `POST /api/v1/sources`、`PATCH /api/v1/sources/{id}` 中的 `root_path`，和 `POST /api/v1/update/check`。 |
| 本地管理员 | `admin` 账号能做的一切，以及站点设置：`GET /api/v1/site-settings`、`PATCH /api/v1/site-settings`、`POST /api/v1/site-settings/restart`，以及 `GET /api/v1/settings` 的完整应答。其他已登录的人得到的是这些接口不存在（`404` `not_found`，并且这次尝试会作为"访问被拒绝"记入审计）。 |

| 级别 | 允许什么 |
|---|---|
| `browse` | 读取文件夹：文件、历史、版本、搜索、恢复点、它的任务的状态、与它有关的审计事件；从中恢复（预览和启动；调用者必须已登录）。 |
| `backup` | 另外还有 `POST /api/v1/backups`（也可以带 `rehash`）以及对应的页面操作：立即备份、校验恢复点、停止该文件夹的任务。 |
| `full` | 另外还有 `PATCH /api/v1/sources/{id}`：文件夹的名称、显示路径、排除规则、启用状态、计划、版本数上限和 `access`；不包括 `root_path`。 |

级别取以下各项中最高的：管理员得到 Full；**guest** 授权所给的（任何人；只能是 `browse`）；**everyone** 授权所给的（任何已登录账号）；账号本人的工号所获得的。因此已登录的账号永远不会比访客权限更低。启动了恢复任务的人，即使只有 `browse`，也可以停止它（页面操作）。

没有账号的访问者得不到的内容：`GET /api/v1/jobs/{id}` 中的 `requested_by`、`error` 文本和 `events`（日志）。恢复任务对访问者返回 `401`。

只有管理员能得到的是服务器磁盘上的文件夹：`GET /api/v1/sources` 中的 `root_path`，`GET /api/v1/settings` 中的 `repository`、`restore_root` 和 `env_file`，以及恢复预览中的 `destination_real`。自动更新的发布地址和最近的错误（`GET /api/v1/settings` 中的 `update.manifest` 和 `update.error`）也只给管理员，因为它们可能引用服务器的共享或文件夹。所有人得到的则是显示文件夹（`display_path`、`destination`、`restore_display_root`）。给其他人的响应中，文本里的真实文件夹（任务错误和日志、恢复消息和问题、审计详情、健康详情、文件未能备份的原因）会按 [ADR 0007](./adr/0007-display-folders-and-hiding-server-paths.md) 的说明被替换：换成显示文件夹、`[<监控文件夹名称>]`、`[backup folder]` 或 `[restore folder]`。

只有本地管理员能得到的是 `GET /api/v1/settings` 的其余部分（`listen`、`database`、`user_directory`、`sso_host`、`base_path`、`search_index`、`local_admin`、`sign_in_disabled`、`session_ttl`、`cookie_secure` 和 `web_log`），以及 `GET /api/v1/audit` 中关于站点设置的事件。

## 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/healthz` | 存活探针，无需认证，返回 `ok`。 |
| GET | `/api/v1/session` | 访问者得到 `{"authenticated": false}`；账号得到 `authenticated`、`user`（工号）、`name`、`role`（`user` 或 `admin`）、`csrf_token`、`auth_disabled`。 |
| GET | `/api/v1/servers` | 组内的服务器，对所有人开放（统计的是调用者有权浏览的部分）：`group`（不在组里的服务器为 false，此时 `servers` 为空）、`this_server`（本服务器的名称）和 `servers[]`（本服务器排在最前），每项有 `name`、`this_server`、`state`（`online`、`offline`、`waiting` 或 `incompatible`）、`version`、`folders`（调用者有权浏览它的多少个文件夹；无法统计时为 null）、`latest_recovery_point_at` 和 `last_seen`；管理员还会得到 `schema`、`contract`、`repository_id`、`repository_root` 和 `restore_root`。 |
| GET | `/api/v1/health` | 仅限账号。`ok`、`components[]`（`database`、`repository`、`search`、`directory`、`restore`、`vss`、`jobs`），每项含 `state`（`ok`、`degraded`、`disabled`、`failed`）和 `detail`；有组件为 `failed` 时 HTTP 状态为 `503`。Redis 没有应答时用户目录为 `degraded`，这不算故障。`search` 组件在某个卷的 NTFS 索引正在建立、或无法读取该卷（没有管理员权限、没有变更日志、不是 NTFS）时为 `degraded`，站点设置 `search_index` 为 `off` 时为 `disabled`，其他情况为 `ok`；它的 `detail` 说明原因，或保存了多少条目（见 [runbook.md](./runbook.md#搜索索引)）。对不是管理员的账号，仓库的 `detail` 只说明它用了多少，其他详情中的真实文件夹会被替换。 |
| GET | `/api/v1/settings` | 仅限账号。当前运行的配置（不含机密信息）。每个账号得到 `version`、`server_host`、`restore_display_root` 和 `update`，即自动更新（见下）。本地管理员还会得到 `listen`、`database` 和 `user_directory`（`host:port/name`）、`sso_host`（单点登录服务，关闭时为空）、`base_path`（路径前缀，没有时为空）、`search_index`（`auto` 或 `off`）、`local_admin`（布尔值）、`sign_in_disabled`、`session_ttl`、`cookie_secure` 和 `web_log`（Web 日志：`{"enabled", "key", "host"}`；关闭时 `enabled` 为 `false`，`key` 和 `host` 是当前生效的设置）。`update` 在未设置站点设置 `update_url` 时为 `{"enabled": false}`，否则有 `enabled`、`state`（`idle`、`checking`、`downloading`、`waiting`、`applying` 或 `error`）、`latest_version`（最近一次查看时清单所说的版本；第一次查看之前为空）、`check_interval`、`waiting_jobs`（处于 `waiting` 的更新在等待多少个任务）、`checked_at`（清单最近一次被读取的时间，读取过才有）。管理员还会得到 `repository`、`restore_root` 和 `env_file`，以及 `update` 中的 `manifest`（发布地址）和 `error`（最近的问题，有问题时才有）：它们都可能引用服务器的共享或文件夹。 |

## 页面路由

| 路由 | 页面 |
|---|---|
| `GET /login`、`POST /login`、`POST /logout` | 登录与退出。任何人都可以打开登录页；退出需要会话。 |
| `POST /auth/sso/start`、`POST /auth/sso/poll` | 单点登录，仅在设置了站点设置 `sso_host` 时可用（否则返回 `404`），并且只接受来自站点本身的请求（否则返回 `403`）。`start` 接受表单字段 `next`（本站路径），返回 `{"token", "url", "expires_in"}`：`url` 是要在窗口中打开的公司单点登录服务的页面。`poll` 接受表单字段 `token`，返回 `200` 和 `{"status": ...}`：`pending`（再问一次；每秒最多一次）、`ok`（带有 `next`，即要去的页面，设置了基础路径时带有该前缀；会话 Cookie 已设置）、`expired`、`mismatch`（单点登录服务看到的地址不是浏览器的）、`no_user`（Windows 没有给出用户）、`denied`（没有可用的账号）、`unavailable`（Redis 没有响应）。令牌只能使用一次。等待中的登录过多时（每个地址 5 个，总共 2000 个）返回 `429` `busy`。见 [ADR 0009](./adr/0009-single-sign-on-and-trusted-proxies.md)。 |
| `GET /lang?set=en\|zh&next=…` | 设置语言 Cookie，并重定向到本站路径。 |
| `GET /help` | 用户手册：说明 TimeVault 是做什么的，以及每个页面怎么用，有英文和中文两种（取决于 EN / 中文 切换）。应用自己的一个页面，对所有人开放（内容对每个人都一样），带有每个页面都有的页眉和圆形按钮；带有 `X-TV-Partial: 1` 的请求只得到内容。每个页面的**文档**按钮都在新标签页中打开它。模板是 `web/templates/help.html`。 |
| `GET /explorer?source=&path=&q=&sort=&order=&type=&page=&per_page=` | 当前文件、已删除项目和搜索结果，默认每页 100 项（`per_page` 可选 50、100、200 或 500，搜索结果为 50、100 或 200）。超出末尾的页码会返回 `303` 到最后一页。对所有人开放，范围是允许访客"浏览"的文件夹（账号还能看到授予它的文件夹）。 |

| `GET /versions?source=&path=` | 单个文件或文件夹的各个版本。对所有人开放，范围是他们可以浏览的文件夹。 |
| `GET /servers` | 服务器页：一个组里的各服务器、它们的状态，以及访问者有权浏览它们的多少个文件夹（不在组里的服务器上是 `404`）。对所有人开放。 |
| `GET /backups`、`POST /backups/run`、`POST /backups/verify` | 监控文件夹、恢复点、任务、计划；启动备份（也可以带 `rehash`）、启动完整性校验（对该文件夹拥有"备份"的账号）。查看对所有人开放，范围是他们可以浏览的文件夹；访问者看不到恢复任务、任务是谁发起的或为什么失败。除管理员之外，任何人都看不到服务器磁盘上的文件夹，只能看到显示文件夹。 |
| `GET /jobs/{id}`、`POST /jobs/{id}/cancel` | 任务、任务日志，以及（恢复任务的）逐项结果。查看备份任务对所有可以浏览其文件夹的人开放，但看不到发起人、错误和日志（其他文件夹的任务返回 `404`）；恢复任务需要账号；取消操作需要对该文件夹拥有"备份"，或者是发起该恢复的人。 |
| `POST /restore/preview`、`POST /restore/start` | 恢复预览与确认（可以浏览该文件夹的账号）。 |
| `GET /audit`、`GET /status`、`GET /settings` | 审计日志（账号可以浏览的文件夹的事件，以及不属于任何文件夹的事件）、组件状态和设置页（账号）。管理员在这些页面上看到真实文件夹，其他人看到显示文件夹。设置页列出账号可以浏览的文件夹以及它对每个文件夹的级别；`GET /settings?edit=<id>` 打开它拥有"完全"的文件夹的表单（其中有"谁能做什么"的编辑器，它会列出用户目录的所有账号，所以不属于普通页面），管理员用 `GET /settings?add=1` 得到添加文件夹的表单。 |
| `POST /settings/sources`、`POST /settings/sources/{id}` | 添加监控文件夹（管理员），以及编辑监控文件夹（管理员和对它拥有"完全"的账号）；表单字段有 `name`、`display_path`、`root_path`（仅限管理员：其他人提交会被拒绝）、`excludes`、`enabled`、`schedule`、`schedule_minutes`、`max_versions`、（当调低上限会删除版本时的）`confirm_prune`、（当列表会取消编辑者自己的"完全"时的）`confirm_lockout`，以及"谁能做什么"编辑器：`access_set`（始终为 `1`，因为没有勾选任何人的列表不会提交任何字段）、`access_rev`（表单所依据的列表的摘要；表单修改了列表、而列表此后已被别人修改时，表单会被拒绝并返回 `409`；没有修改列表的表单则不会动它们）和列表 `access_browse`、`access_backup`、`access_full`，其值是 `guest`、`everyone` 和 `user:<工号>`。没有 `access_set` 的表单会让文件夹的访问权限保持不变（新文件夹则没有任何权限）。 |
| `POST /settings/update/check` | 仅限管理员（**程序更新**卡片上的**立即检查**按钮）：要求更新器立即查看发布，并重定向到 `/settings#updates` 且带一条消息（未设置 `update_url` 时，消息会说明未启用自动更新）。与 `POST /api/v1/update/check` 相同。 |
| `GET /settings/site`、`POST /settings/site`、`POST /settings/site/restart` | 站点设置页、它的表单和它的**立即重启**按钮：仅限本地管理员（其他已登录的账号得到 `404` 页面，没有登录的访问者被带到登录页）。表单为它所包含的每个站点设置提供一个字段 `s_<key>`（空值表示默认值；没有字段的设置保持不变）；有问题的表单返回 `400`，并按输入的样子重新显示。修改和重启会像 API 的一样记入审计。 |

`/history`、`/versions`、`/backups`、`/jobs/{id}` 和 `/audit` 接受 `server=<名称>`，用于组内另一台服务器的文件夹（`/history` 还接受 `source=<服务器>:<编号>`，这是它的文件夹选择器所发送的）；`/explorer` 和每一个 `POST` 路由，对指明另一台服务器的请求都会返回 `501`。

带有 `X-TV-Partial: 1` 请求头的请求只会得到页面内容，界面脚本会据此无刷新地替换内容；链接仍然是普通的、可直接访问的 URL。这类请求的应答带有 `X-TV-Title`、`X-TV-Nav` 和 `X-TV-Notice`（服务在等待为新版本重启期间显示在页眉下面的那句话，经过 URL 编码，没有时为空；只有已登录的账号会得到它），这样脚本无需刷新就能保持标题、导航和提示正确。当页面所显示的任务正在运行或已结束、脚本自己重新加载页面时（任务页和备份页），脚本会在请求中加上 `X-TV-Auto: 1`；应答是一样的，只有 Web 日志会区别对待这样的请求（它不是有人打开的页面；见 [runbook.md](./runbook.md#web-日志)）。

## 示例（PowerShell）

```powershell
$base = 'http://127.0.0.1:8660'
$session = $null
try { Invoke-WebRequest "$base/login" -Method Post -UseBasicParsing -MaximumRedirection 0 -SessionVariable session `
        -Body @{ username = 'admin'; password = $password; next = '/' } } catch { }   # 预期会收到 303
$csrf = (Invoke-RestMethod "$base/api/v1/session" -WebSession $session).csrf_token
Invoke-RestMethod "$base/api/v1/backups" -Method Post -WebSession $session `
    -Headers @{ 'X-CSRF-Token' = $csrf } -ContentType 'application/json' -Body '{"source_id": 1}'
```

`scripts/dev-demo.ps1` 是一个完整可运行的示例（它以本地管理员身份登录）。公司账号用同样的方式登录，`username` 填工号、姓名或邮箱。

## 与 plan.md 的差异

- 文件夹和文件通过**相对于备份源的 `path`** 寻址，而不是 `parent_id` / `node_id`，这样每个 URL 都可以直接访问，也不会泄露内部 id。
- 新增了 `GET /api/v1/session`、`GET /api/v1/settings`、`POST /api/v1/sources` 和 `PATCH /api/v1/sources/{id}`，使 API 可以脚本化调用。`GET /api/v1/site-settings`、`PATCH /api/v1/site-settings` 和 `POST /api/v1/site-settings/restart` 随站点设置页（1.0.1）一起新增；plan.md 没有描述它们。
- 对允许访客"浏览"的文件夹，读取对所有人开放；修改需要账号，有两种角色（`user`、`admin`），并且在每个监控文件夹上有一个级别（`browse`、`backup`、`full`）；plan.md 描述了更丰富的角色模型，目前没有实现。
- `GET /api/v1/files` 读取实时文件夹，`history/tree` 读取某个恢复点的文件夹；两者都可以排序、按类型筛选，并用 `offset`/`limit` 分页（`history/tree` 仍然可以用 `cursor` 分页）。
- 恢复请求指定的是**所配置恢复根目录之下的目标文件夹**，而不是任意路径。
- 任务进度通过轮询（`/api/v1/jobs/{id}`）获取；未实现 Server-Sent Events。

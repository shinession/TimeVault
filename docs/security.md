# English

## Overview

This document lists the security controls that exist in TimeVault (version 0.1.8) and the gaps that remain. It describes the implementation, not an intention; where plan.md asks for more, the gap is listed.

## Controls that exist

| Area | Control |
|---|---|
| Network exposure | The service listens on `127.0.0.1` by default (port 8660). A non-loopback address is refused unless `TIMEVAULT_ALLOW_NON_LOOPBACK=true`, and sign-in can never be disabled on a non-loopback address. At start the service logs a warning when it listens beyond this computer. TLS is not terminated by the service: put a reverse proxy with HTTPS in front and set `TIMEVAULT_COOKIE_SECURE=true`. |
| Open browsing | Without an account a visitor can only look, and only at the monitored folders that give guests Browse (see "Folder access"): the browsing pages and the read-only JSON API. They never see the audit log, the status and settings pages, restore jobs, who requested a job, why a job failed or its log, or the folders on the server's disk, and no endpoint serves file contents. A test walks every route with and without an account (`internal/server/access_test.go`). |
| Folder access | What an account may do is decided for each monitored folder (Browse, Back up, Full; [ADR 0013](./adr/0013-per-folder-access-levels.md)), granted to guests, to everybody who is signed in or to single employee IDs; administrators have Full everywhere. The check is in the HTTP layer and every handler that reaches a folder goes through one of three functions (`loadSource`, `visibleSources`, `jobSource` in `internal/server/access.go`); `TestHandlersReachFoldersThroughTheAccessChecks` fails when a handler reads folders from the service directly. A folder the visitor may not browse is "not found" everywhere (pages, API, jobs, points, versions, search, restore) with the same answer, status and text as a folder that does not exist, so that hidden folders cannot be found out by asking; a refusal for a folder that can be seen is a `403` that is audited with its folder. A restore needs Browse and a signed-in account; guests can only ever be given Browse, because without a session there is no CSRF token and nobody to audit. A visitor with Full on a folder cannot change `root_path`, add folders, or see the folders on the server's disk. The people named in a list are checked against the user directory when they are added, the lists have at most 500 accounts, and the audit log and the lists of jobs show a visitor only the folders they may browse. The lists themselves (`access` in the audit details) are shown only to those who have Full on the folder. A new folder is seen by administrators only until it is given access. The pages and API calls that show a folder check a signed-in visitor with the user directory first (`openChecked`), so a deactivated account is a guest at once. A change of a folder is made in one transaction that locks its row and asks again whether the caller still has Full, so a Full that was revoked meanwhile cannot undo its own revocation; when it replaces the lists it also checks that they are still the ones the form or request was made from (`access_rev`), so an old form cannot bring back what somebody else took away; the update of a Full account that is not an administrator never writes `root_path`; whoever saves lists that take away their own Full has to confirm it (`confirm_lockout`). A person is written `user:<ID>` in forms, so an employee ID spelled `guest` or `everyone` cannot be taken for those groups. The text that hides the server's folders is built from the visible folders only, and the audit record of a refused request holds the route, not the typed path, so neither names a folder the visitor may not see. `internal/server/folders_test.go`, `folders_review_test.go` and `folder_settings_test.go` walk the pages and the API as a guest, two ordinary accounts (one of them has Full control of one folder) and an administrator, over four folders with different lists. |
| The server's own folders | Only administrators (the permission `manage`) see the folders on the server's disk: the real folder of a monitored folder, the backup folder (the repository), the real restore folder and the settings file. Everybody else, signed in or not, sees display folders (`\\server\share\folder`, see [ADR 0007](./adr/0007-display-folders-and-hiding-server-paths.md)); the backup folder is not named at all, only how full it is. Texts that quote a real folder are rewritten before they are sent, in the pages and in the API alike: job errors and logs, restore messages and problems, the reasons a file was not captured or a recovery point failed, audit details, component details. The map of the folders is built from the database per request; when it cannot be built the texts are left out. `PathMap.Mask` finds a folder without regard to case, with either slash, with a `\\?\` prefix, only where it ends (`D:\a\b2` is not `D:\a\b`), repeats until nothing is left and returns `[path hidden]` for a text it cannot make safe; it is tested with 30,000 random texts (`internal/service/paths_test.go`), and `internal/server/display_test.go` walks the pages and API as an administrator, an ordinary account and an anonymous visitor. |
| Sign-in | Company accounts are read from the Redis user directory (`app_user_*` hashes written by another application): read-only, with a restricted pickle decoder that never executes anything and has limits on size and depth; the password is compared in constant time and a record without a password never signs in. An optional local administrator has a hash (`pbkdf2-sha256`, 600,000 iterations, random salt) in `TIMEVAULT_ADMIN_PASSWORD_HASH`; its name, in any case, is never looked up in Redis, and its hash is always computed so timing does not reveal whether the name exists. |
| Brute force | An attempt is counted when it starts, so guesses that run in parallel cannot all pass before the first failure is known: 5 attempts per client address and 10 failures per account name in 10 minutes, then `429` with `Retry-After`, even with the right password. Names are compared without case and, for an e-mail address, by the part before the `@`, so varying the domain does not make a new account. A successful sign-in gives back its own slot only; it does not wipe the failures of the address. A sign-in that failed because Redis did not answer is not held against the account but counts for the address. Failed and throttled attempts are audited. The counters are in memory, keyed by the client address (the address that connects, or the one that a trusted proxy reports) and bounded. |
| Sessions | Stateless, HMAC-signed cookie that carries the account, its name and role and the Redis key it was read from (format version 2; cookies of the MVP are rejected): `HttpOnly`, `SameSite=Lax`, `Secure` when configured, expiry from `TIMEVAULT_SESSION_TTL`. The signing key comes from `TIMEVAULT_SESSION_KEY` or is random per start (sessions then end on restart). Every protected request asks Redis again (the answer is trusted for 60 seconds): a deactivated account or a changed role takes effect within a minute and the session is ended on the spot. When Redis does not answer, a session is trusted as issued and Redis is asked again after 15 seconds; a request that the visitor abandons is never taken for an outage. The pages that show an account more than a visitor (Backups, a job page, `GET /api/v1/sources`, `GET /api/v1/jobs/{id}`) check the account first; the other browsing pages read only the cookie. |
| Single sign-on | Optional (`TIMEVAULT_SSO_HOST`; [ADR 0009](./adr/0009-single-sign-on-and-trusted-proxies.md)). The server issues a token of 120 random bits for each attempt, keeps it in memory for 5 minutes with the client address and accepts only tokens it issued, so nobody can make it read an arbitrary `sso_login_*` key and a result is used once. The result of the company sign-on service is read from Redis with a `GET` only (TimeVault never deletes the key) by the same restricted decoder as the accounts, and the account must be active; the session gets the role of that account. With `TIMEVAULT_SSO_REQUIRE_SAME_IP=true` (the default) the address that the sign-on service saw must be the address of the browser that started the attempt, which stops a sign-in from being forced on somebody who opens a link that carries the attacker's token. At most 5 attempts wait per address and 2000 in all, a flow is looked at once a second, the page it returns to is at most 2,048 bytes (a longer one becomes `/`) so that what a visitor can make the server hold is bounded, and `start` and `poll` refuse requests from other sites. Every attempt is audited with its method, the Windows user and, when refused, the reason. |
| Trusted proxies | `X-Forwarded-For` is believed only for requests that come from an address in `TIMEVAULT_TRUSTED_PROXIES`; the client is then the right-most address of the header that is not a trusted proxy, so a client cannot choose its own address by adding to the header. Otherwise the header is ignored. The client address is used by the single sign-on check, the audit log and the sign-in limits. |
| Path prefix | Optional (`TIMEVAULT_BASE_PATH`, for example `/tv`; [ADR 0012](./adr/0012-base-path-behind-a-reverse-proxy.md)). The session cookie, the language cookie and the one-time message cookie are limited to that path, so the other applications on the same host name do not receive them. The prefix is taken off a request only as a whole path segment. The address that a sign-in, a language switch or a back link returns to is checked again after the prefix is off, because `/tv//host` would otherwise become `//host`, an address on another site. A prefix that starts with a path of the application is refused at start. A test fails when a template has an address that ignores the prefix or when code sets a cookie for the whole host. |
| CSRF | Every state-changing request needs the session's token (header or form field) and is rejected when `Origin` or `Sec-Fetch-Site` shows another site. The sign-in form checks the origin as well. Open redirects through `next` are blocked (only local paths are accepted). |
| Browser hardening | `Content-Security-Policy: default-src 'self'` with no inline script or style (a test scans every page), `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `Cache-Control: no-store` for pages. Output is escaped by `html/template`; a test shows names such as `{{7+7}}.txt` and `a&b'c.txt` are displayed literally. |
| Input validation | Client paths go through `pathutil` (no `..`, drive letters, reserved device names, invalid characters, excessive depth). Request bodies are limited to 1 MiB, JSON is strict (unknown fields rejected). All SQL uses bind parameters. |
| Reading sources | Folders are read through `os.Root`, so a crafted path or a link swapped in during a scan cannot lead outside the source. Junctions and symbolic links are never followed, and a file or folder that is replaced by a link after it was listed is detected and skipped. A source cannot overlap the repository, the restore folder or another source: the folders are compared by their real location (junctions and links resolved), when a source is added and again when each backup starts, and the scan skips those folders as a second guard. Sources are only read. |
| Restore | Writes only below `TIMEVAULT_RESTORE_ROOT`, into a folder whose name is validated as a single path component (created when it does not exist; when it already exists, for example for a repeated restore, the conflict policy decides what happens to files that are already there). The destination must be a plain folder (an existing junction or symbolic link is refused) and the restore root is compared with the repository and every source by real location. Preview first; confirmation token bound to user, exact plan and a 15-minute expiry; replacing files needs an explicit extra confirmation; all writes go through `os.Root`; unsafe catalog names (`..`, `:`, `\`, reserved names) are blocked; each file is written to a temporary file, checked against its SHA-256 and size, and only then renamed. The audit record is written before the job is queued, and a restore that cannot be audited does not run. Nothing in a restore deletes source or repository data. |
| Service instance | Only one service can run against a database: a PostgreSQL advisory lock is taken before start-up recovery, so a second launch cannot mark the first one's running jobs as failed or abort its recovery points. |
| Everything | Only loopback hosts are accepted for the engine URL, enforced when the connection is made; redirects are not followed; responses are size-limited; optional HTTP Basic credentials come from the environment and are never logged. The user's text is split into words that are all quoted so Everything operators (`|`, `!`, `<>`, `regex:`) are literal, the query is confined to the source root, and every result is checked against the root again. |
| Audit | `audit_events` is append-only (a database trigger rejects UPDATE and DELETE). Sign-ins (with their method and, for single sign-on, the Windows user), failed and throttled sign-ins (with the account name as typed, cut to 64 characters, and the reason for a refused single sign-on), refused requests (`access.denied`: no permission, too low a level on a folder, `root_path` from somebody who is not an administrator, or a bad CSRF token; the ones about a folder carry it), source creation and every source change (old and new value per field, the version limit and the access lists included), backup/verify requests and results, restore previews, requests and results, the deletion of old versions (`retention.prune`), job cancellations (with the folder of the job) and the steps of a program update (`app.update`, by the actor `updater`, with no path and no error text) are recorded with the user and remote address; backups, verifications, restores and the deletion of old versions also record how long they ran. |
| Automatic update | Optional (`TIMEVAULT_UPDATE_URL`; [ADR 0014](./adr/0014-self-update-from-a-release-manifest.md)). The address may not hold a user name, a password, a query or a fragment; the manifest is at most 64 KiB and parsed strictly, the program at most 512 MiB, and redirects stop after five. A downloaded program is kept only when its size and sha256 are the manifest's, it is run (`version`, `check-config`, with the environment of the service) only after that, and the install is a rename in the folder of the running program: the target is never taken from the manifest, so `package_url` can only say where to read from. A program of another version than the manifest says is refused, and a release that failed is not tried again until the manifest changes. Asking for a look is for administrators (`manage`, with the CSRF token); the address of the release and the last error, which may quote a share or a folder of the server, are shown to administrators only, in the pages and in the API, and the audit events carry the stage and the versions but no path and no error text. The notice under the header is set as text, never as markup. |
| Pictures of the accounts | Optional (`TIMEVAULT_AVATAR_URL`). The browser reads a picture from the same host with a request of its own, only for signed-in visitors (the places that name accounts are not shown to others), and only when it is an answer of `200` with an image of at most 512 KiB; it is shown from a `data:` URL, so the `Content-Security-Policy` (`img-src 'self' data:`) is unchanged. The employee ID in the address is validated (letters, digits and `. _ - @`) and encoded; the local administrator and the service's own names are never asked for. TimeVault stores and proxies nothing. |
| Secrets | Read only from environment variables or the `.env` file (the environment wins; the start-up log names, and never shows, the settings that the environment overrides), redacted when the configuration is logged, never stored in the repository. The startup log, the Settings page and the Redis report show the database and Redis as `host:port/name` only; errors from the Redis client have the password of the URL masked. `/.env` is git-ignored and, in development, the only file that holds secrets: the dev scripts write the generated database password, session key and administrator password hash there (the generated administrator password is in `data/dev/admin-password.txt`, also git-ignored). |

## Gaps and limits (do not rely on the MVP for these)

- **Authorization is per monitored folder and no finer.** An account has Browse, Back up or Full on each folder (see "Folder access"); there are no per-path rights, NTFS ACLs and Active Directory groups are not consulted, and a person who may browse a folder sees the names, sizes and times of everything in it, and all of its history. Everybody who is signed in can read the audit log (the events of the folders they may browse, and the sign-ins and other events that belong to no folder, which hold other people's addresses and the names that were typed) and the status and settings pages (the settings page shows the service configuration; the status page counts the queued and running jobs of the folders the visitor may browse). Whoever has Full on a folder can lower its version limit, which deletes older versions for good (after a confirmation that the audit log records). A person's rights are those of their employee ID: a deactivated account keeps its entries in the lists until somebody removes them (the editor shows them as "not in the directory"), and takes effect again when the account is reactivated. Single sign-on only identifies the person: the role still comes from the account in Redis.
- **Known limits of the folder rights.** (1) A program older than 0.1.7 does not know the rights: 0.1.6 accepts a database that migration `0005` changed and would let every visitor see every folder and every signed-in account back up and restore them again; never start it against such a database. (2) Folder names are unique, so somebody with Full who renames their folder to the name of a folder they cannot see is told that the name is taken, which shows that such a folder exists (nothing else about it). (3) A restore that is queued or running goes on when the account that started it loses Browse on the folder; it writes below the restore folder only, and an administrator can stop it. (4) While Redis cannot be reached, a session is trusted as issued (see above), so an account that was deactivated or demoted meanwhile keeps the rights it had until Redis answers again; a change of the lists of a folder takes effect at once. (5) Full includes the right to hand Full to anybody, by decision ([ADR 0013](./adr/0013-per-folder-access-levels.md)); the audit log records the old and the new lists.
- **Anonymous browsing exposes metadata.** Anyone who can reach the address sees the names, sizes, modification times and structure of every monitored folder that gives guests Browse, and of its history, the display folders (and so the name of the server), the times and counts of recovery points, and the state and schedule of backups, without an account. Folders that existed before 0.1.7 give guests Browse until an administrator changes that. Not the contents, the folders on the server's disk, who asked for a job or why it failed. Reads are not rate limited. Keep the address on a network where that is acceptable, or put a reverse proxy or firewall in front.
- **Hiding the server's folders is best effort.** It works on decoded text and knows the folders of the monitored folders, the repository and the restore folder as configured. A folder written in an unusual way (an 8.3 short name, a drive letter or a junction that is another name for the same disk) is not recognised, and a text that is already escaped (JSON, `%q`) is not masked as text. The service checks the host of a display folder, not that the share leads to the monitored folder, so a wrong share name shows people a path that does not exist, not a path that exposes anything. Display folders are what administrators typed: do not put anything secret in them.
- **Passwords travel and rest in plain text.** The other application stores the passwords of the company accounts as plain text in Redis, and the sign-in form posts them to TimeVault: without HTTPS anyone on the network path can read them. Redis itself should require a password and not be reachable from the network.
- **Sign-in limits behind a reverse proxy.** The limits count the client address. Without `TIMEVAULT_TRUSTED_PROXIES` that is the address that connects, so behind a proxy all visitors share the proxy's address and five attempts lock everybody out for ten minutes. With the proxies listed, `X-Forwarded-For` is believed from them: the proxy must put the address it saw into the header (set or append, never pass a client's value through unchanged), or a client can choose its own address. In nginx that is `proxy_set_header X-Forwarded-For $remote_addr;` in the first proxy, not `$http_x_forwarded_for`: with the second a forged header was recorded as the address of the client in the audit log in a test against version 0.1.5, and the single sign-on check uses the same address. With two proxies in a row the proxy next to TimeVault must take the address of the browser from the one in front of it (see [runbook.md](./runbook.md#two-proxies-in-a-row)); otherwise it tells TimeVault the address of the front proxy, and every single sign-in is refused. The account limit applies either way.
- **Under a path prefix TimeVault shares its origin.** With `TIMEVAULT_BASE_PATH` the cookies are separated from the other applications of the host name by their path, but scheme, host and port are the same, so a script flaw in another application on that host name could call TimeVault's pages and API with the visitor's session. A host name or a port of its own for TimeVault removes that; the path prefix is the weaker setup.
- **Single sign-on trusts the sign-on service and Redis.** Whoever can write `sso_login_*` keys to the Redis of the accounts, or runs the sign-on service, can sign in as anybody; the same Redis is already trusted for the accounts. The address check only stops a sign-in from being forced on a person; it does not prove who the person is. With `TIMEVAULT_SSO_REQUIRE_SAME_IP=false` the forcing attack is possible for the 5 minutes that a flow lives (it needs a victim who opens a link and a sign-on service that records the victim's account).
- **Lock-out.** Ten failed attempts at one account name refuse that account for ten minutes, the local administrator included, even with the right password; anyone who knows a name can lock it out. A restart clears the counters.
- **Sessions cannot be revoked one by one.** They are stateless. Deactivating an account in Redis ends its sessions within a minute; changing its password in the other application does not. Changing `TIMEVAULT_SESSION_KEY` ends all of them. Logging out only clears the browser's cookie.
- **No TLS in the service** and no rate limit beyond the sign-in limits.
- **Redis data is trusted.** One live record per employee ID is assumed; a stale record that the other application leaves behind can keep an old role or state for the session that signed in with it (the report of `check-redis-users` counts employee IDs on more than one key). A reply is read whole before it is decoded, and the decoder limits only what it decodes. A sign-in costs a `SCAN` of the database; the per-address limit bounds how often a visitor can cause it. A login that matches more than 200 keys is refused as ambiguous. The browsing pages that only read the cookie keep showing the signed-in header and buttons of a deactivated account until its first request that matters ends the session; what such a request would do is refused.
- **The repository is not encrypted or tamper-proof.** Objects get the read-only attribute and are verified by hash, but anyone with file-system access to the repository can alter or delete them. There is no off-host copy. The version limit of a monitored folder (0.1.4) deletes versions and then the repository content that nobody refers to: this is permanent, an administrator who lowers a limit has to confirm it, and the audit log records who did it; a recovery point that lost versions is marked partial and no longer shows every file.
- **Power-loss durability is best effort.** File contents are flushed before an object is published and the folders that received objects are flushed before a recovery point is committed, but this has not been tested against a real power failure. Run a deep integrity check after an unclean shutdown.
- **Missing repository content is found late.** A normal backup does not re-check the repository objects of files it carries over unchanged. An integrity check (Verify) finds missing or damaged objects, a restore refuses to use them, and a **Full re-read** backup writes missing content again.
- **Live-scan consistency.** Files are read from the live disk (no VSS). Torn reads are detected and retried, locked files are skipped and reported, but a set of related files may come from slightly different moments.
- **Metadata fidelity.** NTFS ACLs, alternate data streams, ownership, EFS and hard-link relationships are not preserved; restored files take the destination's permissions. Modification time and the common attribute bits are restored.
- **Privileges.** The service runs as the account that starts it. Run it with the least rights that can read the sources and write the repository and restore folders. A separate privileged worker is not implemented.
- **Everything instance.** The adapter cannot see how Everything is bound. Keep its "Bind to interfaces" option at `127.0.0.1`, disable "Allow file download", and set a username and password.
- **Source path check.** The check that refuses network shares only looks for a leading `\\` on the text as typed. `//host/share` and `\\?\UNC\host\share` are not recognized, so the service would contact that SMB server (and send Windows credentials) when such a source is added. Only administrators can add monitored folders; use local drive paths.
- **Restore plan versus execution.** The confirmation covers the plan that was previewed, but the restore job plans again when it runs and does not compare the result with the approved plan. A file that appears in the destination while the job is queued can be replaced under the `overwrite` policy without a new confirmation, and `create` and `rename` items are published with an unconditional rename, so two restores into the same folder at the same time can replace each other's files. Do not run restores into the same folder concurrently.
- **Restore folder is trusted storage.** The restore root is resolved by path at every step, so replacing it between validation and use is not detected; a staged `.tvpart-*` file is verified by handle but published by path; and the attributes of an existing target are cleared before it is replaced, so a hard link planted there to another file would change that file's attributes. Whoever can write inside the restore folder can change restored files anyway, so keep its permissions tight.
- **Development mode.** With `TIMEVAULT_AUTH_DISABLED=true` everybody is the local administrator and there is no Host header check, so a malicious web page using DNS rebinding could in principle reach the service from the browser of the person who runs it (not tested). Do not use that mode on a computer that browses untrusted sites; use sign-in instead.
- **Automatic backups.** Without a version limit, automatic runs that find changes add recovery points for good. A scheduled folder that cannot be read produces one failed job and one audit record per interval. An automatic run that finds nothing changed is judged by the number of items it could not read, not by which ones. With the Everything probe on (off by default) a scan is skipped when Everything's index says nothing changed, so a change that Everything has not seen is found by the next scan that is not skipped, at the latest after `TIMEVAULT_SCHEDULER_FULL_SCAN_EVERY`.
- **The release folder decides what runs on the server (0.1.8).** With `TIMEVAULT_UPDATE_URL` set, whoever can write the release folder (or its share), or sit on the network path to an `http` address, can make the service run any program, with the rights of the account of the service: it reads every monitored folder and writes the repository and the restore folder. There is no signature; the size and the sha256 in the manifest come from the same place as the program, so they protect against a damaged or half-copied file, not against somebody who can write both. The downloaded program is run twice (`version`, `check-config`) before anything is installed, so a malicious release already runs at that point, as the account of the service. Let only administrators write the release folder, use `https` for an address, run the service with the least rights it needs (the folder of the program must be writable for it, and that is the price of the feature), and do not set the address at all where this is not acceptable. Adding a signature to the manifest is possible without changing the rest ([ADR 0014](./adr/0014-self-update-from-a-release-manifest.md)).
- **An update applies migrations by itself (0.1.8).** A service that updates itself needs `TIMEVAULT_AUTO_MIGRATE=true`, so a new release changes the database without anybody running `migrate`; there is no automatic way back, and an older program may not be safe on a migrated database (see the upgrade notes of each version). The old program is kept (`timevault.old-<version>.exe`) for a way back by hand.
- **The launcher keeps the code it was started with (0.1.8).** In `supervise` mode the process that was started stays as a small launcher; an update replaces the file on disk and the program it starts, not the launcher, which has no network or database code but also gets no fixes until it is restarted by hand.
- **The pictures of the accounts are another application's files (0.1.8).** Whoever may see a name in the audit log, a job page or a list of people may see the picture that the other application keeps for that employee ID; the pictures are not access-controlled by TimeVault. Nothing of this is stored by TimeVault, and the service never serves them itself.

# 中文

## 概述

本文档列出 TimeVault（0.1.8 版）中已有的安全控制和仍然存在的缺口。它描述的是实际实现，而不是意图；plan.md 要求更多的地方，都列在缺口里。

## 已有的控制

| 方面 | 控制措施 |
|---|---|
| 网络暴露 | 服务默认监听 `127.0.0.1`（端口 8660）。除非设置 `TIMEVAULT_ALLOW_NON_LOOPBACK=true`，否则会拒绝非回环地址；并且在非回环地址上永远不允许关闭登录。服务监听本机之外时，启动时会记录一条警告。服务本身不终止 TLS：请在前面放置支持 HTTPS 的反向代理，并设置 `TIMEVAULT_COOKIE_SECURE=true`。 |
| 开放浏览 | 没有账号的访问者只能查看，而且只能查看允许访客"浏览"的监控文件夹（见"文件夹访问"）：浏览页面和只读 JSON API。他们永远看不到审计日志、状态页和设置页、恢复任务、任务是谁发起的、任务为什么失败及其日志，也看不到服务器磁盘上的文件夹，并且没有任何接口提供文件内容。有测试会在有账号和无账号两种情况下遍历每条路由（`internal/server/access_test.go`）。 |
| 文件夹访问 | 账号能做什么，按监控文件夹分别决定（浏览、备份、完全；[ADR 0013](./adr/0013-per-folder-access-levels.md)），可以授予访客、所有已登录的人或单个工号；管理员对所有文件夹拥有"完全"。检查在 HTTP 层，每个要访问文件夹的处理函数都要经过三个函数之一（`internal/server/access.go` 中的 `loadSource`、`visibleSources`、`jobSource`）；当有处理函数直接从服务读取文件夹时，`TestHandlersReachFoldersThroughTheAccessChecks` 会失败。访问者不能浏览的文件夹，在所有地方（页面、API、任务、恢复点、版本、搜索、恢复）都是"未找到"，并且回答、状态码和文字与不存在的文件夹完全相同，所以无法通过询问来探测被隐藏的文件夹；对能看到的文件夹的拒绝是 `403`，并且会连同该文件夹一起记入审计。恢复需要"浏览"权限和已登录的账号；访客只能被授予"浏览"，因为没有会话就没有 CSRF 令牌，也没有可审计的人。对某个文件夹拥有"完全"的访问者不能修改 `root_path`、不能添加文件夹，也看不到服务器磁盘上的文件夹。列表中指定的人在添加时会对照用户目录检查，每个列表最多 500 个账号，审计日志和任务列表只向访问者显示他们可以浏览的文件夹。列表本身（审计详情中的 `access`）只显示给对该文件夹拥有"完全"的人。新文件夹在被授予访问权之前只有管理员能看到。显示文件夹的页面和 API 调用会先向用户目录核实已登录的访问者（`openChecked`），所以被停用的账号会立即变成访客。对文件夹的修改在一个事务中进行：它锁定文件夹的行，并再次确认调用者是否仍有"完全"，所以期间被撤销的"完全"不能撤销自己的撤销；替换列表时，它还会检查它们是否仍是表单或请求所依据的那些（`access_rev`），所以旧表单不能把别人取消的东西又带回来；拥有"完全"但不是管理员的账号所做的更新永远不会写入 `root_path`；保存的列表会取消自己的"完全"的人，必须确认（`confirm_lockout`）。在表单中人员写成 `user:<工号>`，所以拼写为 `guest` 或 `everyone` 的工号不会被当成这两个组。在文本中隐藏服务器文件夹的映射只由可见的文件夹构建，被拒绝请求的审计记录保存的是路由而不是输入的路径，所以两者都不会点出访问者无权看到的文件夹。`internal/server/folders_test.go`、`folders_review_test.go` 和 `folder_settings_test.go` 在四个列表各不相同的文件夹上，分别以访客、两个普通账号（其中一个拥有某个文件夹的"完全"权限）和一个管理员的身份遍历页面和 API。 |
| 服务器自己的文件夹 | 只有管理员（权限 `manage`）能看到服务器磁盘上的文件夹：监控文件夹的真实文件夹、备份文件夹（仓库）、真实的恢复文件夹和设置文件。其他人无论是否登录，看到的都是显示文件夹（`\\server\share\folder`，见 [ADR 0007](./adr/0007-display-folders-and-hiding-server-paths.md)）；备份文件夹根本不会被点名，只会说明它用了多少。引用真实文件夹的文本在发送之前会被改写，页面和 API 一样：任务错误和日志、恢复消息和问题、文件未能备份或恢复点失败的原因、审计详情、组件详情。文件夹的映射每个请求从数据库构建；无法构建时，相关文本会被省略。`PathMap.Mask` 查找文件夹时不区分大小写，两种斜杠都可以，带 `\\?\` 前缀也可以，并且只在文件夹结束的地方才算（`D:\a\b2` 不是 `D:\a\b`），会重复到没有可隐藏的内容，对无法确保安全的文本返回 `[path hidden]`；它用 30,000 个随机文本测试过（`internal/service/paths_test.go`），`internal/server/display_test.go` 则分别以管理员、普通账号和匿名访问者的身份遍历页面和 API。 |
| 登录 | 公司账号从 Redis 用户目录（由另一个应用写入的 `app_user_*` 哈希）读取：只读，使用受限的 pickle 解码器，它绝不执行任何内容，并对大小和深度设有限制；密码以恒定时间比较，没有保存密码的记录永远无法登录。可选的本地管理员的哈希（`pbkdf2-sha256`，600,000 次迭代，随机盐）在 `TIMEVAULT_ADMIN_PASSWORD_HASH` 中；它的名字（无论大小写）永远不会到 Redis 中查找，并且始终会计算哈希，因此耗时不会暴露该名字是否存在。 |
| 暴力破解 | 尝试在开始时就被计数，所以并行的猜测不会在第一次失败被知道之前全部通过：10 分钟内每个客户端地址 5 次尝试、每个账号名 10 次失败，之后返回 `429` 和 `Retry-After`，即使随后提供了正确的密码也一样。账号名不区分大小写，邮箱地址按 `@` 之前的部分比较，所以改变域名不会变成新的账号。成功登录只归还它自己的那一次；不会清除该地址的失败记录。因 Redis 没有应答而失败的登录不会算到账号头上，但会计入地址。失败和被限流的尝试都会写入审计。计数保存在内存中，以客户端地址（连接过来的地址，或受信任的代理报告的地址）为键，并且有上限。 |
| 会话 | 无状态、HMAC 签名的 Cookie，带有账号、姓名、角色以及读取它的 Redis 键（格式版本 2；MVP 的 Cookie 会被拒绝）：`HttpOnly`、`SameSite=Lax`，配置后带 `Secure`，有效期来自 `TIMEVAULT_SESSION_TTL`。签名密钥来自 `TIMEVAULT_SESSION_KEY`，否则每次启动随机生成（此时重启后会话失效）。每个受保护的请求都会再次询问 Redis（答复被信任 60 秒）：账号被停用或角色变化会在一分钟内生效，并且会话会当场结束。当 Redis 没有应答时，会话按签发时的内容被信任，15 秒后再询问 Redis；访问者放弃的请求绝不会被当作故障。对账号比对访问者展示更多内容的页面（备份页、任务页、`GET /api/v1/sources`、`GET /api/v1/jobs/{id}`）会先检查账号；其他浏览页面只读取 Cookie。 |
| 单点登录 | 可选（`TIMEVAULT_SSO_HOST`；[ADR 0009](./adr/0009-single-sign-on-and-trusted-proxies.md)）。服务器为每次尝试签发一个 120 位随机令牌，连同客户端地址在内存中保存 5 分钟，并且只接受自己签发的令牌，所以没有人能让它去读任意的 `sso_login_*` 键，结果也只能使用一次。公司单点登录服务的结果只用 `GET` 从 Redis 读取（TimeVault 从不删除这个键），使用与账号相同的受限解码器，并且账号必须是有效的；会话获得该账号的角色。当 `TIMEVAULT_SSO_REQUIRE_SAME_IP=true`（默认）时，单点登录服务看到的地址必须是发起该尝试的浏览器的地址，这样就能防止把登录强加给打开了带有攻击者令牌的链接的人。每个地址最多同时等待 5 次尝试，总共 2000 次，一个流程每秒最多查看一次，它登录后要返回的页面地址最长 2,048 字节（更长的会变成 `/`），所以访问者能让服务器占用的内容是有界的，`start` 和 `poll` 会拒绝来自其他站点的请求。每次尝试都会审计，记录登录方式、Windows 用户，被拒绝时还有原因。 |
| 受信任的代理 | 只有来自 `TIMEVAULT_TRUSTED_PROXIES` 中地址的请求，其 `X-Forwarded-For` 才会被信任；此时客户端是该头中最右边的、本身不是受信任代理的地址，所以客户端无法通过往该头里追加内容来选择自己的地址。否则该头被忽略。客户端地址用于单点登录检查、审计日志和登录限制。 |
| 路径前缀 | 可选（`TIMEVAULT_BASE_PATH`，例如 `/tv`；[ADR 0012](./adr/0012-base-path-behind-a-reverse-proxy.md)）。会话 Cookie、语言 Cookie 和一次性提示 Cookie 都限制在该路径内，所以同一主机名下的其他应用收不到它们。前缀只会作为完整的路径段从请求中去掉。登录、切换语言或返回链接之后要回到的地址，在去掉前缀之后会再检查一遍，否则 `/tv//host` 会变成 `//host`，即另一个站点的地址。以应用自身某个路径开头的前缀在启动时会被拒绝。当某个模板里有忽略前缀的地址，或者代码设置了作用于整个主机的 Cookie 时，会有测试失败。 |
| CSRF | 每个会改变状态的请求都需要会话令牌（请求头或表单字段），并且当 `Origin` 或 `Sec-Fetch-Site` 显示来自其他站点时会被拒绝。登录表单同样检查来源。通过 `next` 的开放重定向被阻止（只接受本站路径）。 |
| 浏览器加固 | `Content-Security-Policy: default-src 'self'`，没有内联脚本或样式（有测试扫描每个页面），`frame-ancestors 'none'`，`X-Content-Type-Options: nosniff`，`Referrer-Policy: same-origin`，页面使用 `Cache-Control: no-store`。输出由 `html/template` 转义；测试表明 `{{7+7}}.txt` 和 `a&b'c.txt` 这样的名称会被原样显示。 |
| 输入校验 | 客户端路径经过 `pathutil`（不允许 `..`、盘符、保留设备名、非法字符、过深层级）。请求体限制为 1 MiB，JSON 为严格模式（拒绝未知字段）。所有 SQL 都使用绑定参数。 |
| 读取备份源 | 通过 `os.Root` 读取文件夹，所以精心构造的路径或扫描期间被替换进来的链接都无法指向备份源之外。联接点和符号链接永不被跟随；如果文件或文件夹在被列出之后被替换成链接，会被检测到并跳过。备份源不能与仓库、恢复目录或其他备份源重叠：比较的是文件夹的真实位置（解析了联接点和链接之后），添加备份源时以及每次备份开始时都会检查，扫描时也会跳过这些文件夹作为第二道保护。备份源只会被读取。 |
| 恢复 | 只写入 `TIMEVAULT_RESTORE_ROOT` 之下的文件夹，其名称按单个路径组件校验（不存在时创建；已存在时，例如重复恢复，由冲突策略决定如何处理已有的文件）。目标位置必须是普通文件夹（已存在的联接点或符号链接会被拒绝），恢复根目录与仓库以及每个备份源比较的是真实位置。先预览；确认令牌与用户、精确的计划以及 15 分钟有效期绑定；替换文件需要额外的明确确认；所有写入都通过 `os.Root`；目录库中不安全的名称（`..`、`:`、`\`、保留名）会被阻止；每个文件先写入临时文件，核对 SHA-256 和大小，再重命名。审计记录在任务入队之前写入，无法审计的恢复不会运行。恢复不会删除任何源数据或仓库数据。 |
| 服务实例 | 同一个数据库只能运行一个服务：在启动恢复之前会获取 PostgreSQL advisory 锁，所以第二次启动不能把第一个服务正在运行的任务标记为失败，也不能中止它的恢复点。 |
| Everything | 引擎 URL 只接受回环主机，并在建立连接时强制检查；不跟随重定向；限制响应大小；可选的 HTTP Basic 凭据来自环境变量，绝不写入日志。用户输入的文本被拆分为词并全部加引号，使 Everything 的操作符（`|`、`!`、`<>`、`regex:`）都按字面处理；查询被限定在备份源根目录内，并且对每个结果再次检查是否在根目录内。 |
| 审计 | `audit_events` 只追加（数据库触发器会拒绝 UPDATE 和 DELETE）。登录（带有登录方式，单点登录还带有 Windows 用户）、登录失败和被限流的登录（账号名按输入的内容记录，截断到 64 个字符，被拒绝的单点登录还有原因）、被拒绝的请求（`access.denied`：没有权限、对某个文件夹的级别太低、不是管理员的人提交了 `root_path`，或 CSRF 令牌错误；与文件夹有关的会带上该文件夹）、创建备份源和备份源的每一次变更（每个字段的旧值和新值，包括版本数上限和访问权限列表）、备份/校验的请求与结果、恢复预览、请求与结果、旧版本的删除（`retention.prune`）、任务取消（带有任务所属的文件夹）以及程序更新的各个步骤（`app.update`，操作者为 `updater`，没有路径，也没有错误文本），都会连同用户和远端地址一起记录；备份、校验、恢复和旧版本的删除还会记录它们运行了多久。 |
| 自动更新 | 可选（`TIMEVAULT_UPDATE_URL`；[ADR 0014](./adr/0014-self-update-from-a-release-manifest.md)）。地址中不能包含用户名、密码、查询串或片段；清单至多 64 KiB 并被严格解析，程序至多 512 MiB，重定向五次后停止。下载的程序只有在大小和 sha256 与清单一致时才保留，并且只在那之后才会运行它（`version`、`check-config`，使用服务的环境变量），安装是在正在运行的程序所在的文件夹中做重命名：目标从不取自清单，所以 `package_url` 只能说明从哪里读取。版本与清单所说不一致的程序会被拒绝，失败的发布在清单改变之前不会再试。要求立即查看只给管理员（`manage`，并需要 CSRF 令牌）；发布地址和最近的错误可能引用服务器的共享或文件夹，只向管理员显示（页面和 API 都是如此），审计事件中有阶段和版本，但没有路径，也没有错误文本。页眉下面的提示是作为文本设置的，绝不是标记。 |
| 账号头像 | 可选（`TIMEVAULT_AVATAR_URL`）。浏览器用自己的请求从同一主机读取头像，只针对已登录的访问者（显示账号名称的地方不会给其他人看），并且只有应答是 `200`、内容是不超过 512 KiB 的图片时才使用；它从 `data:` URL 显示，所以 `Content-Security-Policy`（`img-src 'self' data:`）保持不变。地址中的工号经过校验（字母、数字和 `. _ - @`）并被编码；本地管理员和服务自己的名称从不请求。TimeVault 不存储也不代理任何东西。 |
| 机密信息 | 仅从环境变量或 `.env` 文件读取（环境变量优先；启动日志会点名、但绝不显示被环境变量覆盖的设置），记录配置日志时会脱敏，绝不存入代码仓库。启动日志、设置页和 Redis 报告只把数据库和 Redis 显示为 `host:port/name`；Redis 客户端的错误信息中，URL 的密码会被遮盖。`/.env` 已被 git 忽略，开发时它是唯一存放机密信息的文件：开发脚本把生成的数据库密码、会话密钥和管理员密码哈希写在这里（生成的管理员密码本身在同样被 git 忽略的 `data/dev/admin-password.txt` 中）。 |

## 缺口与限制（这些方面请勿依赖 MVP）

- **授权按监控文件夹分别决定，没有更细的粒度。** 账号对每个文件夹拥有"浏览"、"备份"或"完全"（见"文件夹访问"）；没有按路径的权限，不会查询 NTFS ACL 或 Active Directory 组，能浏览某个文件夹的人，能看到其中所有内容的名称、大小和时间，以及它的全部历史。每个已登录的人都可以读取审计日志（他们可以浏览的文件夹的事件，以及不属于任何文件夹的登录等事件，其中有他人的地址和输入过的名称）以及状态页和设置页（设置页显示服务配置；状态页统计访问者可以浏览的文件夹的排队和运行中的任务数）。对某个文件夹拥有"完全"的人可以调低它的版本数上限，这会永久删除较旧的版本（需要确认，审计日志会记录）。一个人的权限就是他的工号的权限：被停用的账号在列表中的条目会一直保留，直到有人删除它（编辑器会把它们显示为"不在用户目录中"），账号重新启用后又会重新生效。单点登录只负责识别这个人：角色仍然来自 Redis 中的账号。
- **文件夹权限的已知限制。**（1）早于 0.1.7 的程序不认识这些权限：0.1.6 接受被迁移 `0005` 改过的数据库，会让每个访问者再次看到每个文件夹，让每个已登录账号再次对它们备份和恢复；绝不要让它去启动这样的数据库。（2）文件夹名称是唯一的，所以拥有"完全"的人把自己的文件夹重命名为一个他们看不到的文件夹的名称时，会被告知该名称已被占用，这说明这样一个文件夹存在（关于它的其他信息一概没有）。（3）已排队或正在运行的恢复，在启动它的账号失去该文件夹的"浏览"权限后仍会继续；它只会写入恢复文件夹之下，管理员可以停止它。（4）Redis 无法访问期间，会话按签发时的状态被信任（见上文），所以期间被停用或被降级的账号，会一直保留它原来的权限，直到 Redis 重新应答；文件夹列表的修改则立即生效。（5）"完全"包含把"完全"授予任何人的权利，这是决定如此（[ADR 0013](./adr/0013-per-folder-access-levels.md)）；审计日志会记录修改前和修改后的列表。
- **匿名浏览会暴露元数据。** 能访问该地址的任何人，不用账号就能看到每个允许访客"浏览"的监控文件夹及其历史的名称、大小、修改时间和结构、显示文件夹（因此也包括服务器的名称）、恢复点的时间和数量，以及备份的状态和计划。0.1.7 之前就存在的文件夹，在管理员修改之前仍然允许访客浏览。看不到内容、服务器磁盘上的文件夹、任务是谁发起的或为什么失败。读取没有限速。请把该地址限定在可以接受这一点的网络里，或在前面放置反向代理或防火墙。
- **隐藏服务器的文件夹只是尽力而为。** 它基于已解码的文本，并且只认识按配置给出的监控文件夹、仓库和恢复文件夹。以不寻常的方式书写的文件夹（8.3 短名称、同一磁盘的另一个盘符或联接点别名）无法被识别，已经转义过的文本（JSON、`%q`）也不会被当作文本来隐藏。服务检查显示文件夹的主机，而不检查共享是否通向该监控文件夹，所以共享名写错时，人们看到的是一个不存在的路径，而不是暴露了什么的路径。显示文件夹是管理员输入的内容：不要在里面放任何机密。
- **密码以明文传输和存放。** 另一个应用把公司账号的密码以明文保存在 Redis 中，而登录表单会把它们提交给 TimeVault：没有 HTTPS 时，网络路径上的任何人都能读到。Redis 本身应当要求密码，并且不能从网络访问。
- **反向代理之后的登录限制。** 限制统计的是客户端地址。没有 `TIMEVAULT_TRUSTED_PROXIES` 时它是连接过来的地址，所以放在代理之后时，所有访问者共用代理的地址，5 次尝试就会让所有人被锁定 10 分钟。列出代理之后，会信任它们发来的 `X-Forwarded-For`：代理必须把它看到的地址放进该头（设置或追加，绝不能原样传递客户端给的值），否则客户端可以选择自己的地址。在 nginx 中，就是在第一层代理里写 `proxy_set_header X-Forwarded-For $remote_addr;`，而不是 `$http_x_forwarded_for`：在针对 0.1.5 版本的测试中，用后者时，伪造的头会被当作客户端的地址记入审计日志，而单点登录检查用的是同一个地址。有两层代理时，紧挨着 TimeVault 的代理必须从它前面的那一层取得浏览器的地址（见 [runbook.md](./runbook.md#两层代理)）；否则它告诉 TimeVault 的是前一层代理的地址，每次单点登录都会被拒绝。按账号的限制在两种情况下都有效。
- **在路径前缀之下，TimeVault 与其他应用共享源。** 设置 `TIMEVAULT_BASE_PATH` 后，Cookie 通过路径与同一主机名下的其他应用隔离，但协议、主机和端口是相同的，所以该主机名下另一个应用中的脚本缺陷，可能会以访问者的会话调用 TimeVault 的页面和 API。给 TimeVault 单独的主机名或端口可以消除这一点；路径前缀是较弱的做法。
- **单点登录信任单点登录服务和 Redis。** 能把 `sso_login_*` 键写入账号所在的 Redis、或者能运行单点登录服务的人，可以冒充任何人登录；账号本来就信任同一个 Redis。地址检查只能防止把登录强加给某个人，它并不证明这个人是谁。设置 `TIMEVAULT_SSO_REQUIRE_SAME_IP=false` 后，在一个流程存在的 5 分钟内，上述强加登录的攻击是可能的（需要受害者打开一个链接，并且单点登录服务记录了受害者的账号）。
- **锁定。** 对同一个账号名 10 次失败的尝试，会让该账号被拒绝 10 分钟（包括本地管理员），即使密码正确也一样；知道账号名的任何人都可以把它锁定。重启会清除计数。
- **会话无法单独撤销。** 会话是无状态的。在 Redis 中停用账号会在一分钟内结束它的会话；在另一个应用中修改密码则不会。更改 `TIMEVAULT_SESSION_KEY` 会使所有会话失效。退出登录只会清除浏览器端的 Cookie。
- **服务内没有 TLS**，除登录限制外没有其他限速。
- **Redis 数据是被信任的。** 假定每个工号只有一条有效记录；另一个应用留下的过期记录，可能让用它登录的会话保留旧的角色或状态（`check-redis-users` 的报告会统计出现在多个键上的工号）。回复会被完整读取之后才解码，而解码器只限制它所解码的内容。一次登录会对数据库执行一次 `SCAN`；按地址的限制限制了访问者能触发它的频率。匹配到超过 200 个键的登录名会被当作有歧义而拒绝。只读取 Cookie 的浏览页面，会让被停用账号的登录页眉和按钮一直显示到它的第一次重要请求结束会话为止；这样的请求要做的事会被拒绝。
- **仓库没有加密，也不防篡改。** 对象带有只读属性并通过哈希校验，但任何能访问仓库文件系统的人都可以修改或删除它们。没有异机副本。监控文件夹的版本数上限（0.1.4）会删除版本，随后删除没有人再引用的仓库内容：这是永久的，管理员调低上限时必须确认，审计日志会记录是谁做的；失去版本的恢复点会被标记为不完整，不再显示每个文件。
- **断电后的持久性是尽力而为。** 对象在发布之前会先刷新文件内容，恢复点提交之前会刷新接收了对象的文件夹，但这一点没有在真实断电下测试过。非正常关机之后请运行一次深度完整性校验。
- **仓库内容缺失发现得较晚。** 普通备份不会重新检查它原样沿用的未变化文件所对应的仓库对象。完整性校验（Verify）可以发现缺失或损坏的对象，恢复会拒绝使用它们，而**完整重读**备份会把缺失的内容重新写入。
- **实时扫描的一致性。** 文件读取自在线磁盘（没有 VSS）。撕裂读取会被检测并重试，被锁定的文件会被跳过并报告，但一组相关文件可能来自略有不同的时刻。
- **元数据保真度。** NTFS ACL、备用数据流、所有者、EFS 和硬链接关系不会被保留；恢复出的文件采用目标位置的权限。会恢复修改时间和常用的属性位。
- **权限。** 服务以启动它的账户运行。请使用能读取备份源、写入仓库和恢复目录的最小权限来运行。尚未实现独立的高权限 worker。
- **Everything 实例。** 适配器无法知道 Everything 绑定在哪里。请把它的"绑定到接口"选项保持为 `127.0.0.1`，关闭"允许文件下载"，并设置用户名和密码。
- **备份源路径检查。** 拒绝网络共享的检查只看输入文本开头是否为 `\\`。`//host/share` 和 `\\?\UNC\host\share` 不会被识别，所以添加这样的备份源时，服务会去连接该 SMB 服务器（并发送 Windows 凭据）。只有管理员可以添加监控文件夹；请使用本地盘符路径。
- **恢复的计划与执行。** 确认针对的是预览时的计划，但恢复任务运行时会重新生成计划，并不会与已批准的计划比较。任务排队期间出现在目标位置的文件，可能在 `overwrite` 策略下被替换而无需再次确认；`create` 和 `rename` 项目用无条件的重命名发布，所以同时向同一个文件夹进行两次恢复可能互相替换对方的文件。请不要同时向同一个文件夹运行多个恢复。
- **恢复目录是受信任的存储。** 恢复根目录在每一步都是按路径解析的，因此在校验与使用之间被替换并不会被发现；暂存的 `.tvpart-*` 文件按句柄校验，却按路径发布；已有目标在被替换之前会先清除其属性，所以被人放在那里、指向其他文件的硬链接，会改变那个文件的属性。能写入恢复目录的人本来就能修改恢复出来的文件，所以请收紧它的权限。
- **开发模式。** 设置 `TIMEVAULT_AUTH_DISABLED=true` 时每个人都是本地管理员，并且没有 Host 头检查，所以使用 DNS rebinding 的恶意网页理论上可以从运行该服务的人的浏览器访问它（未经测试）。不要在会浏览不可信网站的计算机上使用该模式；请使用登录。
- **自动备份。** 没有版本数上限时，发现变化的自动运行会永久增加恢复点。无法读取的计划文件夹每个间隔产生一个失败任务和一条审计记录。没有发现变化的自动运行，是按它无法读取的项目数量来判断的，而不是按具体是哪些项目。开启 Everything 探测（默认关闭）后，当 Everything 的索引说没有变化时会跳过扫描，所以 Everything 尚未看到的变化会在下一次没有被跳过的扫描时被发现，最晚在 `TIMEVAULT_SCHEDULER_FULL_SCAN_EVERY` 之后。
- **发布文件夹决定了服务器上运行什么（0.1.8）。** 设置了 `TIMEVAULT_UPDATE_URL` 之后，谁能写入发布文件夹（或其共享），或者能坐在通往某个 `http` 地址的网络路径上，谁就能让服务以服务账号的权限运行任何程序：该账号能读取每个监控文件夹，并写入仓库和恢复文件夹。没有签名；清单中的大小和 sha256 与程序来自同一个地方，所以它们只能防止文件损坏或只复制了一半，防不住能同时写这两样的人。下载的程序在安装之前会被运行两次（`version`、`check-config`），所以恶意的发布在这时就已经以服务账号的身份运行了。请只让管理员能写入发布文件夹，地址使用 `https`，让服务以所需的最小权限运行（程序所在的文件夹必须对它可写，这是这个功能的代价），在不能接受这一点的地方根本不要设置该地址。可以在不改动其余部分的情况下给清单加上签名（[ADR 0014](./adr/0014-self-update-from-a-release-manifest.md)）。
- **更新会自己应用迁移（0.1.8）。** 会自己更新的服务需要 `TIMEVAULT_AUTO_MIGRATE=true`，所以新发布会在没有人运行 `migrate` 的情况下修改数据库；没有自动回退，较旧的程序在已迁移的数据库上也未必安全（见各版本的升级说明）。旧程序会被保留（`timevault.old-<版本>.exe`），用于手工回退。
- **启动器保持它被启动时的代码（0.1.8）。** 在 `supervise` 模式下，被启动的进程作为小型启动器保留；更新替换的是磁盘上的文件和它启动的程序，而不是启动器，它没有网络或数据库代码，但在被手工重启之前也得不到修复。
- **账号头像是另一个应用的文件（0.1.8）。** 谁能在审计日志、任务页或人员列表中看到某个名称，谁就能看到另一个应用为该工号保存的头像；TimeVault 不对头像做访问控制。TimeVault 不存储其中任何内容，也从不自己提供它们。

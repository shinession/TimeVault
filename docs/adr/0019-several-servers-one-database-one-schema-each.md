# English

## Status

Accepted on 2026-11-22 as a design, and amended the same day with two decisions: the live view and the actions happen on the server the person is signed in to, and the first server can be moved into a schema of its own with one command. **Step 1 is built (version 1.1.0); steps 2 and 3 are not:** each step is a release with its own tests and documentation, and "What step 1 built" below says what was built and where it differs from the plan. It builds on [0017](./0017-site-settings-in-the-database.md) (settings per server) and [0018](./0018-native-ntfs-index-replaces-everything.md) (the index that answers "what is on the disk now"), and it extends the one-server-one-database model of [0001](./0001-recovery-point-history-model.md) and [0006](./0006-settings-in-env-and-database-and-scheduled-backups.md).

## Context

- Several file servers each run TimeVault. They are on one intranet and already share the PostgreSQL server and the Redis of the company accounts. People often have to search and compare across servers, and today they have to open each server on its own.
- Each server keeps its content in a repository on its own disk. The owner wants that to stay so: no file content moves between servers, so a server's performance is not touched by what people do on another one.
- Permissions are decided for each monitored folder ([0013](./0013-per-folder-access-levels.md)) and are the same on every server because the accounts are shared. The display folder of a monitored folder (`\\server\share\folder`) names its server, so it never repeats.
- Today one database is one server. The code relies on it: `sources.name` and `sources.root_key` are unique in the whole table; `objects` is keyed by the SHA-256 alone, although each repository is its own; the start-up recovery marks **every** running job as failed and the job runner takes **any** queued job; the scheduler asks for every due folder; and the Site settings ([0017](./0017-site-settings-in-the-database.md)) hold `server_host`, which must differ on every server. The service lock and the lock of each folder's backup, on the other hand, already include `current_schema()` in their key, and the tests already run each in a private schema.
- There is no way for one server to call another: the API knows only a session cookie and a CSRF token.
- The database already has a primary and a replica and is backed up, by the people who run it. That is not a concern of this project.

## Decision

- **One database for the group, one schema for each server.** A server's tables live in its own schema, chosen with `search_path` in `TIMEVAULT_DATABASE_URL` (a URL parameter that pgx passes on to PostgreSQL). The first server keeps the schema it has now (`public`, unless its owner chose another), and the registry holds the schema name, so a server in `public` is a server like any other; its owner can move it into a schema of its own with one command (below), and nothing moves by itself. A server that has no group settings runs exactly as today. The servers do not share tables, so nothing in the write path of a backup, a restore or a job changes: each server's jobs, objects, recovery points, audit events and Site settings stay its own, and each server can be dumped, restored or dropped on its own.
- **Moving the first server out of `public` is one explicit command, never something start-up does.** A server that migrates against an existing but empty schema (at start-up with `TIMEVAULT_AUTO_MIGRATE=true`, which self-update needs, or with `timevault-server migrate`) creates a new, empty catalog there (checked, see the consequences), so a start-up that moved tables by itself would take the tables of the first server from under it as soon as a second server starts. The command is `timevault-server move-schema --to <schema>` (`--from` is the schema the URL selects, `public` when it has no `search_path`). In one transaction it moves the tables of the migrations and `schema_migrations`, with their indexes, identity sequences and constraints, and the function of the audit log, with `ALTER TABLE ... SET SCHEMA` and `ALTER FUNCTION ... SET SCHEMA`. It shows what it would do and changes nothing without `--apply`. It takes the service lock of the schema it moves from and refuses to run while a service holds it; it refuses when that schema does not hold a whole catalog, or when the target already holds a table of TimeVault; it checks that the database account owns what it moves and may use the target (it creates the schema itself when the account may create schemas; otherwise the database administrator creates the empty schema once, `CREATE SCHEMA <name> AUTHORIZATION <account>`, and the command does the rest); and afterwards it checks that nothing was left behind and that the version table is read from the target. It prints the `search_path` to add to `TIMEVAULT_DATABASE_URL`. The order is: stop the service, run the command, change the URL, start the service; the preview of the command says which schema holds the catalog and at which version (`timevault-server check-config` stays offline, as it must: the updater runs it before it replaces the program). The same command with `--from` and `--to` swapped moves everything back. A test compares the list of what it moves with what the migrations create, so a new migration cannot be forgotten. It is part of step 1.
- **A registry of the servers.** One schema, `timevault_cluster`, has a table of servers (`servers`): the name (unique, short, in URLs), the schema, the address at which the other servers call it, its public key, its version, the number of the read contract (below), the id of its repository, its folders for backups and restores (only to hide them in texts, and only administrators see them), and when it was last heard of. An administrator registers a server (a command of `timevault-server`, run with a database account that may write the registry); a server itself only reports that it is alive and which version it is, and cannot change its own key or another row.
- **The repository never leaves its server.** No endpoint returns file content. A restore is previewed and run **only by the server that owns the folder**, into that server's restore folder; the person takes the files from that server's share. There is no restore to another server.
- **What comes from the database and what from the owner.** *From the database, by whichever server the person is on:* the list of folders of all servers, the Time Machine, the versions of a file, the list of backups and jobs and their progress, the audit log, and the comparison of what was backed up. *From the owner, by its API:* the folder as it is on the disk now (the Explorer, its protected / changed / new markers and folder sizes), the search of current files, whether the content of a version is really in the repository, and everything that does something (back up now, verify, cancel, restore preview and restore, the settings and the permissions of a folder). A server that is offline still has its history browsed from the database.
- **Where the person works.** Everything happens in the pages of the server the person is signed in to. Its Explorer, Time Machine, search, Backups and Jobs pages list the folders of all the servers, and for the live part (the Explorer, the sizes, the search) and for every action it calls the owner's API with the employee ID of the person; the owner does the work and answers. There is no "open it on the other server" link and no second sign-in. When the owner is offline, the page says so for what needs it (below). The one exception is the local administrator of a server, which is never forwarded (see Permissions).
- **Reading another server's history.** A server opens, on first use, a small read-only pool for each other server (2 to 4 connections, `search_path` set to that server's schema, `default_transaction_read_only` on, a statement timeout), and the existing read queries of the catalog, the jobs and the audit log run on it. The schema name comes from the registry and is checked as an identifier. A database role for each server that can write its own schema and only read the others is recommended, and a script and the grants are documented, but the group also works with one role for all (then without that protection). A server never writes into another server's schema.
- **A read contract.** The registry holds a contract number for each server. Within a contract, migrations only add (columns, tables, never rename or drop); a change that breaks that raises the number. A server reads only the servers whose contract it knows, and shows the others as "version not compatible" instead of failing, so servers that update themselves one after another never break each other's pages.
- **Addressing.** A folder, a job or a recovery point of this server is addressed as now (`source_id=5`), so every existing address, API call and script keeps working. One of another server is addressed by the name of the server and the id (an optional `server` next to the id; the answers say which `server` an item belongs to). The display folder is for people to read; it can be edited, so it is not a key.
- **Permissions stay as they are.** The grants of a folder live in its owner's schema and the accounts in the shared Redis. The server that the person is on reads the grants of the other servers' folders to decide what is listed (a folder that may not be browsed is "not found", as in [0013](./0013-per-folder-access-levels.md)), and the owner checks again on every call it receives. An `admin` account of the user directory has the same reach on other servers' folders as on its own. **The local administrator of a server is local to it:** it is never forwarded to another server. It sees the live view of its own server only; on another server's folder it can only read the history (from the database), with no live view, no search and no action (decided by the owner on 2026-11-22). Whoever needs more signs in with a company account, or goes to that server's own page. A server's Site settings are changed on that server only.
- **The server-to-server API.** It is `/api/cluster/v1`, kept apart from the API of the people, for servers of the group only. Every server has an Ed25519 key pair (the private key in its `.env`, the public key in the registry). A request is signed with the method, the address, a hash of the body, the time, a one-time number, the caller and the server it is for, and carries the employee ID of the person it is for. The receiver checks the signature against the registry, refuses an old or repeated request, looks the account up in Redis itself (it does not trust a role that was sent), and applies the level of that person on that folder, and the audit log records the person and the server that called. The endpoints are few: the live listing and its sizes, the search, the check of a version's content, the restore preview and start, back up, verify, cancel, and the settings of a folder. They are for the intranet only; whether the traffic must be encrypted (it carries names, sizes and employee IDs, never content) is decided in step 2. An owner serves only a limited number of calls from other servers at the same time, so that what people do on one server cannot slow another one down.
- **Search.** The search of current files goes to every server that is online, in parallel, each answering from its own in-memory index within a time limit; the answer is shown by server with a page for each, and says which servers did not answer in time. A search of names in the history (to find a file that was deleted) is a different feature that does not exist yet and is not part of this decision.
- **Compare.** Two folders, or two points in time, are compared in the catalog by name, size, modification time and SHA-256, which says that the **backed-up** content is the same or differs; this works for any servers because the hashes are in the database. A live listing has no hashes, so the current disk is compared by size and time only. There is no comparison of the contents of files.
- **The entry.** Every server can show all the servers, because every server reads the registry and the other schemas. The people are given one address, an alias for one of them, and the others stay reachable. A session belongs to the server that made it; **the servers do not share the session key**, because with it a server that is broken into could forge the local administrator of every other. The company single sign-on makes the step to another server one click.
- **When a server is offline,** that is, it has not reported for about two minutes, its history is browsed as usual, and the live view, the search and every action say "server offline". No request waits longer than the limits of the other calls (2 to 3 seconds).

## Steps (step 1 built in 1.1.0; steps 2 and 3 planned)

1. **A read-only view of all the servers.** The registry and the heartbeat, the schemas and the roles with their documentation, the read pools and the contract, the `move-schema` command, an "All servers" page, the Time Machine, the versions, the backups and jobs and the audit log for the folders of other servers, and the display of other servers' texts without their real folders. The folders of other servers are listed and their history is browsed in this server's pages; their live Explorer, search and actions say that they come with the next steps (a note, not a link). A version's content is shown as "recorded" (what the `objects` table says) and not as checked. A standalone server is unchanged.
2. **The live part, in the pages of the server the person is on.** The signed server-to-server API for the live listing, the folder sizes, the check of a version's content and the search of current files; the Explorer, the sizes, the search and the comparison of other servers' folders in this server's pages; the decision about encrypting the traffic.
3. **The actions.** Restore preview and restore, back up now, verify, cancel, and the changes of a folder's settings and permissions, offered in the pages of the server the person is on and sent to the owner, which runs them as if the person had made them on its own page. The progress is read from the database like any other job.

## What step 1 built (version 1.1.0)

The decisions above stand. Where the build made a choice that the plan left open, or differs from it:

- **Names.** The table of the register is `servers` and the address parameter is `server` (not `node`: the catalog already has a `nodes` table, for the entries of the file tree). A server finds itself in the register by its own schema, so there is no setting for the name of a server and nothing new in `.env`. The page that lists the servers is called **Servers** (the plan called it "All servers").
- **The register has fewer columns than planned:** `name`, `schema`, `version`, `contract`, `repository_id`, the repository and restore folders and the network path of the restore folder, `registered_at`, `registered_by` and `last_seen`. The address and the public key for the server-to-server API come with step 2, as a migration of the register that only adds columns.
- **The register is made and filled by `timevault-server cluster register <name>`** (with `list` and `remove`), run on each server; the server joins the group when it next starts. A register that cannot be read is told in the log and the server runs on its own.
- **A report every 30 seconds,** by the clock of the database: online within 2 minutes, then offline; a server that never reported (`waiting`) or reports another contract (`incompatible`) is not read.
- **Permissions on another server:** the grants of its folders as stored in its schema, for the account that the visitor is in the user directory; `admin` accounts have full reach, and the local administrator may only browse (and sees no real folder). Everything is read-only in this version.
- **Pages and API.** The `server` parameter is accepted by the Time Machine (also as `source=<server>:<number>`), the versions, Backups, job and Audit pages and by the read endpoints of the API; the Servers page and `GET /api/v1/servers` are new. Everything that changes something, the live view and the search refuse a request that names another server with `501`.
- **A version's content is "recorded"** (`content_checked: false` in the API): the catalog says that the object exists (`node_versions` refers to `objects` by a foreign key), and nobody looks at the repository of the other server.
- **The read side needs nine tables** (listed in the runbook); a test checks that the grants for them are enough for every read of the pages and give nothing more.
- **`move-schema`** also changes the register entry of the server. `check-config` stays offline (the updater runs it before it replaces the program) and does not report the schema; the preview of `move-schema` does.
- **Not built, as planned:** the signed server-to-server API, the live view, the search and the comparison across servers (step 2), the actions (step 3), and protection of the rows of the register one by one.

## Alternatives considered

- **All servers in one schema, with a column that says which server owns a row.** It is the simplest picture, and a query across servers is one query. But it would put the owning server into every constraint, the object table, the job queue, the recovery, the scheduler, the counts and the Site settings; a server that has not been updated yet would see and treat the rows of the others; and a bug in one server could damage the data of all. The per-schema model leaves the write path as it is and keeps the groups' queries possible (the schemas are in one database).
- **A central repository that every server uploads to (agents).** One catalog and one place for the content, but it moves every file over the network, makes the center a single point of failure and a bottleneck, and gives up that each server works alone. The owner asked for the content to stay local.
- **An entry that only forwards pages (a reverse proxy, with a portal page).** It needs no code and is the first thing to try, but it cannot search, list or compare across servers, which is what people asked for.
- **The browser calls every server and puts the answers together.** It needs the content security policy and the cookies to be opened to other hosts and keeps a session for each host in the browser; the servers should combine the answers, not the browser.
- **All servers share one session key (one login for all).** A session of the local administrator is not looked up in Redis, so a server that is broken into could forge the local administrator of the others, who may change the update address and so run any program. Not chosen.
- **Commands to another server through a table in the database (an inbox) instead of the API.** It is durable and needs no authentication between servers for the actions. It was not chosen to keep one way to do things, as the owner described it (the API); it can be reconsidered for the actions if the API proves fragile. The progress of a job is read from the database in both cases.
- **The live view and the actions only on the owner's own page, with a link from the other servers.** The simplest to build (no server-to-server API), and the first release could have it. But the person would have to change address at every step, could not search or compare across servers on one page, and would depend on the single sign-on at each step. The owner chose to work on the server the person is signed in to.
- **Moving the first server by itself when it starts with a `search_path` of its own.** It would be automatic, but a second server started against a new, empty schema would take the tables of the first server from under it, and a mistake in the URL would move a running system. A command with a preview, the service lock and the checks is as short for the person and cannot be set off by accident.
- **A set of views for each server as the contract of the read side.** It would let a server change its tables freely. It is more to maintain than a number and the rule "migrations only add"; it can be added if that rule proves too tight.
- **Merging into one database by copying the old databases.** Not needed: today there is one server, which becomes the first.

## Consequences

- The database is shared by all the servers: it must be sized for them (connections: each server's pool is at least 16, so `max_connections`, or a pooler, has to allow all of them, and the read pools added to that), and if it is down, no server can back up. Its availability and backup are those of the primary and replica that the owner runs; this project does not add to them.
- A server that is broken into, and the role it uses, can read the names, sizes, times and hashes of every server (not the content), and, if the roles are not separated, change them. The separate roles are recommended for that reason. The servers form one trust domain; the Redis and the database already were.
- The processes that run elevated now also receive calls from other servers. The server-to-server API is kept small, signed, intranet-only and read-or-controlled; it never returns file content.
- The updates of the servers are independent, so the rule "migrations only add inside a contract" has to be kept; a change that cannot be additive raises the contract number and is rolled out to all servers.
- A comparison of content is not possible, and a comparison of the live disks is by size and time only.
- The clocks of the servers must agree (NTP): "all the servers as of 10:00" is made from the commit times of the recovery points.
- The history of a folder cannot move to another server, because the content would have to be copied: a server that is retired has to keep its repository for as long as its history must stay restorable.
- Every list shows the server next to the folder, and the audit log, the jobs and the Backups page show their origin.
- The Site settings stay per server ([0017](./0017-site-settings-in-the-database.md)): the settings that are meant to be the same everywhere (`sso_host`, `update_url`, `trusted_proxies`) are entered on each server. A group-wide scope for them can follow.
- The live view and the actions of another server's folders pass through the server the person is on, so they take two hops and are as fast as the owner is; the time limits, the "server offline" notice and the owner's limit on the calls it serves for other servers keep that bounded.
- Moving the first server was tried on 2026-11-22 on a scratch database (PostgreSQL 18.7, 12 tables, about 3 million rows). The move took about 6 ms, because only catalog entries change and no row is copied; a move that was rolled back left everything in place; after the move the counts, the identity numbering, the append-only trigger, the foreign keys and the unique keys behaved as before, the same statements in the other direction moved everything back, and the migration step of the service recognised the catalog ("database schema is up to date"). That step, pointed at a schema that does not exist, fails ("no schema has been selected to create in"); pointed at an existing empty schema it creates a new, empty catalog and leaves the old data where it was, which is why the move is a command and not a step of start-up.
- What the move leaves to the database administrator: PostgreSQL runs the foreign-key checks as the owner of the table, so the owner must be able to use the new schema, or they fail with "permission denied for schema" (the command checks that); grants on the tables travel with them, but a role that has them also needs `USAGE` on the new schema; and anything outside TimeVault that reads the tables as `public.<table>` (reports, scripts) has to be changed.
- The documentation, the changelog and the tests are written step by step, as each step is built: the runbook, the API and the other documents describe step 1 (1.1.0) now, and steps 2 and 3 when they are built.

# 中文

## 状态

于 2026-11-22 作为设计被接受，并在当天补充了两项决定：实时视图和各种操作都在用户当前登录的那台服务器上进行；第一台服务器可以用一个命令搬进它自己的 schema。**第 1 步已经建成（1.1.0 版），第 2、3 步还没有：** 每一步作为一个版本发布，并带有自己的测试和文档；下面的"第 1 步建成了什么"说明建成了什么，以及与计划有何不同。它建立在 [0017](./0017-site-settings-in-the-database.md)（每台服务器各自的设置）和 [0018](./0018-native-ntfs-index-replaces-everything.md)（回答"磁盘上现在有什么"的索引）之上，并扩展了 [0001](./0001-recovery-point-history-model.md) 和 [0006](./0006-settings-in-env-and-database-and-scheduled-backups.md) 中"一台服务器对应一个数据库"的模型。

## 背景

- 有几台文件服务器，各自运行 TimeVault。它们在同一个内网，并且已经共用同一个 PostgreSQL 服务器和公司账号所用的 Redis。人们经常要跨服务器搜索和对比，而现在只能分别打开每一台。
- 每台服务器把内容保存在它自己磁盘上的仓库中。所有者希望保持这一点：文件内容不在服务器之间移动，所以一台服务器的性能不会受到人们在另一台上所做操作的影响。
- 权限按每个监控文件夹决定（[0013](./0013-per-folder-access-levels.md)），而且由于账号是共用的，在每台服务器上都一样。监控文件夹的显示文件夹（`\\server\share\folder`）带有服务器名，所以不会重复。
- 今天一个数据库就是一台服务器，代码依赖了这一点：`sources.name` 和 `sources.root_key` 在整张表中唯一；`objects` 只以 SHA-256 为键，尽管每个仓库是独立的；启动恢复会把**每一个**运行中的任务标成失败，任务运行器会领取**任何**排队的任务；调度器会查询每一个到期的文件夹；站点设置（[0017](./0017-site-settings-in-the-database.md)）里有 `server_host`，它在每台服务器上必须不同。另一方面，服务锁和每个文件夹备份的锁，它们的键里已经包含了 `current_schema()`，测试也已经各自在一个私有 schema 中运行。
- 一台服务器无法调用另一台：API 只认会话 Cookie 和 CSRF 令牌。
- 这个数据库已经有主库和从库，并且由运行它的人负责备份。这不是本项目要考虑的事。

## 决定

- **整个组共用一个数据库，每台服务器一个 schema。** 一台服务器的表在它自己的 schema 中，用 `TIMEVAULT_DATABASE_URL` 里的 `search_path` 指定（这是 pgx 会传给 PostgreSQL 的 URL 参数）。第一台服务器保留它现在所用的 schema（`public`，除非所有者选了别的），登记表里记着 schema 名，所以放在 `public` 里的服务器和其他服务器没有区别；它的所有者可以用一个命令（见下）把它搬进自己的 schema，不会有任何东西自己移动。没有组设置的服务器，运行方式与今天完全一样。服务器之间不共用表，所以备份、恢复和任务的写入路径中没有任何东西要改：每台服务器的任务、对象、恢复点、审计事件和站点设置仍然各是各的，每台都可以单独导出、恢复或删除。
- **把第一台服务器搬出 `public`，是一个明确的命令，绝不是启动时做的事。** 一台服务器如果对一个已存在但为空的 schema 执行迁移（启动时设了 `TIMEVAULT_AUTO_MIGRATE=true`，自更新需要它；或者运行 `timevault-server migrate`），会在那里建立一个新的空目录库（已验证，见"影响"），所以如果启动时自己搬表，第二台服务器一启动，就会把第一台服务器的表从它脚下抽走。命令是 `timevault-server move-schema --to <schema>`（`--from` 是 URL 所选的 schema，URL 里没有 `search_path` 时就是 `public`）。它在一个事务里，用 `ALTER TABLE ... SET SCHEMA` 和 `ALTER FUNCTION ... SET SCHEMA`，把迁移所建立的表和 `schema_migrations`（连同它们的索引、自增序列和约束）以及审计日志的那个函数搬走。它先显示将要做什么，没有 `--apply` 就什么都不改。它会取得被搬出 schema 的服务锁，有服务在运行时拒绝执行；如果那个 schema 里没有完整的目录库，或者目标里已经有 TimeVault 的表，它也拒绝；它会检查数据库账号拥有要搬的对象并且可以使用目标（账号可以创建 schema 时它自己创建；否则由数据库管理员事先一次性创建空 schema：`CREATE SCHEMA <名称> AUTHORIZATION <账号>`，其余由命令完成）；搬完之后还会检查没有东西遗留，并且能从目标读到版本表。它会打印要加到 `TIMEVAULT_DATABASE_URL` 里的 `search_path`。顺序是：停止服务、运行命令、修改 URL、启动服务；命令的预览会说明哪个 schema 里有目录库、是什么版本（`timevault-server check-config` 保持离线，必须如此：更新程序在替换程序之前要运行它）。同一个命令把 `--from` 和 `--to` 对调，就能把一切搬回去。有一个测试会把它要搬的清单和迁移所建立的对象相比较，所以新增的迁移不会被漏掉。它属于第 1 步。
- **服务器登记表。** 一个 schema，`timevault_cluster`，里面有一张服务器表（`servers`）：名称（唯一、简短、出现在 URL 中）、schema、其他服务器调用它所用的地址、它的公钥、它的版本、读取契约的编号（见下）、它的仓库 id、它用于备份和恢复的文件夹（只用来在文本中隐藏它们，并且只有管理员能看到），以及最近一次有它的消息的时间。由管理员登记一台服务器（`timevault-server` 的一个命令，用可以写入登记表的数据库账号运行）；服务器自己只报告它还活着以及它是什么版本，不能修改自己的密钥，也不能修改别的行。
- **仓库永不离开它的服务器。** 没有任何接口返回文件内容。恢复**只由拥有该文件夹的服务器**预览和执行，写入那台服务器自己的恢复文件夹；人们从那台服务器的共享里取文件。不支持恢复到另一台服务器。
- **哪些来自数据库，哪些来自拥有者。** *来自数据库，由用户所在的那台服务器读取：* 所有服务器的文件夹列表、时间机器、文件的各个版本、备份和任务的列表及其进度、审计日志，以及对已备份内容的对比。*来自拥有者，通过它的 API：* 文件夹在磁盘上现在的样子（文件浏览、已保护/已变更/新增的标记和文件夹大小）、当前文件的搜索、某个版本的内容是否真的在仓库中，以及一切会做点什么的操作（立即备份、校验、取消、恢复预览和恢复、文件夹的设置和权限）。一台服务器离线时，它的历史仍然可以从数据库中浏览。
- **人在哪里工作。** 一切都在用户登录的那台服务器的页面里进行。它的文件浏览、时间机器、搜索、备份和任务页面列出所有服务器的文件夹；对于实时的部分（文件浏览、大小、搜索）和每个操作，它带着这个人的工号调用拥有者的 API，由拥有者去做并回答。没有"到另一台服务器上打开"的链接，也没有第二次登录。拥有者离线时，需要它的部分会如此提示（见下）。唯一的例外是一台服务器的本地管理员，它从不被转发（见权限）。
- **读取另一台服务器的历史。** 一台服务器在第一次用到时，为每一台其他服务器打开一个小的只读连接池（2 到 4 个连接，`search_path` 设为那台服务器的 schema，开启 `default_transaction_read_only`，带语句超时），目录库、任务和审计日志现有的读取查询在它上面运行。schema 名取自登记表，并按标识符检查。建议为每台服务器配一个数据库角色，对自己的 schema 可写、对其他的只读，并会写明脚本和授权；但整个组用同一个角色也能工作（这时就没有这层保护）。服务器从不写入另一台服务器的 schema。
- **读取契约。** 登记表为每台服务器保存一个契约编号。在同一个契约之内，迁移只增不减（只加列、加表，从不重命名或删除）；破坏这一点的改动会提高编号。一台服务器只读取它认识的契约的服务器，把其余的显示为"版本不兼容"，而不是出错，这样一台接一台自己更新的服务器，就不会弄坏彼此的页面。
- **编号。** 本服务器的文件夹、任务或恢复点，仍按现在的方式编号（`source_id=5`），所以现有的每个地址、API 调用和脚本都继续可用。另一台服务器的，用服务器名加编号（编号旁边多一个可选的 `server`；应答会说明某一项属于哪个 `server`）。显示文件夹是给人看的；它可以被编辑，所以不能当作键。
- **权限保持原样。** 文件夹的授权保存在拥有者的 schema 中，账号保存在共用的 Redis 中。用户所在的那台服务器读取其他服务器上文件夹的授权，以决定列出什么（不能浏览的文件夹是"未找到"，与 [0013](./0013-per-folder-access-levels.md) 一样），而拥有者对它收到的每次调用再检查一遍。用户目录中的 `admin` 账号，在其他服务器的文件夹上拥有与在自己服务器上相同的范围。**一台服务器的本地管理员只属于它自己：** 它永远不会被转发给另一台服务器。它只能看到自己所在服务器的实时视图；在另一台服务器的文件夹上，它只能读取历史（从数据库），没有实时浏览、搜索和任何操作（所有者于 2026-11-22 决定）。需要更多权限的人，用公司账号登录，或者用那台服务器自己的页面。一台服务器的站点设置只在那台服务器上修改。
- **服务器之间的 API。** 它是 `/api/cluster/v1`，与给人使用的 API 分开，只供组内的服务器使用。每台服务器有一对 Ed25519 密钥（私钥在它的 `.env` 中，公钥在登记表中）。请求会连同方法、地址、请求体的哈希、时间、一次性的随机数、调用者和目标服务器一起签名，并带有这次请求所代表的那个人的工号。接收方用登记表核对签名，拒绝过旧或重复的请求，自己到 Redis 查这个账号（不信任发来的角色），并应用这个人在该文件夹上的级别，审计日志会记录这个人和发起调用的服务器。接口很少：实时列表及其大小、搜索、版本内容的检查、恢复预览和启动、备份、校验、取消，以及文件夹的设置。它们只供内网使用；流量是否必须加密（它带有名称、大小和工号，绝不带内容）在第 2 步决定。拥有者同一时间只为其他服务器处理有限数量的调用，这样人们在一台服务器上的操作就不会拖慢另一台。
- **搜索。** 当前文件的搜索会并行发往每一台在线的服务器，各自在限定时间内用自己的内存索引回答；结果按服务器分别显示，每台各有自己的分页，并说明哪些服务器没有在时间内应答。在历史中搜索名称（为了找到已删除的文件）是另一个功能，目前还不存在，不属于本决定。
- **对比。** 两个文件夹，或同一文件夹的两个时间点，在目录库中按名称、大小、修改时间和 SHA-256 对比，由此说明**已备份**的内容相同还是不同；因为哈希都在数据库里，这对任何服务器都适用。实时列表没有哈希，所以对当前磁盘只按大小和时间对比。不提供文件内容的对比。
- **入口。** 每台服务器都能显示所有服务器，因为每台都读取登记表和其他 schema。给人们的是一个地址，即其中一台的别名，其他的仍然可以访问。会话属于创建它的那台服务器；**各服务器不共用会话密钥**，因为有了它，一台被攻破的服务器就能伪造其他每一台的本地管理员。公司单点登录让跳转到另一台服务器只需点一下。
- **服务器离线时，** 也就是大约两分钟没有报告，它的历史照常浏览，而实时视图、搜索和每个操作都会说"服务器离线"。任何请求等待的时间都不会超过其他调用的限制（2 到 3 秒）。

## 步骤（第 1 步已在 1.1.0 中建成；第 2、3 步为计划）

1. **所有服务器的只读视图。** 登记表和心跳、schema 和角色及其文档、只读连接池和契约、`move-schema` 命令、"所有服务器"页面，以及其他服务器的文件夹所对应的时间机器、版本、备份和任务、审计日志，并在文本中显示其他服务器的内容时隐藏它们的真实文件夹。其他服务器的文件夹出现在列表里，它们的历史在本服务器的页面里浏览；它们的实时文件浏览、搜索和各种操作，提示将随后续步骤提供（一条说明，而不是链接）。版本的内容显示为"已记录"（`objects` 表所说的），而不是"已检查"。独立运行的服务器不受影响。
2. **实时部分，在用户所在服务器的页面里。** 用于实时列表、文件夹大小、版本内容检查和当前文件搜索的、带签名的服务器间 API；在本服务器的页面里对其他服务器的文件夹进行文件浏览、查看大小、搜索和对比；关于流量是否加密的决定。
3. **操作。** 恢复预览和恢复、立即备份、校验、取消，以及对文件夹设置和权限的修改，在用户所在服务器的页面里提供，并发送给拥有者，由它像这个人在它自己的页面上操作那样执行。进度像任何其他任务一样，从数据库读取。

## 第 1 步建成了什么（1.1.0 版）

上面的决定依然有效。建设过程中，计划留着没定的地方做了哪些选择，以及与计划有何不同：

- **名称。** 登记表的表名是 `servers`，地址参数是 `server`（不用 `node`：目录库里已经有一张 `nodes` 表，用于文件树的条目）。一台服务器用它自己的 schema 在登记表里找到自己，所以没有设置服务器名称的配置项，`.env` 里也没有任何新增。列出各服务器的页面叫**服务器**（计划里叫"所有服务器"）。
- **登记表的列比计划的少：** `name`、`schema`、`version`、`contract`、`repository_id`、仓库文件夹和恢复文件夹以及恢复文件夹的网络路径、`registered_at`、`registered_by` 和 `last_seen`。服务器间 API 所需的地址和公钥，随第 2 步而来，作为登记表的一个只增加列的迁移。
- **登记表由 `timevault-server cluster register <名称>` 建立和填写**（还有 `list` 和 `remove`），在每台服务器上运行；服务器在下次启动时加入组。读不了登记表时会写进日志，服务器独自运行。
- **每 30 秒报告一次，** 按数据库的时钟：2 分钟之内是在线，之后是离线；从未报告（`waiting`）或报告了另一个契约（`incompatible`）的服务器不会被读取。
- **在另一台服务器上的权限：** 按那台服务器 schema 中保存的文件夹授权，针对访问者在用户目录中的账号；`admin` 账号有完全的权限，本地管理员只能浏览（并且看不到任何真实文件夹）。这个版本里一切都是只读的。
- **页面和 API。** 时间机器（也可以写成 `source=<服务器>:<编号>`）、版本页、备份页、任务页和审计页，以及 API 的读取接口，都接受 `server` 参数；服务器页和 `GET /api/v1/servers` 是新增的。凡是会改变东西的操作、实时视图和搜索，对指明另一台服务器的请求都以 `501` 拒绝。
- **版本的内容是"已记录"**（API 中是 `content_checked: false`）：目录库说明这个对象存在（`node_versions` 通过外键引用 `objects`），没有人去查看另一台服务器的仓库。
- **读取一侧需要九张表**（运维手册里列出了）；有一个测试检查针对它们的授权足够支持页面的每一次读取，并且不多给任何权限。
- **`move-schema`** 也会修改这台服务器在登记表里的条目。`check-config` 保持离线（更新程序在替换程序之前要运行它），不报告 schema；`move-schema` 的预览会报告。
- **按计划没有建设的：** 带签名的服务器间 API、实时视图、搜索和跨服务器的对比（第 2 步），操作（第 3 步），以及对登记表各行的逐行保护。

## 考虑过的备选方案

- **所有服务器放在同一个 schema 中，用一列说明某行属于哪台服务器。** 这是最简单的图景，跨服务器的查询就是一条查询。但这会把"所属服务器"放进每个约束、对象表、任务队列、恢复、调度器、各种计数和站点设置里；还没有更新的服务器会看到并处理别的服务器的行；而且一台服务器的缺陷可能损坏所有服务器的数据。每台一个 schema 的模型保持写入路径不变，并且（因为这些 schema 在同一个数据库里）组内的联合查询仍然可行。
- **所有服务器都上传到一个中央仓库（agent）。** 一个目录库、一个存放内容的地方，但它要把每个文件都通过网络传输，让中心成为单点故障和瓶颈，并放弃了每台服务器可以独立工作的优点。所有者要求内容留在本地。
- **只转发页面的入口（反向代理加门户页）。** 不需要代码，是最先该试的东西，但它无法跨服务器搜索、列出或对比，而这正是人们提出的需求。
- **由浏览器调用每一台服务器并把答案拼在一起。** 这需要对其他主机放开内容安全策略和 Cookie，并在浏览器里为每台主机保留一个会话；把答案合并起来应该由服务器来做，而不是浏览器。
- **所有服务器共用一个会话密钥（一次登录通行所有服务器）。** 本地管理员的会话不会到 Redis 中查找，所以一台被攻破的服务器就能伪造其他服务器的本地管理员，而本地管理员能修改更新地址，从而运行任意程序。没有选择。
- **用数据库里的一张表（收件箱）代替 API，向另一台服务器发出命令。** 它是持久的，并且这些操作不需要服务器之间的认证。没有选择它，是为了只保留一种做事方式，也就是所有者所描述的（API）；如果 API 被证明脆弱，可以为这些操作重新考虑它。两种做法里，任务的进度都是从数据库读取。
- **实时视图和各种操作只放在拥有者自己的页面里，其他服务器只放一个链接。** 构建起来最简单（不需要服务器间 API），第一个版本就能有。但这样人每走一步都要换一次地址，无法在同一个页面上跨服务器搜索和对比，并且每一步都要依赖单点登录。所有者选择了在用户登录的那台服务器上工作。
- **第一台服务器在带着自己的 `search_path` 启动时自动搬家。** 这样是自动的，但第二台服务器一旦指向一个新的空 schema 启动，就会把第一台服务器的表从它脚下抽走，而且 URL 里的一个错误就会搬动一个正在运行的系统。带预览、服务锁和检查的命令，对人来说同样简短，而且不会被意外触发。
- **为每台服务器准备一组视图，作为读取侧的契约。** 它能让一台服务器自由改动自己的表。它比一个编号加上"迁移只增不减"的规则维护起来更多；如果那条规则被证明太紧，可以再加。
- **复制旧数据库、合并进一个数据库。** 不需要：今天只有一台服务器，它就成为第一台。

## 影响

- 数据库由所有服务器共用：它必须按它们来配置规格（连接数：每台服务器的连接池至少 16 个，所以 `max_connections` 或连接池代理要容得下所有服务器，再加上只读连接池），而且它一旦不可用，所有服务器都不能备份。它的可用性和备份由所有者运营的主库和从库负责，本项目不增加这方面的内容。
- 一台被攻破的服务器以及它所用的角色，可以读取每台服务器的名称、大小、时间和哈希（不是内容），如果角色没有分开，还可以修改它们。出于这个原因，建议使用分开的角色。这些服务器构成同一个信任域；Redis 和数据库原本就是如此。
- 以提升权限运行的进程，现在还会收到来自其他服务器的调用。服务器间 API 保持很小、带签名、只限内网，并且是只读或受控的；它从不返回文件内容。
- 各服务器的更新是独立的，所以"迁移在一个契约内只增不减"这条规则必须遵守；无法做到只增的改动，要提高契约编号，并在所有服务器上一起推行。
- 无法对比内容；对实时磁盘的对比只按大小和时间。
- 各服务器的时钟必须一致（NTP）："10:00 时所有服务器的状态"是用恢复点的提交时间得出的。
- 一个文件夹的历史不能搬到另一台服务器，因为那需要复制内容：退役的服务器，在它的历史还必须可以恢复的期间，要保留它的仓库。
- 每个列表都会在文件夹旁边显示服务器，审计日志、任务和备份页会显示它们来自哪里。
- 站点设置仍然是每台服务器各自的（[0017](./0017-site-settings-in-the-database.md)）：那些本来应该处处相同的设置（`sso_host`、`update_url`、`trusted_proxies`）要在每台服务器上分别填写。以后可以再为它们增加组范围。
- 另一台服务器的文件夹的实时视图和各种操作，要经过用户所在的那台服务器，所以多了一跳，速度取决于拥有者；上面的时间限制、"服务器离线"的提示，以及拥有者对其他服务器调用的数量限制，把这一点控制在范围之内。
- 搬动第一台服务器，已于 2026-11-22 在一个临时数据库上试过（PostgreSQL 18.7，12 张表，约 300 万行）。搬动大约用了 6 毫秒，因为只改目录项，不复制任何行；被回滚的搬动让一切原样不动；搬动之后，计数、自增编号、只追加的触发器、外键和唯一键的表现都和之前一样，同样的语句反方向执行能把一切搬回去，而且服务的迁移步骤认出了这个目录库（"database schema is up to date"）。这个步骤如果指向一个不存在的 schema，会失败（"no schema has been selected to create in"）；如果指向一个已存在的空 schema，它会在那里建立一个新的空目录库，原来的数据仍然留在原处——这就是为什么搬家是一个命令，而不是启动时的一个步骤。
- 搬动没有替数据库管理员做的事：PostgreSQL 以表的拥有者身份执行外键检查，所以拥有者必须能使用新的 schema，否则检查会以"permission denied for schema"失败（命令会检查这一点）；表上的授权会跟着表走，但拥有授权的角色还需要新 schema 的 `USAGE`；任何在 TimeVault 之外以 `public.<表名>` 读取这些表的东西（报表、脚本）都要修改。

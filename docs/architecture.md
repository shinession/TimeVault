# English

## Overview

TimeVault is one Go service, `timevault-server` (`cmd/timevault-server`), that hosts the web UI, the JSON API and the background workers. It keeps history in PostgreSQL and file content in a separate, content-addressed repository folder. It reads source folders; it never changes them. Anyone can browse the folders that let guests browse; company accounts from a Redis user directory sign in to do more, and what an account may do is decided for each monitored folder (version 0.1.7; see [ADR 0005](./adr/0005-redis-user-directory-and-open-browsing.md) and [ADR 0013](./adr/0013-per-folder-access-levels.md)). Since 1.0.1 it also keeps an index of the monitored folders in its own memory, built from the NTFS volume and kept up to date from the change journal of the volume (no search program is needed; see [ADR 0018](./adr/0018-native-ntfs-index-replaces-everything.md)), and its operating settings are in the database, edited by the local administrator only (see [ADR 0017](./adr/0017-site-settings-in-the-database.md)).

This document describes what is implemented. Items that plan.md describes but TimeVault does not do are listed in [mvp-status.md](./mvp-status.md).

## Data flow

**Backup.** A backup job takes the per-source advisory lock, discards anything an unfinished earlier build left behind, creates a `building` recovery point, walks the source folder by folder, copies new or changed files into the repository, writes the changes for each folder in one transaction, validates that every object it newly recorded still exists, flushes the repository folders to disk, and finally marks the point `committed` in a single update. Once that update is issued it is not abandoned: a cancellation that arrives later cannot turn a committed point into a failed job. Readers only ever query committed points, so a point that is being built, failed or was cancelled is never visible.

**Single instance.** Only one service may run against a database (schema). At start, before it recovers anything, the service takes a PostgreSQL advisory lock on a dedicated connection; a second service stops with "another TimeVault service is already running against this database". Without this, the second service's start-up recovery would mark the first one's running jobs as failed.

**Browse.** The Explorer lists the folder as it is on disk (through `os.Root`, so a crafted path cannot leave the source) and marks each item *protected*, *changed* or *new* by comparing it with the newest committed point. Items that existed at that point but are gone from disk are listed as *deleted since the last backup*. The Time Machine page lists the same folder as it was at any committed point. Both read **all** the children of the folder (a directory read, or one SQL query without `LIMIT`) and hand them to `internal/listing`, which filters by type, sorts, cuts the requested page and counts the types of the whole folder; the pages and the API use the same call (`Service.ListLive`, `Service.ListHistory`), so they cannot disagree. See [ADR 0008](./adr/0008-folder-lists-are-cut-on-the-server.md). The sort, the type filter and the page are query parameters, so every view has an address that can be shared.

**Display folders.** People reach the folders over the network, so every monitored folder has a display path (`sources.display_path`) and the restore folder a display root (the Site setting `restore_display_root`). `Service.AddSource` and `UpdateSource` apply the policy before the engine looks at the disk: with the Site setting `server_host` set the display path is required and its host must be that one, otherwise it is optional and only its syntax is checked (`backup.SourceError` carries the message key and arguments, so the Settings page can answer in the visitor's language). On every request that has something to show, `internal/server/visibility.go` builds a `viewer` for the account: administrators get texts as they are, everybody else gets them through `service.PathMap` (`Mask`, `MaskValue`), which replaces every real folder of the sources, the repository and the restore folder. See [ADR 0007](./adr/0007-display-folders-and-hiding-server-paths.md).

**Search.** The search box sends the text to a `search.Provider`. The NTFS provider sanitizes the text into plain terms, confines the query to the source root, asks the index of the volume (which reads the change journal first when it did not in the last 2 seconds, so a change of a moment ago counts) for the entries whose names contain every term, folders first and then by name, in a page of a bounded size, and re-checks every result against the root. While the index of the volume is being built, when it cannot read the volume, or when the folder is not below a volume that is indexed, the search is unavailable: the page shows a degraded notice and the API answers `503` `search_unavailable`; browsing and history keep working.

**Restore.** A restore is previewed first (nothing is written), then confirmed with a token that is bound to the user and to the exact plan, then run as a background job into a folder below the configured restore root. See [Restore flow](#restore-flow).

**Sign-in and access.** Every route is registered with one of three wrappers in `internal/server`: `open` (anyone; reads only the cookie, so browsing never depends on Redis), `openChecked` (anyone, but a visitor with a cookie is first checked with the user directory because the page shows an account more than a visitor) and `need(permission, handler)` (a signed-in, active account with the permission; checks the CSRF token on state-changing methods; audits a refusal as `access.denied`). The permissions are `browse` (everyone), `account` (any signed-in account, for signing out and for the actions whose level is checked per folder, see below) and `audit` (the audit log, the status and settings pages) for every signed-in account, `manage` for `admin` accounts only, and `site` for the local administrator only (the Site settings: `needSite` wraps those routes, answers a signed-in account without the permission with the page that is not there, `404`, and audits the attempt as `access.denied`). A sign-in goes through `auth.Manager.Login`: the name of the optional local administrator is checked against its own hash and never looked up elsewhere; any other name is passed to the `auth.Directory`, which `internal/redisuser` implements by finding the `app_user_*` hash (`SCAN`, then `HGETALL`), decoding its fields without executing anything, and comparing the password. The session cookie carries the account, name, role and Redis key; `Manager.Verify` asks the directory again at most once a minute per account and record (`Refresh`), so a deactivation or role change takes effect within a minute, trusts the session as issued for 15 seconds at a time while the directory does not answer, and never takes a request that the visitor abandoned for an outage. Sign-in attempts are counted when they start, per client address and per account name.

**Automatic backups.** `service.RunScheduler` runs in its own goroutine, started after the job runner. Every 15 seconds (and once at start) it asks the catalog for the sources that are due (`enabled`, `schedule_minutes` set, and `last_run_at` empty or at least that many minutes ago) and goes through them in order of need (`rankDue`: no committed point first, then the most overdue in proportion to its interval, then the quickest last run, then the id). A source that already has a queued or running backup is skipped. With the change probe on (`scheduler_probe`), a due source that the NTFS index says did not change is done at once, without a scan, and its interval restarts (`probeUnchanged`: the index knows the folder, answers within 3 seconds, holds as many entries below it as were recorded before the last complete scan, saw nothing created, modified, renamed, moved, deleted or changed in its attributes since 5 minutes before that scan and has been watching the volume since then (`liveSince`), the newest point has no item that was not captured, and that scan is younger than `scheduler_full_scan_every`; a tick asks the index at most 25 times, and an index that does not answer is left alone for a minute, `probeBackedOff`). Changing the exclude patterns of a source clears its last scan (`catalog.UpdateSource`), so its next run scans. The first source that has to be scanned is queued as a backup job whose requester is `scheduler`, if the pace allows (`mayStartScan`: fewer than `scheduler_parallel` automatic backups are queued or running, and the gap since the last start and the rest since the last end have passed; the pace is kept in memory), and then the tick ends. See [ADR 0011](./adr/0011-staggered-scheduler-and-change-probe.md). The backup runs with `SkipUnchanged`: after the scan, when no path was added, modified or deleted and the number of items that could not be read equals that of the newest committed point, the engine discards the recovery point it had begun and returns `ErrUnchanged`; the job runner then deletes the job (`jobs.ErrForget`) and no audit event is written. Whatever the outcome of a run, `last_run_at` and `last_run_ms` are set when it ends, and so are `last_walk_at` and `last_walk_items` after a complete scan (`recordRun`), so the next run is due one interval later. The engine takes the source's advisory lock first and reads the source only then; changing the folder of a source takes the same lock and is refused (`ErrBusy`) while a backup of it runs.

**Folder access.** What a visitor may do with a monitored folder is decided in the HTTP layer, one folder at a time (`internal/server/access.go`; [ADR 0013](./adr/0013-per-folder-access-levels.md)); the service layer does not know who asks. The grants of a folder are loaded with it (`catalog.Source.Access`, from the table `source_access`, read in the same read-only repeatable-read transaction as the folder) and `access.List.LevelFor` turns them and the visitor (`access.Who`: signed in or not, the employee ID, administrator or not) into a level. Every handler that reaches a folder gets it from `loadSource(ctx, session, id, minimum)` (a folder with at least that level; `service.ErrNotFound` when the visitor may not browse it, so a hidden folder answers like one that does not exist; `service.ErrForbidden`, a 403 that is audited with its folder, when they may browse it but not do this), from `visibleSources` (the folders to list) or from `jobSource` (the folder of a job, for the job pages and the cancel button); `TestHandlersReachFoldersThroughTheAccessChecks` fails when a handler reads folders from the service directly. The pages and API calls that browse a folder are registered with `openChecked`, so a visitor whose account was deactivated or lost its role is a guest at once (while the directory does not answer, the session is trusted as issued, as before). The lists of jobs and of audit events are cut in SQL to the visible folders (`jobs.Filter` and `audit.Filter` with `OnlySources` and `SourceIDs`; events without a folder are always kept; an old `job.cancel` event that has no folder is attributed to the folder of its job), the status page counts the jobs of the visible folders only, and the `PathMap` that hides the server's folders in text is built from the visible folders only (`Service.PathMapFor`). The audit record of a refused request keeps the route (the pattern that matched, with the numbers it captured filled in, such as `/jobs/12/cancel`) and not the path that was typed, so it cannot name a folder that the visitor cannot see. The settings page builds the editor of who may do what only when it is asked for (`?edit=<id>`, `?add=1`), from `Manager.Accounts` (the active accounts, kept for a minute by `redisuser.Directory`); a list that was entered is checked by `access.Spec.List` and, for the people it adds, against that list or `Manager.FindAccount` (`SSODirectory.Identify`). In a form and in the API a person is written `user:<employee ID>` (`access.ParseToken`), so an employee ID that is spelled `guest` or `everyone` cannot be taken for those groups. An account with Full access changes a folder with `catalog.SourceUpdate.KeepRoot` set (the SQL then never writes the real folder) and an `Authorize` function that the catalog calls in the update's own transaction, after it has locked the row of the folder, with the grants that are in force at that moment: a change that was allowed by grants which were revoked meanwhile is refused (`service.ErrForbidden`). A change that takes away the Full access of the one who makes it needs `confirm_lockout` (`409 lockout_not_confirmed` otherwise). A change that replaces the lists also names the grants it was made from (`access.List.Digest`, `access_rev` in the forms and in the API): the same `Authorize` function compares it with the stored grants and refuses the change with `accessChangedError` (`409 access_changed`) when they differ, and a form whose editor was not touched (`settingsForm.untouched`) does not write the lists at all. `viewer.audit` replaces the `access` of an audit detail with `[hidden]` unless the visitor has Full on the folder of the event, and `Service.PreviewRestore` and `Service.StartRestore` check the recovery point with `Service.Point` first, so a point of another folder is answered as one that does not exist.

**Single sign-on.** `internal/server/sso.go` keeps the sign-ins in progress in memory (a token, the client address, the page to go to afterwards, the time). `POST /auth/sso/start` issues a token (15 random bytes, 24 characters) and returns the address of the company sign-on service with it; the browser opens that address in a window. `POST /auth/sso/poll` looks the flow up, compares the client address with the one that started it (with the Site setting `sso_require_same_ip`), reads `sso_login_<token>` through `auth.SSODirectory.SSOResult` (a `GET` by `internal/redisuser`, decoded by the same restricted pickle decoder as the accounts), maps the employee ID to an active account with `Identify` (the newest record, which must be activated) and starts the same session as a password sign-in (`Manager.StartSession`). The flow is then removed, so a result is used once; the key in Redis is never deleted and expires on its own. The client address comes from `Server.clientIP`, which believes `X-Forwarded-For` only from the Site setting `trusted_proxies`. When the check refuses a sign-in over the addresses, `Server.addressDetail` adds how the request reached the server (`connection`, `trusted_proxy`, `forwarded`) to the audit record, and the same goes to the log. See [ADR 0009](./adr/0009-single-sign-on-and-trusted-proxies.md).

**Path prefix.** With the Site setting `base_path` (for example `/tv`) the site can be served under a path of a host name that other applications share. Inside, the routes, the redirect targets and the template paths stay written without the prefix; `internal/server/basepath.go` takes it off on the way in and puts it on on the way out. `Server.withBase` is the outermost handler: a path that starts with the prefix loses it (`http.StripPrefix`), the bare prefix is sent to the same address with a slash, and any other request is served as it is, so a proxy may keep or remove the prefix. It wraps the response in `prefixWriter`, which puts the prefix on every `Location` header that names a path of the application: the redirects of the pages, the `Location` of the API and the redirects of the `ServeMux`. The templates write every address with the `url` function (`Server.href`), the address a link carries for the page to come back to (`next`, `back`) is written with `route`, the script reads the prefix from `<meta name="tv-base">`, and the cookies take their path from `Server.cookiePath` and `auth.Options.CookiePath`. An address that comes back from the browser goes through `Server.local` and `Server.safeNext`, which take the prefix off and check the result again. Two tests keep the pieces honest: no template may write an address that starts with a slash, and no code may set a cookie for the whole host. See [ADR 0012](./adr/0012-base-path-behind-a-reverse-proxy.md).

**Automatic update.** With the Site setting `update_url` set, `runServe` in `cmd/timevault-server/main.go` builds an `update.Updater` from an `update.Source` (an `http(s)` address or a path), the job runner (as its `Drainer`), the path of the running program (`os.Executable`, taken before anything is swapped) and the audit logger, and runs it in a goroutine next to the scheduler. About 10 seconds after the start, at every interval and when `CheckNow` is called (the **Check now** button, `POST /api/v1/update/check`) it reads the manifest (`update.ParseManifest`). A version other than the running one is downloaded to `timevault.new.exe` through a `.part` file and kept only when its size and sha256 are the manifest's (`update.Download`), then examined by running it (`ExecChecker`: `version`, and `check-config`, which is `runCheckConfig` in `main.go`: it loads the bootstrap settings and runs `ValidateBootstrap`, and connects to nothing, so the Site settings in the database are not part of it). When it passes, `Runner.Drain` makes the workers take no job; the running jobs go on and new ones stay queued. When `Runner.Running` is zero, `update.Swap` renames the running program to `timevault.old-<version>.exe` and the new one to the name of the program (it undoes the first rename when the second fails), and `WriteMarker` leaves a note next to it. `Updater.Run` returns the `*update.Update`; `runServe` then stops the scheduler, the web server and the runner as for any shutdown (which releases the database lock) and hands a `restart` to `serveAndRestart`. That either exits with the code 75 (`update.RestartExit`, for a service manager) or turns the process into a launcher (`update.Supervise`) that runs the program again as a child, with `TIMEVAULT_SUPERVISED_BY` set, for as long as the child ends with 75; a program that has that variable set always exits with 75 (`update.Decide`) and watches the launcher: its standard input is a pipe that only the launcher holds, and when it ends the program shuts down in order (`update.StopWithLauncher`, started in `runServe`), so a launcher that is killed leaves no program behind. The new program reads and deletes the note (`update.TakeMarker`) and records the `done` event. Whatever goes wrong before the swap leaves the service running, with the state and the error in `Updater.Status`, which is what the Settings card, `GET /api/v1/settings` and the notice under the header show (the notice goes with every page, also in the `X-TV-Notice` header of the partial pages the script swaps in). The audit events (`app.update`, actor `updater`) carry no path and no error text. See [ADR 0014](./adr/0014-self-update-from-a-release-manifest.md).

**Pictures of the accounts.** The server says where they are, which names may have one and which host the policy must allow, and fetches nothing: `avatar_url` (with its default from `server_host` worked out by `parseAvatarURL` in the config) goes into `<meta name="tv-avatar">`; `pictureSource` in `avatar.go` turns the host of an absolute address into the source added to `img-src` (`contentSecurityPolicy`, built once in `New`, with the wildcard of the domain for a host name with an underscore, which a policy cannot name); and the templates write `data-avatar="<employee ID>"` next to a name through the `avatar` and `person` partials (`Page.AvatarID` leaves out the local administrator, the names the service uses itself and anything that is not an employee ID). `initAvatars` in `app.js` loads each picture once with an `Image`, only when it is about to be seen (`IntersectionObserver`). An error, or a picture of exactly 480×320 pixels (the placeholder that the host of the pictures answers with `202` for a missing one, and the pictures themselves come as `text/plain`), counts as no picture and is remembered for ten minutes in `sessionStorage`; any other is shown in an `<img>`, which the browser serves from what it just loaded. The default picture is in the page and stays when anything fails.

**Web log.** With `web_log` on (by default when `TIMEVAULT_REDIS_URL` is set), `runServe` opens a `redisuser.Conn` (`Connect`: a pool of 2 connections, the timeout `TIMEVAULT_REDIS_TIMEOUT`) and starts a `weblog.Writer` for the list `web_log_key`. The writer is the `weblog.Sink` that the service (`service.Config.WebLog`, for the scheduler) and the server (`server.Options.WebLog`) are given, and the function that the audit logger gets with `SetMirror` writes to it; when the web log is off the sink is `nil` and no mirror is set. Lines come from four places. `Server.requestLog` (the end of every request except the static files and `/healthz`) reports a page that somebody opened or a request that failed (`webLogRequest`; the route is `routeOf`, the pattern that matched, never the address as it was typed; the request header `X-TV-Auto` marks the reloads that the page script made by itself). `audit.Logger.Record` hands every event to the mirror after the `INSERT` succeeded (`weblog.Audit`: the result decides the status and the level, and of the detail only the route of a refusal and the stage of a program update are used). The scheduler reports `scheduler.queued`, `scheduler.error` and, for the debug level, `scheduler.skipped`. And `runServe` writes `started` once everything is built and `stopped` when it returns. `Writer.Write` only puts the line into a queue of 1,024 and returns, so a request, an audit record or a scheduler tick never waits for Redis; a worker takes up to 100 lines and sends them with one `RPUSH`. Two token buckets cut a flood at the door (page lines: 10 per second on average with a burst of 100; event lines: 20 per second with a burst of 200), a full queue drops the line, and after a failed `RPUSH` the worker leaves Redis alone (30 seconds, doubling up to 5 minutes) and drops what comes meanwhile, warning once with the password of the URL masked (`Conn.Redact`). At shutdown the queue is sent first, for at most 3 seconds. A line is `ip | time | message | status | level | host`, encoded by `Encode` as `zlib.compress(pickle.dumps(line, protocol=4))`, the format that the company's applications share; the account is in the message as `user=<employee ID>`, because a field cannot be added. The debug lines (the polling of a job, the automatic reloads, `scheduler.skipped`) are written only with `log_level` `debug`, which is the one use that the web log has for the log level. `internal/redisuser` still only reads (the `Store` does not use a `Conn`), and `config.parseWebLog` refuses a key that starts like the keys of the accounts or of the single sign-on results. See [ADR 0016](./adr/0016-web-log-in-the-shared-redis-list.md).

**Page guide.** Every page except the sign-in page has two round buttons at the bottom right, next to the arrows (`layout.html`): **Documentation**, a link to `GET /help` in a new tab (`handleHelp` in `pages_help.go`, the template `help.html`, open to everybody), and **Guide**, which starts a step-by-step tour of the page. The steps are written in the templates: `Page.Tour(key)` (`render.go`) gives an element the attributes `data-tour`, `data-tour-title` and `data-tour-text`, with the texts of the messages `tour.<key>.title` and `tour.<key>.text` in the language of the page (`i18n_tour.go`, English and Chinese), so that an element which the page does not show has no step. `web/assets/js/tour.js` (a plain script: no library, no inline script or style) collects the visible elements that carry the attributes, those in the content first and then the header and the round buttons, dims the page, lights up one part and shows a bubble with the title, the text, "Step n of N" and the buttons; it clicks and changes nothing. It ends when another page is shown or the back button is used, and it goes on when the same page refreshes itself (the job page does while its job runs). `TestEveryStepOfTheGuideIsTranslatedAndUsed` checks that every step that a template names has its two texts in both languages and that no text is left over.

**Folder sizes.** When the live listing holds folders, `Service.ListLive` asks `fillFolderSizes` for their sizes: one `NTFS.Subfolders` call (the folders directly inside the folder, with the size of everything below each, from the index) whose answer is cached for 10 seconds. A question waits at most 2 seconds; when the index does not answer, the sizes stay unknown (shown as `-`) and it is not asked again for 15 seconds. The sizes take part in sorting by size. The Time Machine and the versions page read the catalog and do not use them.

**NTFS index.** Unless the Site setting `search_index` is `off`, `runServe` creates an `ntfsindex.Manager` (`Config.Roots` is `sourceRoots`: the folders of all the monitored folders in the catalog, asked again every 10 seconds, so one that is added or removed is noticed) and runs it in a goroutine; `search.NewNTFS` wraps it as the `Provider`, `FolderLister` and `ChangeProber` of the service. For each drive letter that has monitored folders the Manager opens the volume and builds an `index` in a goroutine. `build` reads the state of the journal first (`Journal`) and remembers the time (`liveSince`), lists the folders of the volume without decoding names (`Dirs`, `FSCTL_ENUM_USN_DATA`), works out which of them are inside the monitored folders, then lists the entries with their sizes and times (`Entries`, `FSCTL_QUERY_FILE_LAYOUT`), decodes a name only for an entry that is inside, and drops the rest. The records that the journal wrote since the build began are applied afterwards; applying a record is idempotent, so one that the listing already showed does no harm (`index.apply`: create, delete, the old and the new name of a rename, and a write, after which `refresh` reads the size and time again a little later). The index answers a search below a folder (a name that contains every term, folders first and then by name, with a partial heap selection when there are many hits), the folders directly inside a folder with the size of everything below each (sums that are worked out when asked and made stale by a change) and a probe (`probe`: how many entries are below the folder, and whether the monitored folder that holds it saw a change since a time, or has not been watched since then). `Manager.find` reads the journal before it answers when that was not done in the last 2 seconds (the probe always does). A journal that was replaced or overwritten (`ErrJournalLost`), and a folder that was moved into a monitored folder from outside, make the volume be built again (the second at most once a minute); until it is ready the volume answers `ErrNotReady`. `Manager.Health` says what the Status page shows: idle, building, ready, or why a volume cannot be indexed (`ErrAccessDenied`, `ErrJournalOff`, `ErrUnsupported`). See [ADR 0018](./adr/0018-native-ntfs-index-replaces-everything.md) and [runbook.md](./runbook.md#search-index).

**Site settings and start-up.** `runServe` starts in two steps, because a Site setting (`job_workers`) decides the size of the pool that the rest needs. It reads the bootstrap settings from the environment and `.env` (`loadBootstrap`, `ValidateBootstrap`), connects to the database with a small pool of its own, applies the migrations (or checks that they were applied: the table `site_settings` is one of them), reads the Site settings with `sitesettings.Store.Load`, builds the configuration with `config.Load(config.SiteLookup(base, stored))`, validates it (`ValidateServe`) and only then opens the real pool. A stored set that is not valid together stops the service with a message that names the problems (`timevault-server settings` is the way back). Settings of the old `.env` that are Site settings now, and the removed Everything settings, are named in a warning (`config.LegacySettings`) and otherwise ignored. The Site settings page (`internal/server/site.go`) builds its form from `config.SiteSettings` and `SiteEffective`, checks a posted form with `siteChange` and `config.SiteProblems` against the bootstrap settings (`SiteBackend.Base`), stores the difference (`diffSite`: a value that equals its default is not stored) with `sitesettings.Store.Save` in one transaction and audits it by key name (`auditSite`). A setting takes effect after a restart: the page compares what is stored with what the service started with (`SiteBackend.Running`) and, when they differ, offers **Restart now**. `SiteBackend.Restart` is made in `main.go`: it calls `Runner.Drain`, and when jobs still run it calls `Resume` and returns `ErrJobsRunning` (`409 jobs_running`); otherwise it asks `runServe` to stop as for an update, and `serveAndRestart` starts the program again the way it does after an update (`update_restart`). See [ADR 0017](./adr/0017-site-settings-in-the-database.md).

**Version limit.** After a backup committed a recovery point, and when the folder has a limit, `pruneAfterBackup` calls `Engine.Prune`: with the writer lock of the source, `catalog.PruneVersions` deletes (in batches of 500 files, one transaction each) the versions of the files that backup changed that fall outside the newest N captured versions of the file, and flags the recovery points that lost versions (`recovery_points.partial`) in the same transaction. When versions were deleted, `Engine.SweepObjects` then deletes the objects that no version refers to (the file first, then its record), within 2 minutes; it only runs while no backup holds the shared side of a gate in the backup engine (it takes the exclusive side with a try-lock and never makes a backup wait), and a sweep that could not run or finish is repeated by the scheduler's next tick. This cleanup inside a backup never waits: while a restore or verification of the folder is queued or running, or when it fails, a `prune` job for the whole folder is queued instead (`Service.StartPrune`, at most one active per folder), which survives a restart. Setting or lowering a limit queues the same job. The job queue lets the cleanup of a folder take turns with the other jobs of that folder (`jobs.Runner.claim`): it is not claimed while a backup, a restore or a verification of the folder runs, and none of them is claimed while it runs, so a job that has to wait stays queued and holds no worker. Lowering a limit first needs `confirm_prune` when it would delete versions (`PruneNotConfirmedError`; the preview uses the same SQL as the deletion), and a limit cannot change while a cleanup of the folder runs. While the versions of a folder are being deleted (`Service.pruning`, or a running `prune` job), `StartRestore` and `StartVerify` refuse that folder (`ErrPruneRunning`), and a restore or verification that was queued before waits for the deletion to end (`waitWhilePruning`). Verification of a partial point skips the comparison with the manifest. See [ADR 0010](./adr/0010-version-limit-and-garbage-collection.md).

## Data model (PostgreSQL)

History uses validity ranges so a recovery point only stores what changed:

| Table | Meaning |
|---|---|
| `sources` | Monitored folders: name, folder (`root_path`), `display_path` (NULL = none; the network path people know it by, at most 520 characters), exclude patterns, `enabled`, `schedule_minutes` (NULL = manual only, otherwise 1 to 43200), `last_run_at` (when the last backup run ended), `last_run_ms` (how long it took), `last_walk_at` and `last_walk_items` (when the last complete scan started and how many entries the index held below the folder then), and `max_versions` (NULL = keep every version, otherwise 1 to 10000). |
| `source_access` | Who may do what with a folder: one row per folder and principal, with `kind` (`guest`, `everyone` or `user`), `account` (the employee ID, upper case, for `user` only) and `level` (`browse`, `backup` or `full`; a guest can only have `browse`). A folder without rows can be seen by administrators only; administrators are not listed. |
| `recovery_points` | One row per backup attempt: sequence number `seq` per source, `state`, `consistency`, counters, manifest digest, `verification`, and `partial` (older versions of some files were deleted by the version limit). |
| `nodes` | One row per path slot, identified by (`parent_id`, exact `name`); `name_key` is the lower-cased name used for sorting and case-insensitive lookup. The root of a source has `parent_id` NULL. |
| `node_versions` | Each state of a slot: folder or file, size, modification time, attributes, content hash, `state` (`ok` or `skipped` with a reason), valid for the sequence numbers `first_point`..`last_point` (`last_point` NULL while open). |
| `objects` | Content objects that exist in the repository (hash, size). |
| `jobs`, `job_events`, `restore_items` | Background jobs (kinds `backup`, `verify`, `restore` and `prune`), their log lines and per-item restore results. |
| `audit_events` | Append-only (a trigger rejects UPDATE and DELETE), with `duration_ms` for the operations that have a duration. |
| `site_settings` | The Site settings that have a value: `key` (the lower-case name, such as `job_workers`), `value`, `updated_at` and `updated_by` (the account that saved it, `cli` for `timevault-server settings`). A setting without a row has its default; a value that equals the default is not stored. |

A file that is unchanged between two points costs no new row. A folder that disappears closes the versions of its whole subtree with one recursive statement. A path that is deleted and later comes back gets a new version on the same node. Rename and move are recorded as delete plus add (bytes are still stored once, because content is addressed by hash).

A build writes its rows under its own sequence number and closes old versions at the previous committed sequence number. Because readers only use committed sequence numbers, none of this is visible until the point is committed. After a crash or cancellation the next build (or the start-up recovery) deletes every version with `first_point` greater than the newest committed sequence and re-opens every version closed at it.

## Recovery point lifecycle

`building` → `committed`, or `failed` / `aborted`. After commit `verification` is `validated` (the commit-time checks passed: every object this build newly recorded exists with the right size), then `verified` after a deep integrity check, or `failed` when a check finds a problem; a point with `verification = failed` is not restorable. A normal backup does not re-check the content of files it carries over unchanged; an integrity check (Verify) finds repository objects that went missing or were damaged since, and a **Full re-read** backup writes missing content again. Job phases shown in the UI: `snapshot_preparing` → `scanning` (enumerating and copying are interleaved per folder) → `manifest_validating` → `committing` → `committed`; after a backup with a version limit also `pruning` (deleting old versions) and `sweeping` (freeing space), ending again at `committed`.

The **manifest digest** is a SHA-256 over one canonical line per path (path, kind, size, modification time, attributes, content hash) in a fixed order. The backup computes it while it scans; verification recomputes it from the catalog. If the two differ, the catalog was changed after commit.

## Repository

```text
<repository>/
  timevault-repository.json      format version and repository id
  objects/ab/cd/<sha256>         immutable content, read-only attribute set
  tmp/                           objects being written; stale files are cleaned
```

An object is streamed to `tmp/`, hashed while it is written, flushed, and only then renamed to its final name, so `objects/` never holds a partial object. Before a recovery point is committed the backup flushes the folders that received new objects (`Barrier`), so a power failure cannot leave the catalog pointing at an object whose directory entry was lost; this is best effort and has not been tested against a real power loss. The repository refuses a non-empty folder that is not a TimeVault repository. Writers of identical content agree on who created the object (striped lock per hash prefix).

## Consistency on a live disk

The MVP reads the live file system (`consistency = live_scan`); it does not use a VSS snapshot. To avoid storing torn copies:

- A file's size and modification time are read from the open handle before and after the copy. If they differ the file is read again (up to three attempts), then recorded as *not captured* with the reason.
- A file locked by another process (sharing violation) or unreadable is recorded as *not captured*; if an earlier good version exists it is kept and a warning is logged.
- A folder that cannot be listed keeps its previous state; its contents are never treated as deleted.
- Junctions, symbolic links and other reparse points are not followed; they are recorded as *not captured*. A file or folder that is replaced by a link after its folder was listed is detected and not followed either, so another file's content is never recorded under the wrong path.
- Names that Windows cannot represent safely (reserved device names, trailing dots or spaces, invalid characters) are skipped and counted.
- Paths deeper than 256 folders are recorded as *not captured*, because browsing and restoring accept at most that depth.
- Overlap checks (a source against the repository, the restore folder and other sources) compare where the folders really are, resolved through junctions and links, both when a source is added and when each backup starts.

The UI labels every point *Live scan* so nobody mistakes it for a snapshot.

## Restore flow

1. **Preview** (`Preview`): validates the request, resolves each selected path at the chosen point, classifies every item against the destination (create, overwrite, rename, skip; an existing file counts as identical only when its size, modification time and SHA-256 all match the catalog, so existing files are read while planning) and checks that every content object exists with the right size. Nothing is written. The result carries a digest of the plan.
2. **Confirm**: the token is an HMAC over (user, plan digest, expiry of 15 minutes). The service re-plans and compares digests, so a changed destination or a different request makes the preview stale. Replacing existing files additionally needs an explicit confirmation.
3. **Execute** (background job): plans again and refuses to write anything if items are blocked (missing content, not captured, unsafe name) unless *allow partial* was chosen. Every file is streamed from the repository into a temporary file in the destination folder, its SHA-256 and size are checked, the modification time and attributes are applied, and only then it is renamed into place. All paths go through `os.Root` on the destination folder. Per-item outcomes are stored for the job page.

Restores only write below `TIMEVAULT_RESTORE_ROOT`, into a folder named by the requester (created when it does not exist; when it already exists, for example for a repeated restore, the conflict policy decides what happens to files that are already there). The destination folder must be a plain folder: if it already exists as a junction or symbolic link the restore is refused, and the restore root is compared with the repository and every source by its real location. Nothing in a restore deletes or overwrites source data or repository content.

## 概述

TimeVault 是一个 Go 服务 `timevault-server`（`cmd/timevault-server`），同时承载网页界面、JSON API 和后台任务。历史记录保存在 PostgreSQL 中，文件内容保存在独立的、按内容寻址的仓库文件夹中。它只读取备份源文件夹，绝不修改它们。任何人都可以浏览允许访客浏览的文件夹；来自 Redis 用户目录的公司账号登录后可以做更多事，而一个账号能做什么是按每个监控文件夹分别决定的（0.1.7 版；见 [ADR 0005](./adr/0005-redis-user-directory-and-open-browsing.md) 和 [ADR 0013](./adr/0013-per-folder-access-levels.md)）。从 1.0.1 起，它还在自己的内存中保存监控文件夹的索引，该索引由 NTFS 卷建立，并由卷的变更日志保持最新（不需要任何搜索程序，见 [ADR 0018](./adr/0018-native-ntfs-index-replaces-everything.md)），并且它的运行设置保存在数据库中，只有本地管理员可以编辑（见 [ADR 0017](./adr/0017-site-settings-in-the-database.md)）。

本文档描述已经实现的内容。plan.md 中提到但 TimeVault 尚未实现的部分，见 [mvp-status.md](./mvp-status.md)。

| `internal/server`、`web/` | HTTP 路由与访问控制（`open`、`openChecked`、`need`）、中间件、服务端渲染页面（Go 模板）、JSON API、内嵌静态资源、EN/中文文案、列表控件（排序链接、类型筛选、分页）、单点登录流程（`sso.go`）、路径前缀（`basepath.go`）、`access.go`（按文件夹的检查）和 `settings_access.go`（"谁可以做什么"的编辑器）、`visibility.go`（决定每一类访问者能看到服务器上的哪些文件夹）、`update.go`（更新卡片、页眉下面的提示以及"立即查看"的请求）、`site.go`（站点设置页、它的 API 和重启，位于只让本地管理员进入的 `needSite` 之后）、`avatar.go`（哪些名称有头像）、`pages_help.go`（用户手册）、`i18n_tour.go` 和 `web/assets/js/tour.js`（页面导览，见"页面导览"），以及 `server.go` 中的请求日志（每个请求的地址和用户，以及向 Web 日志的报告）。 |

## 数据流

**备份。** 备份任务先取得该备份源的 advisory 锁，清除之前未完成的构建留下的内容，创建状态为 `building` 的恢复点，逐个文件夹遍历备份源，把新增或变化的文件复制进仓库，每个文件夹的变更在一个事务中写入，校验自己新记录的每个对象仍然存在，把仓库文件夹刷新到磁盘，最后用一条更新语句把恢复点标记为 `committed`。这条更新一旦发出就不会被放弃：之后才到达的取消操作，不会把已提交的恢复点变成失败的任务。读取方只会查询已提交的恢复点，所以构建中、失败或被取消的恢复点永远不可见。

**单实例。** 同一个数据库（schema）只能运行一个服务。启动时，在做任何恢复之前，服务会在一个专用连接上获取 PostgreSQL advisory 锁；第二个服务会以"another TimeVault service is already running against this database"退出。否则，第二个服务启动时的恢复会把第一个服务正在运行的任务标记为失败。

**浏览。** 文件浏览页通过 `os.Root` 列出磁盘上当前的文件夹（精心构造的路径无法跳出备份源），并与最新已提交的恢复点对比，把每一项标记为*已保护*、*已变更*或*新增*。在该恢复点存在、但磁盘上已经没有的项目，会列为*自上次备份以来已删除*。时间机器页面则列出同一文件夹在任意已提交恢复点时的样子。两者都会读取文件夹的**全部**子项（一次目录读取，或一条没有 `LIMIT` 的 SQL 查询），再交给 `internal/listing`，由它按类型筛选、排序、截取请求的那一页，并统计整个文件夹中各类型的数量；页面和 API 使用同一个调用（`Service.ListLive`、`Service.ListHistory`），所以它们不会不一致。见 [ADR 0008](./adr/0008-folder-lists-are-cut-on-the-server.md)。排序、类型筛选和页码都是查询参数，所以每个视图都有可以分享的地址。

**显示文件夹。** 人们通过网络访问文件夹，所以每个监控文件夹都有一个显示路径（`sources.display_path`），恢复文件夹有一个显示根路径（站点设置 `restore_display_root`）。`Service.AddSource` 和 `UpdateSource` 在引擎查看磁盘之前先应用这套策略：设置了站点设置 `server_host` 时显示路径是必填的，并且它的主机必须是该主机，否则它是可选的，只检查语法（`backup.SourceError` 携带消息键和参数，所以设置页可以用访问者的语言回答）。每个有内容要显示的请求，`internal/server/visibility.go` 都会为该账号构建一个 `viewer`：管理员得到原样的文本，其他人得到经过 `service.PathMap`（`Mask`、`MaskValue`）处理的文本，它会替换备份源、仓库和恢复文件夹的每一个真实文件夹。见 [ADR 0007](./adr/0007-display-folders-and-hiding-server-paths.md)。

**搜索。** 搜索框把文本交给 `search.Provider`。NTFS 提供者把文本清理成纯文本的词，把查询限定在备份源根目录内，向该卷的索引询问名称包含每一个词的条目（如果过去 2 秒内没有读过变更日志，索引会先读，所以刚刚发生的变化也算在内），先文件夹、再按名称排序，页大小受限，并对每个结果再次检查是否位于根目录内。该卷的索引正在建立、无法读取该卷，或者该文件夹不在已建立索引的卷之下时，搜索不可用：页面显示降级提示，API 返回 `503` `search_unavailable`；浏览和历史功能不受影响。

**恢复。** 恢复先预览（不写入任何内容），再用与用户和该计划绑定的令牌确认，然后作为后台任务写入所配置恢复根目录下的文件夹。见[恢复流程](#恢复流程)。

**登录与访问控制。** `internal/server` 中的每条路由都用三种包装之一注册：`open`（任何人；只读取 Cookie，所以浏览从不依赖 Redis）、`openChecked`（任何人，但带有 Cookie 的访问者会先向用户目录核实，因为页面对账号展示的内容比对访问者更多）和 `need(权限, 处理函数)`（必须是具有该权限的、已登录且有效的账号；对会改变状态的方法校验 CSRF 令牌；被拒绝时以 `access.denied` 记入审计）。权限有：`browse`（所有人）、`account`（任何已登录的账号，用于退出，以及用于那些按文件夹检查级别的操作，见下文）和 `audit`（审计日志、状态页和设置页），它们对每个已登录账号开放，仅限 `admin` 账号的 `manage`，以及仅限本地管理员的 `site`（站点设置：这些路由由 `needSite` 包装，对没有该权限的已登录账号回答一个不存在的页面，即 `404`，并把这次尝试以 `access.denied` 记入审计）。登录由 `auth.Manager.Login` 处理：可选的本地管理员的名字只与它自己的哈希比对，绝不去别处查找；其他名字交给 `auth.Directory`，由 `internal/redisuser` 实现，即找到 `app_user_*` 哈希（先 `SCAN`，再 `HGETALL`），在不执行任何内容的前提下解码其字段，再比对密码。会话 Cookie 携带账号、姓名、角色和 Redis 键；`Manager.Verify` 对每个账号和记录最多每分钟向目录再核实一次（`Refresh`），所以停用账号或更改角色在一分钟内生效；目录无应答时，每次按签发时的状态信任会话 15 秒；访问者已放弃的请求不会被当作故障而计入。登录尝试在开始时就按客户端地址和账号名分别计数。

**文件夹访问。** 访问者可以对一个监控文件夹做什么，是在 HTTP 层逐个文件夹决定的（`internal/server/access.go`；[ADR 0013](./adr/0013-per-folder-access-levels.md)）；服务层并不知道是谁在请求。文件夹的授权随文件夹一起加载（`catalog.Source.Access`，来自表 `source_access`，与文件夹在同一个只读的可重复读事务中读取），`access.List.LevelFor` 把授权和访问者（`access.Who`：是否已登录、工号、是否管理员）换算成一个级别。每个要访问文件夹的处理函数都通过 `loadSource(ctx, session, id, minimum)`（级别至少为该值的文件夹；访问者不能浏览它时返回 `service.ErrNotFound`，所以被隐藏的文件夹与不存在的文件夹回答一样；能浏览但不能做这件事时返回 `service.ErrForbidden`，即带着文件夹记入审计的 403）、`visibleSources`（要列出的文件夹）或 `jobSource`（任务所属的文件夹，用于任务页面和取消按钮）取得文件夹；当某个处理函数直接从服务读取文件夹时，`TestHandlersReachFoldersThroughTheAccessChecks` 会失败。浏览文件夹的页面和 API 调用都用 `openChecked` 注册，所以账号已被停用或失去角色的访问者会立即变成访客（目录无应答期间，按签发时的状态信任会话，与以前一样）。任务和审计事件的列表在 SQL 中被裁剪到可见的文件夹（`jobs.Filter` 和 `audit.Filter` 的 `OnlySources` 与 `SourceIDs`；没有文件夹的事件始终保留；没有文件夹的旧 `job.cancel` 事件归到其任务所属的文件夹），状态页只统计可见文件夹的任务，在文本中隐藏服务器文件夹的 `PathMap` 也只由可见的文件夹构建（`Service.PathMapFor`）。被拒绝请求的审计记录保存的是路由（匹配到的模式，其中捕获到的数字已填入，例如 `/jobs/12/cancel`），而不是输入的路径，所以它不会点出访问者看不到的文件夹。设置页只在被请求时才构建"谁可以做什么"的编辑器（`?edit=<id>`、`?add=1`），人员来自 `Manager.Accounts`（有效账号，由 `redisuser.Directory` 缓存一分钟）；输入的名单由 `access.Spec.List` 检查，其中新增的人员则对照原名单或 `Manager.FindAccount`（`SSODirectory.Identify`）检查。在表单和 API 中，人员写成 `user:<工号>`（`access.ParseToken`），所以拼写为 `guest` 或 `everyone` 的工号不会被当成这两个组。具有完全权限的账号修改文件夹时，会设置 `catalog.SourceUpdate.KeepRoot`（SQL 因此从不写入真实文件夹），并带一个 `Authorize` 函数，目录库在更新自己的事务中、锁定文件夹的行之后，用那一刻有效的授权调用它：如果某个更改所依据的授权在此期间已被撤销，该更改会被拒绝（`service.ErrForbidden`）。取消更改者自己的完全权限的更改需要 `confirm_lockout`（否则返回 `409 lockout_not_confirmed`）。替换列表的更改还会说明它所依据的授权（`access.List.Digest`，在表单和 API 中是 `access_rev`）：同一个 `Authorize` 函数会把它与已保存的授权比较，两者不同时用 `accessChangedError` 拒绝该更改（`409 access_changed`），而编辑器没有被动过的表单（`settingsForm.untouched`）根本不写入列表。`viewer.audit` 会把审计详情中的 `access` 替换为 `[hidden]`，除非访问者对该事件所属的文件夹拥有"完全"权限；`Service.PreviewRestore` 和 `Service.StartRestore` 会先用 `Service.Point` 检查恢复点，所以属于另一个文件夹的恢复点，得到的回答与不存在的恢复点一样。

**自动备份。** `service.RunScheduler` 在自己的 goroutine 中运行，在任务运行器之后启动。它每 15 秒（启动时也运行一次）向 catalog 查询到期的备份源（`enabled`、设置了 `schedule_minutes`，且 `last_run_at` 为空或距今至少这么多分钟），并按需要程度依次处理它们（`rankDue`：没有已提交恢复点的先来，然后是相对于自己的间隔超期最多的，再然后是上次运行最快的，最后是 id）。已经有排队或运行中备份的备份源会被跳过。开启变更探测（`scheduler_probe`）后，如果 NTFS 索引说某个到期的备份源没有变化，就立即处理完毕、不做扫描，并让它的间隔重新开始（`probeUnchanged`：索引认识该文件夹、3 秒内应答、其下的条目数量与上次完整扫描之前记录的数量相同、自上次扫描前 5 分钟以来没有看到任何创建、修改、重命名、移动、删除或属性变化，并且自那时起一直在监视该卷（`liveSince`）、最新的恢复点没有未捕获的项目，并且那次扫描比 `scheduler_full_scan_every` 更新；一个周期最多询问索引 25 次，没有应答的索引在一分钟内不会再被询问，`probeBackedOff`）。更改备份源的排除规则会清除它上次的扫描记录（`catalog.UpdateSource`），所以它的下一次运行会进行扫描。第一个必须扫描的备份源会在间隔状态允许时被排入一个请求者为 `scheduler` 的备份任务（`mayStartScan`：排队或运行中的自动备份少于 `scheduler_parallel` 个，并且自上次启动以来的间隔和自上次结束以来的休息都已过去；间隔状态保存在内存中），然后这个周期结束。见 [ADR 0011](./adr/0011-staggered-scheduler-and-change-probe.md)。备份以 `SkipUnchanged` 运行：扫描之后，如果没有任何路径被新增、修改或删除，且无法读取的项目数量与最新已提交的恢复点相同，引擎会丢弃它已开始创建的恢复点并返回 `ErrUnchanged`；任务运行器随后删除该任务（`jobs.ErrForget`），也不写入审计事件。无论一次运行的结果如何，`last_run_at` 和 `last_run_ms` 都在其结束时设置，完整扫描之后还会设置 `last_walk_at` 和 `last_walk_items`（`recordRun`），所以下一次在一个间隔之后到期。引擎先取得备份源的 advisory 锁，然后才读取备份源；更改备份源的文件夹要取得同一把锁，并且在它的备份运行期间会被拒绝（`ErrBusy`）。

**单点登录。** `internal/server/sso.go` 在内存中保存进行中的登录（令牌、客户端地址、登录后要去的页面、时间）。`POST /auth/sso/start` 签发一个令牌（15 个随机字节，24 个字符），并连同它返回公司单点登录服务的地址；浏览器在一个窗口中打开该地址。`POST /auth/sso/poll` 查找该流程，把客户端地址与发起它的地址比较（设置了站点设置 `sso_require_same_ip` 时），通过 `auth.SSODirectory.SSOResult` 读取 `sso_login_<token>`（由 `internal/redisuser` 用 `GET` 读取，并用与账号相同的受限 pickle 解码器解码），用 `Identify` 把工号对应到有效账号（最新的记录，且必须已激活），然后开始与密码登录相同的会话（`Manager.StartSession`）。随后该流程被移除，所以一个结果只能使用一次；Redis 中的键从不被删除，而是自己过期。客户端地址来自 `Server.clientIP`，它只信任来自站点设置 `trusted_proxies` 的 `X-Forwarded-For`。当检查因为地址而拒绝一次登录时，`Server.addressDetail` 会把请求是怎样到达服务器的（`connection`、`trusted_proxy`、`forwarded`）加入审计记录，同样的内容也会写入日志。见 [ADR 0009](./adr/0009-single-sign-on-and-trusted-proxies.md)。

**路径前缀。** 设置站点设置 `base_path`（例如 `/tv`）后，站点可以放在多个应用共用的主机名的某个路径下提供服务。内部的路由、重定向目标和模板路径仍然不带前缀地书写；`internal/server/basepath.go` 在进入时去掉前缀，在出去时加上前缀。`Server.withBase` 是最外层的处理器：路径以前缀开头的请求会去掉前缀（`http.StripPrefix`），只有前缀本身的请求会被送到带斜杠的同一地址，其他请求原样处理，所以代理可以保留也可以去掉前缀。它用 `prefixWriter` 包装响应，给每个指向应用路径的 `Location` 头加上前缀：页面的重定向、API 的 `Location` 以及 `ServeMux` 自己的重定向。模板用 `url` 函数（`Server.href`）写每个地址，链接中携带的、用于回到某个页面的地址（`next`、`back`）用 `route` 写，脚本从 `<meta name="tv-base">` 读取前缀，Cookie 的路径来自 `Server.cookiePath` 和 `auth.Options.CookiePath`。从浏览器返回的地址要经过 `Server.local` 和 `Server.safeNext`，它们会去掉前缀并把结果再检查一遍。两个测试保证各部分不出错：任何模板都不能写以斜杠开头的地址，任何代码都不能设置作用于整个主机的 Cookie。见 [ADR 0012](./adr/0012-base-path-behind-a-reverse-proxy.md)。

**自动更新。** 设置了站点设置 `update_url` 时，`cmd/timevault-server/main.go` 中的 `runServe` 会用一个 `update.Source`（`http(s)` 地址或路径）、任务运行器（作为它的 `Drainer`）、正在运行的程序的路径（`os.Executable`，在交换任何东西之前取得）和审计记录器构建一个 `update.Updater`，并在调度器旁边的一个 goroutine 中运行它。启动后约 10 秒、每个间隔，以及调用 `CheckNow` 时（**立即检查**按钮、`POST /api/v1/update/check`），它会读取清单（`update.ParseManifest`）。与正在运行的版本不同的版本，会通过 `.part` 文件下载到 `timevault.new.exe`，只有大小和 sha256 与清单一致时才保留（`update.Download`），然后通过运行它来检查（`ExecChecker`：`version`，以及 `check-config`，即 `main.go` 中的 `runCheckConfig`：它加载引导设置并运行 `ValidateBootstrap`，不连接任何东西，所以数据库中的站点设置不在其内）。通过后，`Runner.Drain` 让 worker 不再取任务；正在运行的任务继续，新的任务保持排队。`Runner.Running` 为零时，`update.Swap` 把正在运行的程序重命名为 `timevault.old-<版本>.exe`，把新程序重命名为程序的名字（第二次重命名失败时会撤销第一次），`WriteMarker` 在旁边留下一个说明文件。`Updater.Run` 返回 `*update.Update`；之后 `runServe` 像任何一次关闭那样停止调度器、Web 服务器和任务运行器（这会释放数据库锁），并把一个 `restart` 交给 `serveAndRestart`。它要么以退出码 75 退出（`update.RestartExit`，供服务管理器使用），要么把进程变成一个启动器（`update.Supervise`），只要子进程以 75 结束，就用设置了 `TIMEVAULT_SUPERVISED_BY` 的环境再次把程序作为子进程运行；设置了该变量的程序始终以 75 退出（`update.Decide`），并且会监视启动器：它的标准输入是一个只由启动器持有的管道，管道结束时程序会有序关闭（`update.StopWithLauncher`，在 `runServe` 中启动），所以启动器被强制终止时不会留下任何程序。新程序读取并删除说明文件（`update.TakeMarker`），并记录 `done` 事件。交换之前出的任何问题都会让服务继续运行，状态和错误在 `Updater.Status` 中，设置页的卡片、`GET /api/v1/settings` 和页眉下面的提示显示的就是它（提示随每个页面一起发送，页面脚本换入的局部页面则通过 `X-TV-Notice` 响应头带上它）。审计事件（`app.update`，操作者 `updater`）中没有路径，也没有错误文本。见 [ADR 0014](./adr/0014-self-update-from-a-release-manifest.md)。

**账号头像。** 服务器说明头像在哪里、哪些名称可以有头像，以及策略必须允许哪个主机，但它不获取任何东西：`avatar_url`（其默认值来自 `server_host`，由配置中的 `parseAvatarURL` 得出）放入 `<meta name="tv-avatar">`；`avatar.go` 中的 `pictureSource` 把绝对地址的主机变成加到 `img-src` 的来源（`contentSecurityPolicy`，在 `New` 中构建一次；主机名带下划线时策略无法写出它，就用其所在域的通配符）；模板通过 `avatar` 和 `person` 局部模板在名称旁边写出 `data-avatar="<工号>"`（`Page.AvatarID` 会排除本地管理员、服务自己使用的名称和任何不是工号的东西）。`app.js` 中的 `initAvatars` 用 `Image` 把每张头像只加载一次，并且只在它即将被看到时才加载（`IntersectionObserver`）。出错，或者图片恰好是 480×320 像素（存放头像的主机对缺失的头像用 `202` 回答的占位图；头像本身以 `text/plain` 发送），都算没有头像，并在 `sessionStorage` 中记住十分钟；其他图片显示在 `<img>` 中，浏览器会用刚加载的内容来提供它。默认头像在页面里，任何环节失败时它都保留。

**Web 日志。** `web_log` 开启时（设置了 `TIMEVAULT_REDIS_URL` 时默认开启），`runServe` 会打开一个 `redisuser.Conn`（`Connect`：含 2 个连接的连接池，超时为 `TIMEVAULT_REDIS_TIMEOUT`），并为列表 `web_log_key` 启动一个 `weblog.Writer`。这个写入方就是交给服务（`service.Config.WebLog`，用于调度器）和服务器（`server.Options.WebLog`）的 `weblog.Sink`，审计记录器通过 `SetMirror` 得到的函数也向它写入；Web 日志关闭时，这个 sink 是 `nil`，也不设置镜像。这些行来自四个地方。`Server.requestLog`（除静态文件和 `/healthz` 之外，每个请求结束时）报告有人打开的页面或失败的请求（`webLogRequest`；route 是 `routeOf`，即匹配到的模式，绝不是输入时的地址；请求头 `X-TV-Auto` 标记页面脚本自己发起的重新加载）。`audit.Logger.Record` 在 `INSERT` 成功之后把每个事件交给镜像（`weblog.Audit`：结果决定状态码和级别，详情中只使用被拒绝请求的路由和程序更新的阶段）。调度器报告 `scheduler.queued`、`scheduler.error`，以及调试级别的 `scheduler.skipped`。`runServe` 在一切构建完成后写 `started`，在返回时写 `stopped`。`Writer.Write` 只把行放进容量为 1,024 的队列就返回，所以请求、审计记录或调度器的一个周期从不等待 Redis；一个 worker 取最多 100 行，用一次 `RPUSH` 发送。两个令牌桶在入口处截断大量涌入的行（页面行：平均每秒 10 行，突发 100 行；事件行：每秒 20 行，突发 200 行），队列满了就丢弃这一行，`RPUSH` 失败之后，worker 会暂停访问 Redis（30 秒，加倍直到 5 分钟），期间到来的行都被丢弃，并警告一次，其中 URL 的密码被遮盖（`Conn.Redact`）。关闭时先发送队列，最多等待 3 秒。一行是 `ip | time | message | status | level | host`，由 `Encode` 编码为 `zlib.compress(pickle.dumps(line, protocol=4))`，这是公司各应用共用的格式；账号以 `user=<工号>` 写在 message 中，因为不能增加字段。调试行（任务的轮询、自动重新加载、`scheduler.skipped`）只在 `log_level` 为 `debug` 时写入，这是 Web 日志对日志级别的唯一用法。`internal/redisuser` 仍然只读（`Store` 不使用 `Conn`），而 `config.parseWebLog` 会拒绝以账号或单点登录结果的键开头的键。见 [ADR 0016](./adr/0016-web-log-in-the-shared-redis-list.md)。

**页面导览。** 除登录页之外，每个页面的右下角、箭头旁边都有两个圆形按钮（`layout.html`）：**文档**，在新标签页中打开 `GET /help` 的链接（`pages_help.go` 中的 `handleHelp`、模板 `help.html`，对所有人开放），以及**页面导览**，开始逐步介绍本页。步骤写在模板里：`Page.Tour(key)`（`render.go`）给元素加上 `data-tour`、`data-tour-title` 和 `data-tour-text` 属性，文字取自消息 `tour.<key>.title` 和 `tour.<key>.text`，使用页面的语言（`i18n_tour.go`，英文和中文），所以页面没有显示的元素没有对应的步骤。`web/assets/js/tour.js`（普通脚本：没有库，没有内联脚本或样式）收集带有这些属性的可见元素，先是内容中的，然后是页眉和圆形按钮，让页面变暗，点亮一个部分，并显示一个气泡，其中有标题、文字、"第 n 步，共 N 步"和按钮；它不点击也不更改任何东西。显示另一个页面或使用后退按钮时，它结束；同一个页面自己刷新时（任务页在任务运行期间会这样），它继续。`TestEveryStepOfTheGuideIsTranslatedAndUsed` 检查模板所点名的每个步骤在两种语言中都有它的两段文字，并且没有多余的文字。

**文件夹大小。** 当实时列表中有文件夹时，`Service.ListLive` 会请 `fillFolderSizes` 提供它们的大小：一次 `NTFS.Subfolders` 调用（文件夹中直接包含的各个文件夹，以及从索引得到的其下所有内容的大小），答案缓存 10 秒。一次询问最多等待 2 秒；索引没有应答时，大小保持未知（显示为 `-`），并且 15 秒内不再询问。大小参与按大小排序。时间机器和版本页面读取的是目录库，不使用它们。

**NTFS 索引。** 除非站点设置 `search_index` 为 `off`，`runServe` 会创建一个 `ntfsindex.Manager`（`Config.Roots` 是 `sourceRoots`：目录库中所有监控文件夹的文件夹，每 10 秒重新询问一次，所以新增或移除的文件夹会被注意到），并在一个 goroutine 中运行它；`search.NewNTFS` 把它包装成服务的 `Provider`、`FolderLister` 和 `ChangeProber`。对每个有监控文件夹的盘符，Manager 会打开该卷，并在一个 goroutine 中建立一个 `index`。`build` 先读取日志的状态（`Journal`）并记住时间（`liveSince`），不解码名称地列出卷上的文件夹（`Dirs`，`FSCTL_ENUM_USN_DATA`），找出其中哪些在监控文件夹之内，再列出带大小和时间的条目（`Entries`，`FSCTL_QUERY_FILE_LAYOUT`），只对在其内的条目解码名称，并丢弃其余的。建立开始之后日志写下的记录会在之后应用；应用一条记录是幂等的，所以列表中已经出现的变化不会造成问题（`index.apply`：创建、删除、重命名的旧名称和新名称，以及写入，写入之后 `refresh` 会稍后重新读取大小和时间）。索引回答某个文件夹之下的搜索（名称包含每一个词，先文件夹、再按名称，命中很多时用部分堆选择）、文件夹中直接包含的各个文件夹及其下所有内容的大小（在被询问时才计算、被变化弄成过期的汇总）以及探测（`probe`：该文件夹之下有多少条目，以及包含它的监控文件夹自某个时间以来是否看到变化，或自那时起是否没有被监视）。如果过去 2 秒内没有读过日志，`Manager.find` 会在回答之前先读（探测总是会读）。日志被替换或被覆盖（`ErrJournalLost`），以及有文件夹从外部被移入监控文件夹，都会让该卷重新建立（后者最多每分钟一次）；在它就绪之前，该卷回答 `ErrNotReady`。`Manager.Health` 说明状态页显示的内容：空闲、正在建立、就绪，或者某个卷为什么无法建立索引（`ErrAccessDenied`、`ErrJournalOff`、`ErrUnsupported`）。见 [ADR 0018](./adr/0018-native-ntfs-index-replaces-everything.md) 和 [runbook.md](./runbook.md#搜索索引)。

**站点设置与启动。** `runServe` 分两步启动，因为一个站点设置（`job_workers`）决定了其余部分所需连接池的大小。它先从环境变量和 `.env` 读取引导设置（`loadBootstrap`、`ValidateBootstrap`），用一个自己的小连接池连接数据库，应用迁移（或检查迁移已应用：表 `site_settings` 就是其中之一），用 `sitesettings.Store.Load` 读取站点设置，用 `config.Load(config.SiteLookup(base, stored))` 构建配置，校验它（`ValidateServe`），然后才打开真正的连接池。已保存的设置放在一起无效时，服务会停止并给出点名问题的消息（`timevault-server settings` 是回头的路）。旧 `.env` 中现在属于站点设置的设置，以及已删除的 Everything 设置，会在一条警告中被点名（`config.LegacySettings`），其余则被忽略。站点设置页（`internal/server/site.go`）根据 `config.SiteSettings` 和 `SiteEffective` 构建表单，用 `siteChange` 和 `config.SiteProblems` 对照引导设置（`SiteBackend.Base`）检查提交的表单，用 `sitesettings.Store.Save` 在一个事务中保存差异（`diffSite`：与默认值相同的值不会被保存），并按键名记入审计（`auditSite`）。设置在重启之后才生效：页面把已保存的内容与服务启动时所用的比较（`SiteBackend.Running`），不同时提供**立即重启**。`SiteBackend.Restart` 在 `main.go` 中构建：它调用 `Runner.Drain`，如果仍有任务在运行就调用 `Resume` 并返回 `ErrJobsRunning`（`409 jobs_running`）；否则它让 `runServe` 像更新那样停止，`serveAndRestart` 再像更新之后那样（`update_restart`）重新启动程序。见 [ADR 0017](./adr/0017-site-settings-in-the-database.md)。

**版本数上限。** 一次备份提交了恢复点之后，如果文件夹有上限，`pruneAfterBackup` 会调用 `Engine.Prune`：持有备份源的写入锁，由 `catalog.PruneVersions` 删除（每个事务 500 个文件）这次备份改动过的文件中落在该文件最新 N 个已捕获版本之外的版本，并在同一个事务中把失去版本的恢复点标记出来（`recovery_points.partial`）。删除了版本之后，`Engine.SweepObjects` 会删除没有任何版本引用的对象（先删文件，再删它的记录），时间限制为 2 分钟；它只在没有备份持有备份引擎中那道闸门的共享侧时运行（它以尝试加锁的方式取得独占侧，绝不让备份等待），没有能运行或没有能完成的清扫会由调度器的下一个周期重复。备份内部的这一步清理从不等待：当该文件夹的恢复或校验排队或正在运行，或者它失败时，会改为排入一个针对整个文件夹的 `prune` 任务（`Service.StartPrune`，每个文件夹最多一个活动任务），它在重启后依然存在。设置或调低上限会排入同样的任务。任务队列让一个文件夹的清理与该文件夹的其他任务轮流执行（`jobs.Runner.claim`）：该文件夹的备份、恢复或校验正在运行时不会领取它的清理，清理运行时也不会领取它们中的任何一个，所以需要等待的任务保持排队状态，不占用任何 worker。调低上限在会删除版本时，首先需要 `confirm_prune`（`PruneNotConfirmedError`；预览与删除使用同一段 SQL），并且文件夹的清理正在运行时不能更改上限。在删除某个文件夹的版本期间（`Service.pruning`，或一个正在运行的 `prune` 任务），`StartRestore` 和 `StartVerify` 会拒绝该文件夹（`ErrPruneRunning`），而在此之前已排队的恢复或校验会等到删除结束（`waitWhilePruning`）。校验不完整的恢复点时会跳过与清单的比较。见 [ADR 0010](./adr/0010-version-limit-and-garbage-collection.md)。

## 数据模型（PostgreSQL）

历史使用"有效期区间"模型，因此恢复点只保存发生变化的部分：

| 表 | 含义 |
|---|---|
| `sources` | 监控文件夹：名称、文件夹（`root_path`）、`display_path`（NULL 表示没有；人们所知的网络路径，最多 520 个字符）、排除规则、`enabled`、`schedule_minutes`（NULL 表示仅手动，否则为 1 到 43200）、`last_run_at`（上一次备份运行结束的时间）、`last_run_ms`（它花了多久）、`last_walk_at` 和 `last_walk_items`（上一次完整扫描开始的时间，以及当时索引在该文件夹之下记录的条目数量），以及 `max_versions`（NULL 表示保留每个版本，否则为 1 到 10000）。 |
| `source_access` | 谁可以对文件夹做什么：每个文件夹和每个对象一行，包含 `kind`（`guest`、`everyone` 或 `user`）、`account`（工号，大写，仅 `user` 有）和 `level`（`browse`、`backup` 或 `full`；访客只能是 `browse`）。没有任何行的文件夹只有管理员能看到；管理员不在其中列出。 |
| `recovery_points` | 每次备份尝试一行：每个备份源内的序号 `seq`、`state`、`consistency`、计数器、清单摘要、`verification`，以及 `partial`（版本数上限删除了某些文件的较旧版本）。 |
| `nodes` | 每个路径位置一行，由（`parent_id`，精确 `name`）标识；`name_key` 是小写化的名称，用于排序和不区分大小写的查找。备份源的根节点 `parent_id` 为 NULL。 |
| `node_versions` | 路径位置经历的每个状态：文件夹或文件、大小、修改时间、属性、内容哈希、`state`（`ok`，或带原因的 `skipped`），在序号 `first_point`..`last_point` 之间有效（仍然有效时 `last_point` 为 NULL）。 |
| `objects` | 仓库中存在的内容对象（哈希、大小）。 |
| `jobs`、`job_events`、`restore_items` | 后台任务（类型 `backup`、`verify`、`restore` 和 `prune`）、任务日志行，以及恢复的逐项结果。 |
| `audit_events` | 只追加（触发器会拒绝 UPDATE 和 DELETE），对有耗时的操作带有 `duration_ms`。 |
| `site_settings` | 有值的站点设置：`key`（小写的名称，例如 `job_workers`）、`value`、`updated_at` 和 `updated_by`（保存它的账号，用 `timevault-server settings` 保存时是 `cli`）。没有行的设置取默认值；与默认值相同的值不会被保存。 |

两个恢复点之间没有变化的文件不产生任何新行。文件夹消失时，用一条递归语句关闭其整棵子树的版本。被删除后又重新出现的路径，会在同一个节点上产生新版本。重命名和移动会被记录为"删除 + 新增"（由于内容按哈希寻址，字节仍然只存一份）。

构建过程使用自己的序号写入新行，并把旧版本在"上一个已提交序号"处关闭。读取方只使用已提交的序号，所以在恢复点提交之前，这些改动都不可见。崩溃或取消之后，下一次构建（或启动时的恢复）会删除所有 `first_point` 大于最新已提交序号的版本，并重新打开所有在该序号处被关闭的版本。

## 恢复点生命周期

`building` → `committed`，或 `failed` / `aborted`。提交后 `verification` 为 `validated`（提交时的检查已通过：本次构建新记录的每个对象都存在且大小正确），完整性深度校验通过后为 `verified`，发现问题则为 `failed`；`verification = failed` 的恢复点不可恢复。普通备份不会重新检查它原样沿用的未变化文件的内容；完整性校验（Verify）可以发现之后丢失或损坏的仓库对象，而**完整重读**备份会把缺失的内容重新写入。界面显示的任务阶段：`snapshot_preparing` → `scanning`（枚举与复制按文件夹交替进行）→ `manifest_validating` → `committing` → `committed`；有版本数上限的备份之后还有 `pruning`（删除旧版本）和 `sweeping`（释放空间），并重新以 `committed` 结束。

**清单摘要**是对每个路径一行规范文本（路径、类型、大小、修改时间、属性、内容哈希）按固定顺序计算的 SHA-256。备份扫描时计算它；校验时从目录库重新计算。两者不一致说明提交之后目录库被改动过。

## 仓库

```text
<repository>/
  timevault-repository.json      格式版本与仓库 id
  objects/ab/cd/<sha256>         不可变内容，已设置只读属性
  tmp/                           正在写入的对象；过期文件会被清理
```

对象先以流方式写入 `tmp/`，边写边计算哈希，刷新到磁盘后才重命名为最终名称，因此 `objects/` 中永远不会出现不完整的对象。在恢复点提交之前，备份会先刷新接收了新对象的文件夹（`Barrier`），这样断电就不会让目录库指向一个目录项已丢失的对象；这是尽力而为的做法，尚未在真实断电下测试过。仓库会拒绝一个非空且不是 TimeVault 仓库的文件夹。写入相同内容的多个写入者通过按哈希前缀分段的锁，对"谁创建了对象"达成一致。

## 在线磁盘上的一致性

MVP 读取的是在线文件系统（`consistency = live_scan`），不使用 VSS 快照。为避免保存"撕裂"的副本：

- 在复制前后，从已打开的句柄读取文件大小和修改时间。若两者不同，则重新读取（最多三次），之后记录为*未能备份*并写明原因。
- 被其他进程锁定（共享冲突）或无法读取的文件会记录为*未能备份*；如果之前存在可用版本，则保留旧版本并记录警告。
- 无法列出的文件夹保持其之前的状态，其内容绝不会被当作已删除。
- 联接点（junction）、符号链接和其他重解析点不会被跟随，而是记录为*未能备份*。如果文件或文件夹在其所在文件夹被列出之后被替换成链接，也会被检测到并且不会被跟随，因此不会把另一个文件的内容记录在错误的路径下。
- Windows 无法安全表示的名称（保留设备名、结尾为点或空格、非法字符）会被跳过并计数。
- 深度超过 256 层文件夹的路径会被记录为*未能备份*，因为浏览和恢复最多接受这个深度。
- 重叠检查（备份源与仓库、恢复目录以及其他备份源之间）比较的是文件夹的真实位置，即解析了联接点和链接之后的位置；添加备份源时和每次备份开始时都会检查。

界面把每个恢复点都标注为*实时扫描*，避免被误认为快照。

## 恢复流程

1. **预览**（`Preview`）：校验请求，在所选恢复点解析每个所选路径，把每一项与目标位置对比并分类（创建、替换、改名、跳过；已有文件只有在大小、修改时间和 SHA-256 都与目录库一致时才算"完全一致"，因此规划时会读取已有文件），并检查每个内容对象存在且大小正确。不会写入任何内容。结果带有该计划的摘要。
2. **确认**：令牌是对（用户、计划摘要、15 分钟有效期）的 HMAC。服务会重新生成计划并比较摘要，所以目标位置变化或请求不同都会使预览失效。替换已有文件还需要额外的明确确认。
3. **执行**（后台任务）：再次生成计划，如果存在被阻止的项目（内容缺失、未备份成功、名称不安全），除非选择了*允许部分恢复*，否则不会写入任何内容。每个文件从仓库流式写入目标文件夹中的临时文件，校验 SHA-256 和大小，应用修改时间和属性，最后才重命名到位。所有路径都通过针对目标文件夹的 `os.Root` 访问。逐项结果会保存下来，供任务页面查看。

恢复只会写入 `TIMEVAULT_RESTORE_ROOT` 之下、由请求者命名的文件夹（不存在时创建；已存在时，例如重复恢复，由冲突策略决定如何处理已有的文件）。目标文件夹必须是普通文件夹：如果它已经作为联接点或符号链接存在，恢复会被拒绝；恢复根目录与仓库以及每个备份源比较的是它们的真实位置。恢复操作不会删除或覆盖源数据和仓库内容。
